# ADR-033: Private Properties Are Per Type

[ADRs](./README.md)

> Status: ✅ Adopted

## Context

The properties of an `object` or `service` are private. Only the type itself can access them. A subtype therefore cannot know which properties its supertype has.

If a subtype could not reuse a property name that its supertype happens to use, the supertype's private implementation would leak through the error message. Adding a property to a supertype would also break existing subtypes.

## Decision

Each `object`/`service` type owns its properties. A subtype may declare a property with the same name as a property in its supertype. They are two distinct properties.

A method only sees the properties of the type that declares it. A method declared in the supertype reads the supertype's property, even if the instance is of the subtype.

The frontend does not report a name clash between properties of a subtype and its supertype, and it does not merge or inherit properties. The `properties` of a type declaration in the CIR list only the properties declared by that type itself.

The backend must lower the properties of each type separately, so that same-named properties do not conflict.

## Consequences

### Negative

- A subtype can shadow a supertype's property name, which might surprise someone reading both types side by side. The privacy rule means they normally don't see both.
- Each instance holds the properties of every type in its hierarchy.

### Positive

- Encapsulation holds: a supertype may add, rename or remove properties without affecting its subtypes.
- The frontend needs no knowledge of the supertype's state to validate a subtype.

## Alternatives Considered

- Report a name clash as an error.
  - This leaks the supertype's private properties and makes adding a property a breaking change.
