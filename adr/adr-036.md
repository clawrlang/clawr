# ADR-036: Standard Library for Clawr

> Status: 📝 Proposed

## Context

There should be a standard library for Clawr that provides commonly used functions and utilities, ensuring consistency and reducing the need for developers to implement these from scratch.

The standard library should include functions for common tasks such as string manipulation, array operations, mathematical computations, and date/time handling. It should also provide utilities for error handling, logging, and configuration management. By having a well-defined standard library, Clawr can promote best practices and improve developer productivity.

The standard library should include:

- The `subset` and `type` definitions of [ADR-032](./adr-032.md)
- `copy(of:)` function that creates a shallow copy of a reference-counted object (allowing it to be transferred to the opposite isolation semantics)
- `print(_ x: HasStringRepresentation)`
- The built-in `trait`s, such as `HasStringRepresentation`

(add more standard library functions as needed)

Traits should affect syntax:

- `HasStringRepresentation`: can be used in string interpolation.
- `Equatable`: can be compared using equality operators (`==` and `!=`).
- `HashEquatable`: can be used as keys in hash-based collections, such as dictionaries and sets. Its hashing contract is being explored in [ADR-037](./adr-037.md).
- `Ordered`: can be compared using strict relational operators (`<`, `>`).
- `Ordered` and `Equatable`: can be compared with “-or-equal” operators (`<=`, `>=`).
- `Iterable`: can be used as the iterated collection in a `for`-`in` loop (or other iteration constructs).
- `Serializable` (as JSON, YAML…)

Some definitions are used only in static analysis, while others affect runtime behavior. Runtime-backed functions may be provided by `libClawr` through `extern`; precompiling Clawr function bodies is deferred.

## Decision

### Source of truth: Clawr declarations

The standard library is declared in Clawr source files (e.g. `packages/stdlib/*.clawr`). The frontend parses and registers those declarations for static analysis. `print(_:)` is resolved from the stdlib declaration; `copy(of:)` remains hardcoded pending generics. Only signatures are loaded for now; precompiling the declarations into a serialised form is deferred.

### `extern`

A function whose implementation is provided by the runtime (`libClawr`) is declared with the keyword `extern` and has no body:

```clawr
extern func print(_ x: HasStringRepresentation)
```

- `extern` declarations take part in static analysis like any other function.
- Runtime-backed declarations must agree with the backend and runtime ABI. The current backend provides `print` through the runtime header.
- Numeric `subset` and `type` declarations are used for static analysis. Traits used for runtime dispatch also require matching runtime interface descriptors and witnesses.
- Functions with Clawr bodies in the stdlib need precompilation and are out of scope for now.

### Namespace

Stdlib declarations live in the `clawr` namespace (ADR-019), which is implicitly available to programs. Its declarations can be used unqualified, and declarations in the program scope shadow stdlib declarations. Explicit source-level qualification is deferred. References to stdlib traits in CIR retain their canonical namespace and use the `interface` value-set; they do not redeclare the runtime's interface descriptor.

### Scope

The frontend creates a stdlib scope as the parent of the current root scope. Name lookup falls through from the root scope to the stdlib scope. The language server uses the same scope.

### Prerequisites and order

1. Add full `namespace` syntax and qualification for free functions and types (deferred; the initial standard-library aliases use an implicit parent scope).
2. Parse `extern func` (no body) and carry it through the semantic model. _(Done in the frontend: `extern` is a keyword and a third implementation case; it registers the signature without emitting a declaration.)_
3. Add the stdlib parent scope. _(The scope now provides the named numeric aliases from `packages/stdlib/stdlib.clawr`.)_
4. Move `print(_:)` to an `extern` declaration. _(The stdlib signature and trait are registered for static analysis; primitive trait arguments are boxed and user-defined conformances use the runtime trait ABI.)_
5. Add the built-in traits, then the `real` conversions (`binary32`/`binary64`).
6. Move `copy(of:)` once generics (see [the generics draft](./drafts/generics.md)) can express its constraint.

## Consequences

- The standard library is now a first-class part of the language, with declarations available for static analysis.
- The separation between static analysis and runtime behavior is clearer, with `extern` functions explicitly marked and handled.
- The frontend can resolve standard library function signatures from source; `copy(of:)` remains implementation-specific until generics are available.
- The use of `extern` provides a clear contract between the language and its runtime, improving modularity and clarity.
- Precompilation of Clawr function bodies is deferred, simplifying the initial implementation and focusing on static analysis.
- The approach lays the groundwork for future enhancements, such as precompilation and optimization of Clawr function bodies, without complicating the current implementation.
