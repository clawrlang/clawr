# ADR-020: Singleton `service`

[ADRs](./README.md)

## Status

💡 **Proposed**

> An idea to be considered for adoption

## Context

[ADR-018](./adr-018.md) removes `companion` from the construction process. [ADR-019](./adr-019.md) proposes to replace “static” `companion` methods with free functions in a `namespace`.

Factories are still useful. And so is having a single place to go to for such construction.

## Decision

Add a new keyword — e.g. `singleton`, `singleton service` or `instance` — for declaring a `service` that cannot be created multiple instances of.

This object will function as a normal `service` and can hence conform to `role`s but not `trait`s.

## Rationale

- Singletons are useful for other use-cases than just construction.
- The fact that it conforms to a `role` enables dependency injection/-inversion patterns.

## Consequences

### Negative

- The initialization of Singletons must be implemented in generic fashion by the backend.
- The backend must be able to preempt concurrency issues in the initialization/first access.

### Positive

- Makes the Singleton pattern easy for the programmer — it is part of the syntax.
- A Singleton for parallel execution might be able to preclude a lot of concurrency issues.

## Alternatives Considered

- Allowing a `companion` to conform to `role`s. (Thereby essentially becoming a singleton.)
