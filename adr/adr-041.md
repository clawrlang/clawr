# ADR-041: Binary and Ternary Fields

> Status: 📝 Proposed

## Context

I/O formats and algorithms can specify sequences of binary or ternary states, independently of the hardware executing the program. Clawr needs to represent and manipulate those sequences without treating the storage representation of an `integer` as part of the language.

## Implemented Subset and Broader Proposal

The compiler implements an initial subset of binary and ternary fields. Its current syntax and semantics are specified in [Binary and Ternary Fields](../spec/language/builtin-types/fields.md). This ADR records the broader proposed design; it does not adopt the unimplemented operations and I/O abstractions below.

### Values and widths

The [language reference](../spec/language/builtin-types/fields.md) defines current field kinds, lane order, lengths, and operations. Generic widths and subscript syntax remain open design questions for future extensions. Any algorithm-specified width should remain independent of backend word size.

Field literals use `0b` for binary lanes, `0t` for ternary lanes, and `0x` for hexadecimal groups of four binary lanes. They preserve leading zeroes and infer exact widths; underscores are visual separators only. Integer literals remain decimal, independently of the platform's numeric representation. String constructors remain available for dynamic input and empty fields.

### Manipulation

The current pointwise operations, shifts, lane access, slicing, and concatenation are specified in the [language reference](../spec/language/builtin-types/fields.md). Future work may add lane replacement, lane-position rotation, and additional ternary operations. Their syntax, bounds, and error behavior remain to be designed. State rotation of ternary lane values is distinct from rotation of lane positions.

### Encodings and I/O

The initial [octet file-stream API](../spec/stdlib/README.md#octet-file-streams) implements binary file input/output using MSB-first groups of eight binary lanes. It rejects partial-octet writes, exposes caller-selected read sizes and EOF, and uses panic for errors. Ternary wire encodings, numeric codecs, and file adapters for the logical stream roles remain future work.

The [logical lane-stream contract](../spec/stdlib/streams.md) defines separate binary and ternary input/output roles without requiring generics. Counts are lanes; `readSome(maxLanes:)` may return an earlier short read, and only an empty field signals EOF. Exact-read helpers assemble algorithm-sized blocks or panic on premature EOF. Writes preserve lane order and add no padding or records. Aliases share endpoint state; errors remain panics. In-memory implementations accept arbitrary final lengths and provide immutable output snapshots.

The existing octet file API keeps its current count, alignment, and EOF behavior; it is not silently reinterpreted as a lane-stream adapter. Future file adapters must specify treatment of incomplete final storage units. Repartitioning writes alone does not require framing: a three-bit write followed by a five-bit write can form one octet. Text encoding remains a separate layer.

A field is not an integer or a physical buffer. Reading or writing requires an explicit format and an I/O interface; neither the field type nor the host architecture implicitly determines a wire representation. An encoding must specify lane order, grouping, symbol mapping, length or framing, padding, and what happens to malformed input. Endianness belongs to an encoding of multi-lane values, not to the field's storage.

For example, an octet-oriented binary protocol can define each octet as eight binary lanes, with the first lane corresponding to the octet's most significant bit. Under that particular convention, `10000000` is octet `0x80`. Another protocol may specify a different ordering. A non-multiple of eight lanes needs an explicit length and padding rule; an arbitrary octet stream does not carry that bit length on its own. I/O must not expose the backend's in-memory packing as the protocol encoding.

Ternary fields also require a specified encoding. For illustration, a binary transport could encode each lane using two bits: `false` as `00`, `ambiguous` as `01`, and `true` as `10`, rejecting `11` as invalid. This is just an example format, **not** the runtime's internal mapping or a standard wire format. A ternary transport can use a different mapping and framing. A binary-to-ternary encoding must preserve all binary lanes; discarding one physical trit state is one possible implementation, not a portable wire protocol or a requirement on hardware.

Encoding and decoding numeric values are explicit operations whose format defines radix, digit mapping, significance order, signedness and out-of-range behavior. They are mathematical mappings, not casts of the backend's integer storage. For example, unsigned binary decoding of `1001` with the first lane most significant yields integer 9 on either kind of machine. One ternary field kind is sufficient for balanced and unbalanced ternary encodings: each encoding specifies how its three states map to digits. Clawr's `integer` includes negative values. Whether numeric codecs are part of the initial I/O library and which error APIs they use remain open; silent clamping, wrapping, or taking an absolute value must not be assumed.

### Algorithms and representation

Structural operations and pointwise logic can express many data transforms, but algorithms may also require operations with explicitly defined numeric interpretations. For example, SHA-256 and ChaCha20 use addition modulo 2³²; field logic alone does not make that addition automatic. It can be implemented as a lane algorithm, or by an explicit codec and wrapping operation. Such operations belong in libraries or separately specified abstractions, not implicitly on abstract `integer` storage. Correctness, performance, and constant-time behavior for cryptographic code require separate implementation guarantees.

Ternary algorithms may need different logic, carry rules, rotations of lane states, or encodings; binary XOR is not a universal ternary primitive. The implemented operations do not claim to cover every ternary algorithm. A backend may pack or chunk fields differently, but must preserve their observable sequences and operations; internal invalid states must not become observable field values.

### Open questions for future extensions

- How should generic widths, lane rotation and caller-selectable shift fill be expressed?
- Which additional operations are language primitives and which are library functions, and how should structured errors eventually be exposed?
- Which file, network, and text adapters should implement the logical stream roles, and which additional binary and ternary encodings should they support?
- How should explicit numeric codecs expose width, signedness and overflow or malformed-data errors?
- Which additional ternary truth tables are useful, and what guarantees should an eventual crypto-oriented library provide?

## Rationale

1. [ADR-000](./adr-000.md) mandates platform agnosticity
2. Reading ternary data on a binary computer (and vice versa) should be possible
3. I/O formats and algorithms can specify a lane count and encoding without depending on the host's native word size or radix.
4. Both field kinds can be emulated on hardware with a different radix, though their performance and implementation costs will vary.

> [!tip]
>
> Ternary fields can be emulated using two separate binary fields. One bit from each field (in the same relative positions) would emulate the same ternary bit (or trit). This makes it easy to perform lane-wise operations using standard bit-wise operations.
>
> Two bits model four states — not just three — so one state per position would have to either be considered invalid or equal to another.

## Alternatives Considered

- Allow ternary fields only on ternary platforms. Allow binary fields on both.

## Consequences

### Positive

- Code can be made more reusable
- Binary computers can understand raw ternary data

### Negative

- Emulation, packing, and conversions may cost time and space.
- Portable semantics do not by themselves define a wire format or guarantee efficient or constant-time implementations.
