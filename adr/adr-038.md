# ADR-038: Multi-File Programs and Future Modules

> Status: ✅ Adopted

## Context

A program should be able to organize its declarations across multiple source files without requiring each file to be compiled as a separate program. The frontend also needs to load the standard library from multiple files ([ADR-036](./adr-036.md)).

This decision covers **multi-file programs**, not separately importable modules or packages. The latter require further decisions about identity, visibility, dependencies, and distribution.

## Decision

Analyze an ordered set of source modules together in one program scope and emit one combined CIR artifact. This permits multi-file programs without introducing a package or separate-compilation system.

> [!note]
>
> Current rules are defined in [Programs and Source Modules](../spec/language/programs.md). Example-tool behavior belongs in [Building Multi-File Programs](../guides/implementation/programs.md) and [VS Code Projects and Independent Scripts](../guides/ide-reference/projects.md). This ADR records the reasoning, not another copy of those contracts.

### Separate modules and libraries are deferred

This decision does not define import syntax, separate module scopes or exports, package identity or versions, dependency resolution, library entry-point rules, separate compilation, or linking independently compiled CIR modules. In particular, none of the package-identity or version-unification options below is adopted by this ADR.

## Rationale

- Shared analysis lets a program be split into files without inventing a premature package system.
- Explicit source order preserves the existing source-order rules for aliases.
- One combined CIR works with the existing backend while retaining the possibility of independently distributed CIR described in
  [ADR-001](./adr-001.md).
- The stdlib and user programs can reuse ordered source parsing while keeping their scopes and emission policies distinct.

## Alternatives Considered

- **Require a single source file:** simple, but forces unrelated declarations into one file.
- **Make every file a separate importable module now:** provides isolation and separate compilation, but requires unresolved language and linking decisions.
- **Discover all sources implicitly in the compiler:** convenient for small projects, but makes source membership and alias order less explicit. The editor provides discovery separately and supports an explicit override.

## Consequences

### Positive

- Declarations and diagnostics can span files while the backend still consumes a single CIR artifact.
- Existing programs remain usable, subject to the explicit one-`@main` requirement for executable builds.

### Negative

- Files do not isolate names; declarations in the same program can conflict.
- Alias resolution and global initialization can depend on source order.
- There is no separate compilation, package dependency management, or cross-file rename.

## Future Design Questions

The earlier multi-module sketch identified issues that remain open:

- **Identity:** how package, version, module, namespace, and name contribute to type and function identity, including conflicting versions of the stdlib.
- **Visibility:** which declarations a module or package exports and whether dependencies can be hidden or re-exported.
- **Distribution:** whether a module produces its own CIR, how a linker combines modules, and how source locations and provenance are represented in bundled CIR.
- **Versioning and linking:** whether compatible versions unify, incompatible versions coexist or conflict, and how runtime symbols and ABI requirements are resolved.

Those questions need a separate design before separately compiled libraries or importable modules can be considered implemented.
