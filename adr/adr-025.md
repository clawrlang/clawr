# ADR-025: The `real` Datatype: Precision axes and bases

[ADRs](../README.md)

## Status

💡 **Proposed**:

> An idea to be considered for adoption

## Context

`integer` represents all of ℤ. A range constraint lets the backend choose a native representation. `real` should likewise mean all of ℝ, but irrational numbers like π and √2 cannot be stored exactly in finite memory, so a stored `real` needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

## Decision 1: Precision Kinds and Bases

There are two precision kinds over a closed set of bases:

| Kind      | Meaning                                         | Example           |
| --------- | ----------------------------------------------- | ----------------- |
| `scale n` | **Absolute** resolution: multiples of $b^{-n}$  | `scale 2` (cents) |
| `sig n`   | **Relative** resolution: $n$ significant digits | `sig 15`          |

| Keyword | Meaning                          | Base |
| ------- | -------------------------------- | ---: |
| `dec`   | Decimal (the default if omitted) |   10 |
| `bin`   | Binary                           |    2 |
| `ter`   | Balanced ternary (reserved)      |    3 |

For `sig n b`, the base $b$ determines the precision rules. For `bin` and `ter`, $b$ is the precision base, and the storage base is a backend property as long as precision guarantees are met. For `dec`, however, $b$ is both the precision base and a strict requirement for a base-10 storage/representation model.

### `scale n`

A `scale n` precision implies a rational value ($\text{numerator} / \text{denominator}$) where the denominator is $b^n$ (the declared precision parameters) and only the numerator is actually stored in the representation. A `scale n` grid includes $0$; the smallest non-zero magnitude is exactly $b^{-n}$, fully specified and platform-independent. No guarantee boundary is needed: the grid itself defines the resolution, and it is native on any base (the numerator is an integer).

### `sig n`

A `sig n` precision does not imply any specific storage layout for `bin` and `ter`. The backend may choose freely as long as it can store the entire range with at least the requested precision in base $b$. However, `dec` types strictly require a decimal storage/representation model.

> [!warning] Implementation-agnostic, not result-agnostic (for `bin`/`ter`).
>
> A backend may store a `bin` or `ter` `sig` value in any grid that delivers at least the declared precision, while `dec` types strictly require a base-10 representation. The storage base for `bin` and `ter` need not match the declared base. Consequently, results may differ between platforms for binary/ternary, but `dec` maintains decimal-exact behavior. A `sig` type is a portable statement about _precision_ (and for `dec`, decimal representation), not necessarily bit-identical results across non-decimal bases. `scale` is the precision kind that is both implementation-agnostic and result-agnostic, because it stores only an integer numerator.

**The precision guarantee.** For a declaration `real (a...b) sig n base` with $M = \max(\vert{}a\vert{}, \vert{}b\vert{})$ and precision base $b$:

$$x_{\text{guarantee}} = \min\!\left(M \cdot b^{-2n},\ \frac{b^2}{M}\right)$$

For every stored value with $\vert{}x\vert{} \ge x_{\text{guarantee}}$, precision $n$ in base $b$ is guaranteed. This is the whole contract. The backend must meet it; a backend that cannot must reject the declaration at compile time with an error naming $x_{\text{guarantee}}$.

**Why the two terms.** The first term $M \cdot b^{-2n}$ gives $n$ significant digits of headroom below the top of the range, which is the natural relative-precision floor for a bounded interval. For a _narrow_ range it is the binding one: `real (0...1) sig 5 bin` gives $2^{-10}$. The second term $b^2/M$ is the smallest normal magnitude of an IEEE-like format with maximum $M$ and the IEEE exponent balance $e_{\max} + e_{\min} \approx 1$. For a _wide_ range it is the binding one: `real (-(2^53-1)·2^971 ... (2^53-1)·2^971) sig 53 bin` gives $2^{-1022}$, exactly binary64's smallest normal. Without the second term, a wide range would give a vacuous guarantee ($10^{276}$ for binary64's range), which is meaningless. The $\min$ picks whichever term is tighter for the given range.

**Below $x\_{\text{guarantee}}$** the language makes no guarantee. A value with $\vert{}x\vert{} < x_{\text{guarantee}}$ may be stored with reduced precision, may be stored exactly if it happens to land on the backend's grid, or may be unrepresentable (in which case storage panics). Which of these occurs — and at what magnitudes — is a backend property, not part of the type. Programmers who need defined behaviour arbitrarily close to zero use `scale`, whose grid is exact and platform-independent.

For a range that contains only $0$ (`M = 0`), $x_{\text{guarantee}} = 0$ and the guarantee is vacuous.

**Calibration.** $x_{\text{guarantee}}$ must be large enough that a type whose range and precision exactly match an IEEE representation can use that representation directly, and small enough that it does not admit a sloppy implementation. The second term is chosen precisely so that IEEE formats satisfy it exactly, with no epsilon and no tolerance needed.

### Rationale

- Any `real` number can be expressed on the form $m \cdot b^e = m / b^{-e}$.
- A `sig n` grid cannot extend to arbitrarily small magnitudes in fixed-size storage, so a documented boundary below which precision is not guaranteed is necessary.
- That boundary can vary by platform for `bin`/`ter`: a binary processor will necessarily have a different one from a ternary one. Documenting $x_{\text{guarantee}}$ as a floor on $\vert{}x\vert{}$ minimises the risk of unpleasant surprises.
- Stating the guarantee directly as "precision $n$ holds for all $\vert{}x\vert{} \ge x_{\text{guarantee}}$" keeps the contract independent of _how_ a backend represents values near zero. Subnormals, smallest normal, mantissa width — all are backend-internal.
- The $\min$ with $b^2/M$ makes the guarantee meaningful for wide ranges (IEEE-format ranges) without weakening it for narrow ranges. Binary64 satisfies $b^2/M$ exactly (up to a factor $1 - 2^{-53}$, in the safe direction); no tolerance is needed.
- The distinction between absolute (`scale n`) and relative (`sig n`) precision allows developers to choose the appropriate trade-off between fixed resolution and result identity.

### Consequences

- Enforces a consistent and predictable behaviour for arithmetic operations _within a platform_, reducing the likelihood of subtle bugs related to precision and rounding.
- Simplifies reasoning about numerical accuracy by ensuring that all values are rounded only once at storage.
- May introduce cross-platform variation in results for `sig` types using `bin` or `ter`. This is documented and deliberate. `dec` types guarantee base-10 exactness.
- Limits flexibility in intermediate computations, as multiple roundings at different stages are not allowed.
- Backends whose representation cannot guarantee $n$ digits at all $\vert{}x\vert{} \ge x_{\text{guarantee}}$ must reject the declaration at compile time, naming $x_{\text{guarantee}}$ and the target's actual precision boundary.
- $x_{\text{guarantee}}$ need not appear in source syntax; it is an internal contract, but it may surface in diagnostics and in a `--explain-types` mode so that programmers can understand behaviour below the boundary without a `floor`-like clause.

### Alternatives Considered

- Using only $M \cdot b^{-2n}$: gives a vacuous guarantee for wide ranges (IEEE-format ranges), which is the common case for `float64`-style types.
- Using only $b^2/M$: gives a vacuous guarantee for narrow ranges, where the maximum is not determined by exponent balance.
- Introducing a tolerance $\epsilon$ on $x_{\text{guarantee}}$: unnecessary — binary formats satisfy $b^2/M$ exactly, and ternary formats either satisfy it or do not, independently of any $\epsilon$.
- Exposing a `floor`-style clause (e.g. `sig 5 bin floor 1e-6`): rejected because it adds surface syntax for a backend-internal concern; `scale` already covers the case where defined behaviour near zero matters.
- Documenting the backend's minimum representable magnitude and smallest normal separately: rejected because it exposes implementation detail; one guaranteed-precision floor on $\vert{}x\vert{}$ is enough.

## Decision 2: Compatibility and Precision

Compatibility is universe and range; precision is representation

A `subset` of `real` is an exact range, as for `integer`:

```clawr
subset probability = real (0.0...1.0)
```

Precision is written where storage is declared (variables, `data` fields, array elements, parameters, returns), not in the `subset`:

```clawr
mut p: probability scale 5            // multiples of 0.00001
mut q: probability sig 5              // 5 significant digits
mut y: real (1.0...1000.0) sig 15     // bounded and away from zero
mut balance: real scale 2             // unbounded range: lowered to an arbitrary-size integer
mut d: real big                       // arbitrary-size decimal
```

A `type` is a subset plus a representation. **Compatibility is decided by the universe and the range only.** Precision never makes two types incompatible. Equality also compares values and ignores representation, so `1.20` at `scale 2` equals `1.20000` at `scale 5` _within the same storage base_.

**Lowering may use a different base for `bin`/`ter`.** A backend may store a `sig` value (see [Decision 1](https://www.google.com/search?q=%23decision-1-precision-kinds-and-bases)) in any grid that delivers at least the declared precision ($n$ significant digits in base $b$) at every magnitude in the guaranteed region, provided that `dec` types are strictly stored using a base-10 representation. For `bin` and `ter`, the storage base need not match $b$: a `sig 15 bin` value may be stored in binary64 or ternary as long as each satisfies the precision requirement. A backend that stores in a different base for `bin`/`ter` is fully conformant.

`scale` is unchanged: it stores an integer numerator, which is exact on every base. Consequently `scale n b` is both implementation-agnostic _and_ result-agnostic, and is the appropriate tool when cross-platform result identity matters.

Rounding is into the **storage grid**, once (see ADR-026), after the value has been checked against the declared precision. The declared precision is a _requirement_, not a storage format.

### Rationale

- Compatibility is determined solely by the universe and range, ensuring that different representations of the same logical type are considered equal.
- Allowing any storage base that meets the precision requirement for `bin`/`ter` makes the specification implementation-agnostic across hardware formats, while requiring base-10 representation for `dec` preserves decimal exactness (e.g. `0.1 + 0.2 == 0.3`).
- Single rounding into the storage grid ensures predictable behavior and avoids cumulative rounding errors within a platform.
- The distinction between compatibility and precision allows developers to reason about correctness independently of performance optimizations related to storage and computation.
- `scale` is called out as the result-agnostic choice; `sig` with `bin`/`ter` is documented as precision-portable but not result-portable.

### Consequences

- Ensures that different representations of the same logical type are treated consistently _within a platform_, improving reliability and predictability.
- Allows backends to use native formats for `bin`/`ter` that satisfy precision requirements without emulation, while mandating base-10 storage for `dec`.
- Reduces the risk of cumulative rounding errors by enforcing single rounding at storage.
- Cross-platform identity is guaranteed for `dec` and `scale` types, but not necessarily for `bin`/`ter` `sig` types across differing architectures.
- Provides a clear distinction between compatibility and precision, aiding developers in reasoning about correctness and performance optimizations.

### Alternatives Considered

- Requiring the storage base to match the declared base for all bases: simpler semantics and result-agnostic, but forces binary hardware to emulate ternary types and vice versa; rejected for `bin`/`ter` in favour of implementation-agnosticism.
- Allowing `dec` to be lowered to binary floating-point: rejected because `0.1 + 0.2 == 0.3` must hold for decimal representations.
- Not distinguishing between compatibility and precision, which would simplify the type system but could lead to unexpected behavior when different representations of the same logical type are compared.
- Allowing multiple roundings at different stages of computation, which could provide more flexibility but would complicate reasoning about numerical accuracy.

## Decision 3: Exact Values and Single Rounding at Storage

### 3. Semantics: exact values, one rounding at storage

Arithmetic computes the exact result. A value is checked against the **declared precision** (at most $n$ significant digits in base $b$), then rounded once into the **storage grid** when stored.

- **Cross-base operands are rejected.** An arithmetic expression whose operands' precision bases differ is a compile error unless one operand is explicitly converted via `round(x, to: ...)`. This enforces strict clarity and avoids hidden translation costs.
- **Division and square root are not exact.** A bare `/` between `real big` values requires a target precision or named call (`divide(a, by: b, to: sig 20 dec)`).
- **NaN, ±∞ and signed zero do not exist** for reals. Division by zero, overflow, and underflow panic.
- **Rounding:** One default mode (round to nearest, ties to even), plus an explicit `round(x, mode: ...)`.

**Where the declared precision applies.** For `sig n`, the declared precision is authoritative at and above $x_{\text{guarantee}}$: a value is checked against the ideal $n$-digit grid, then rounded once into whatever storage grid the backend uses. Below $x_{\text{guarantee}}$, the language makes no precision guarantee; the backend's actual representable values govern, and values it cannot represent at all panic at storage. The single-rounding rule applies within whichever grid is authoritative for the value's magnitude; it never rounds twice.

**Results may differ across platforms for `bin`/`ter`.** Two backends that both satisfy the same `bin` or `ter` `sig` declaration may produce different stored values for the same source expression, because their storage grids differ. Equality compares stored values exactly within a platform; it does not guarantee cross-platform identity for `bin`/`ter`. For `scale` and `dec`, the storage grid preserves exact rational/decimal representation, so results are consistent across platforms.

### Rationale

While it is easy to create a common scale factor as the LCM of the operand scale-factors, there is no general way to reduce the result to a `dec`, `bin`, or `ter` scale. At least not if ternary is an alternative. Allowing different storage bases for `bin`/`ter` is the price of implementation-agnosticism.

### Consequences

- Ensuring exact values and single rounding at storage simplifies reasoning about numerical behavior and avoids cumulative rounding errors within a platform.
- Rejecting cross-base operands without explicit conversion prevents hidden performance costs and maintains clarity in arithmetic expressions.
- By not supporting NaN, ±∞, and signed zero, the model enforces strict correctness and eliminates special-case handling in numerical computations.
- The single rounding at storage ensures that arithmetic operations are predictable and consistent within a backend.
- Cross-platform result identity is guaranteed for `scale` and `dec`. For `bin`/`ter` `sig`, it is not, and this is documented.

### Alternatives Considered

- Allowing implicit cross-base conversions, which would improve convenience but could introduce hidden performance costs and reduce clarity.
- Supporting NaN, ±∞, and signed zero, which would increase compatibility with standard floating-point semantics but complicate reasoning and special-case handling.
- Requiring storage base to match declared base for all types: result-agnostic but forces emulation for non-decimal non-native hardware; rejected for `bin`/`ter` in favour of implementation-agnosticism.

## Decision 4: Assignment, Equality, and Literals

- **Range is checked as type compatibility** (compile-time where provable, otherwise dynamic panic).
- **Precision check at assignment** is against the declared precision: above $x_{\text{guarantee}}$, the value must have at most $n$ significant digits in base $b$. Below $x_{\text{guarantee}}$, the check is against the backend's actual representable values. The value is then rounded once into the storage grid.
- **Precision is lost only explicitly**, with `round(x, to: ...)`. Across precision bases (`dec`, `bin`, `ter`) `round` is required at compile time.
- **Equality** compares stored values exactly within a platform, making it transitive and independent of representation _within that platform_. Cross-platform, `a == b` may differ for `bin`/`ter`. `isclose(a, b, tol)` is a library function.
- **Literals** are exact rational values checked against the declared precision and then rounded once into the storage grid, with exact rational folding for `const` arithmetic.

### Rationale

- Assignment enforces that values conform to the declared precision, ensuring that precision is maintained and any necessary rounding is explicit.
- Equality checks are exact within a platform, providing predictable and consistent behavior regardless of the underlying representation.
- Literals are validated against the declared precision at compile-time, allowing for early detection of precision mismatches and ensuring that constant expressions are correctly folded.

### Consequences

- Inferring a singleton subset for `const` declarations allows the compiler to optimize aggressively while ensuring constant values remain unchanged.
- Requiring explicit precision for `mut` declarations prevents unintended precision loss and enforces clarity in variable representation.
- This approach provides a balance between safety and flexibility, enabling efficient and correct numerical code while maintaining control over precision and representation.
- Cross-platform equality is not guaranteed for `bin`/`ter` `sig`; this is documented and is the reason `scale` and `dec` exist.

### Alternatives Considered

- Not inferring a singleton subset for `const` declarations, which would reduce compiler optimizations but simplify the type system.
- Allowing implicit precision for `mut` declarations, which would increase convenience but could lead to unintended precision loss and less predictable behavior.

## Decision 5: Inference

- `const x = 1.25` infers a singleton subset plus the literal's own precision (`sig n`).
- `mut` declarations require an explicit precision because a variable needs a representation for every future assignment. An unconstrained `mut a: real` is rejected.

### Rationale

- By inferring a singleton subset for `const` declarations, the compiler can perform aggressive optimizations and ensure that the value remains constant throughout its lifetime.
- Requiring explicit precision for `mut` declarations enforces clarity and prevents unintended loss of precision during assignments, ensuring that the variable always has a well-defined representation.
- This approach balances safety and flexibility, allowing developers to write efficient and correct numerical code while maintaining control over precision and representation.

### Consequences

- `const` declarations benefit from aggressive compiler optimizations due to the inferred singleton subset.
- `mut` declarations maintain explicit precision, preventing unintended precision loss and ensuring clarity in variable representation.
- Developers have a clear understanding of the precision and representation of their variables, leading to more predictable and correct numerical code.

### Alternatives Considered

- Not inferring a singleton subset for `const` declarations, which would reduce compiler optimizations but simplify the type system.
- Allowing implicit precision for `mut` declarations, which would increase convenience but could lead to unintended precision loss and less predictable behavior.
- Using a different approach for balancing safety and flexibility, such as introducing additional type annotations or constraints for numerical variables.

## Decision 6: `real big`

`real big` is an arbitrary-size decimal residing in the `real` universe, heap-lowered (`Real*`) with copy-on-write semantics. `real big` has $x_{\text{guarantee}} = 0$: every non-zero magnitude is representable with full precision, so no boundary exists below which precision may degrade.

### Rationale

The design of `real big` as an arbitrary-size decimal with exact intermediate representations and single rounding at storage ensures that computations are precise and predictable. By rejecting cross-base operations unless explicitly converted, the language enforces clarity and prevents hidden performance costs. This approach balances correctness with performance, providing a robust framework for numerical computations across different bases.

### Consequences

- `real big` provides exact intermediate representations, ensuring precise and predictable computations.
- Single rounding at storage simplifies reasoning about numerical behavior and avoids cumulative rounding errors.
- Cross-base operations are rejected unless explicitly converted, preventing hidden performance costs and maintaining clarity.
- The design enforces strict correctness by not supporting NaN, ±∞, and signed zero, eliminating special-case handling in numerical computations.
- Backends need to handle exact intermediates and copy-on-write semantics, which may introduce additional complexity.
- Developers have a clear and consistent framework for performing high-precision arithmetic, leading to more reliable numerical code.

### Alternatives Considered

- Using fixed-size arbitrary-precision decimals, which would simplify backend implementation but reduce flexibility and potentially introduce precision limitations.
- Allowing NaN, ±∞, and signed zero, which would increase compatibility with standard floating-point semantics but complicate reasoning and special-case handling.
- Implicit cross-base conversions, which would improve convenience but could introduce hidden performance costs and reduce clarity.
- Using mutable arbitrary-size decimals without copy-on-write semantics, which could simplify memory management but might lead to unintended side effects and less predictable behavior.
- Using a hybrid approach with both fixed-size and arbitrary-size decimals, which could offer a balance between performance and flexibility but would increase the complexity of the type system and backend implementation.
