# ADR-031: Backend Execution Mechanics and Lowering for Reals

[ADRs](../README.md)

## Status

💡 **Proposed**:

> An idea to be considered for adoption

## Context

[ADR-025](./adr-025.md) establishes that the `real` datatype separates universe/range (`subset`) from precision and representation (`type`), introducing `scale n` (absolute) and `sig n` (relative) across bases (`dec`, `bin`, `ter`).

Following the policy update, a critical distinction applies to storage bases:

- For `bin` and `ter`, the storage base is backend-defined as long as the precision guarantees ($x_{\text{guarantee}}$) are satisfied.
- For `dec`, the storage and representation model must strictly be base-10 to ensure exact decimal arithmetic semantics (such as `0.1 + 0.2 == 0.3`).

This ADR defines how backends must lower real arithmetic, handle assignments, enforce single rounding at storage, and manage conversions across different bases.

## Decision: Lowering and Execution Rules

### 1. Representation and Base Constraints in Backends

- **`dec` Backends:** Must utilize a base-10 representation format (e.g., IEEE decimal floating-point or packed decimal representations) to fulfill the requirement that decimal literals and operations retain decimal-exact behavior.
- **`bin` and `ter` Backends:** May lower `sig` types to any native hardware representation (such as binary64 or custom ternary layouts) provided that the layout delivers at least the requested $n$ significant digits down to $x_{\text{guarantee}}$.
- **`scale` Types:** Always lowered using an integer numerator corresponding to $b^{-n}$, making them fully platform-independent and result-agnostic regardless of the underlying backend architecture.

### 2. Single Rounding at Storage

Computations within expressions are performed with exact intermediate precision (or arbitrary precision where applicable, such as for `real big`).

- A value is checked against the declared precision requirements.
- It is **rounded exactly once** directly into the target storage grid upon assignment or storage.
- Intermediate multi-stage rounding is strictly prohibited, ensuring predictable behavior and preventing cumulative rounding drift within a platform.

### 3. Cross-Base Operations and Conversions

- Arithmetic operations mixing different precision bases (`dec`, `bin`, `ter`) are disallowed at compile time unless an explicit conversion via `round(x, to: ...)` is provided.
- Because `dec` enforces a strict base-10 representation while `bin`/`ter` may vary, cross-base conversions require explicit lowering steps handled by the backend's runtime or compiler-generated conversion routines.

## Rationale

- Mandating base-10 storage for `dec` preserves expected human-centric decimal arithmetic (including expressions like `0.1 + 0.2 == 0.3`), aligning with user expectations for decimal types.
- Allowing flexible storage bases for `bin` and `ter` preserves hardware efficiency and true implementation-agnosticism on non-binary architectures without forcing emulation.
- Enforcing single rounding at storage maintains mathematical rigor and keeps performance predictable across backends.

## Consequences

- Backend implementers for `dec` must support true decimal representations rather than relying on binary floating-point approximations.
- Binary and ternary backends retain full freedom to optimize layout representation as long as precision boundaries ($x_{\text{guarantee}}$) are strictly respected.
- Clear compile-time rejection of mixed-base expressions prevents hidden performance penalties and ambiguous rounding behaviors.
