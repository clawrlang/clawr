# ADR-016: Backend-Managed Boxing of Unboxed Primitives

> Status: ✅ Adopted

## Context

[ADR-000](./adr-000.md) defines integers and floats abstractly. [ADR-005](./adr-005.md) defines them as sets and ranges. [ADR-015](./adr-015.md) defines ARC for structures and explicitly boxed primitives.

However, an unboxed primitive such as `integer` may be arbitrarily large unless constrained to a range. The frontend cannot know whether a given value fits
in a machine word, nor when a backend will need to allocate or reuse a pointer for it. Therefore the frontend cannot inject ARC operations for implicit boxing.

## Decision

Unboxed primitive values are not ARC-managed in the CIR. The backend chooses their representation, and any implicit boxing is backend-private and must preserve value semantics. Explicitly boxed primitives are normal ARC-managed values per [ADR-015](./adr-015.md).

> [!note]
> The rules themselves are defined in the specification: [Automatic Reference Counting](../spec/cir/arc.md#boxing). For how the example backend chooses between `int64_t` and `Integer*`, see the [backend implementation notes](../guides/implementation/backend/README.md).

## Rationale

- The frontend cannot know backend representation thresholds.
- Keeping implicit boxing out of the CIR keeps the CIR platform-agnostic.
- Backends may use platform-specific arbitrary-precision integer libraries.
- Forcing ARC onto unboxed primitives would be premature and platform-dependent.

## Consequences

### Positive

- Backends are free to choose efficient primitive representations.
- The CIR remains simple and portable.
- Explicit boxing remains fully ARC-managed and predictable.

### Negative

- Backend bugs in primitive boxing are invisible to the frontend.
- Different backends may have different performance and memory behaviour for
  the same primitive operations.
- Debugging implicit boxing is backend-specific.
