# the Core Tenets of Clawr

These are not the core values of Clawr. First: Clawr is an artefact, it does not have its own values. Second: as Clawr’s founder, I do not know my own values well enough to just list them. What I can do is list a few things that I find valuable/meaningful, while also thinking as good representation for how Clawr has been designed:

1. Clawr works
2. Clawr is not a tech-bruh language
3. Solve the Problem; don’t Build a Solution

## The Problem with “Values”

Companies like to tout a set of “values” that define them and their philosophy. Employees are expected to learn these values by heart and act accordingly. But there is a problem. They are not values. They are dogma.

True values are not simple. They are generally not fixed. And they are in all-honesty almost never particularly well known.

All we do know is what we feel. We can know what we need with a burning passion and what we merely accept as necessary. We know what we would rather not have and what we cannot possibly abide. These are *signals* of our values, but not our *actual* values. While it is theoretically possible to go deep and figure some of this out, I can almost guarantee that no company has done any work to that effect before announcing its “core values.“

## 1. Clawr Works

That is a primary goal of this language. It should be easy to build something that works.

- The syntax and semantics should be intuitive.
- It should be easy to refactor code.
- And you should be able to focus on modelling rather than messing around with technical minutiae.

## 2. Clawr is not a Tech-Bruh Language

Security, safety and performance are good qualities, but they should emerge from good programming principles and intelligent tools; they should not obscure intent or distract from the model.

- If you want to tweak memory management, use a different language.
- If you want to decide what constants are serialized as machine code, use a different language.
- If you want to riddle your code with safety-tags, use a different language.

## 3. Solve the Problem; don’t Build a Solution

By focusing on the problem domain, the specific solution can be deferred. If the solution is the focus, it risks leaving awkward issues unresolved and purposely avoided.

What matters is that we **solve the problem**. What specific solution we use is not essential. There is always a better solution waiting around the next corner.

- The right technology today may be obsolete in five years.
- The right data structure and topology today easily becomes wrong when new requirements emerge.
- Every solution is an assumption about how to solve the problem.
- The problem will also change, but explicitly stated goals can be amended. Implicit goals make even the smallest change fraught.
