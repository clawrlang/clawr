# ADR-040: Extensions

> Status: 📝 Proposed

## Context

Swift extensions allow you to add new functionality to existing classes, structures, enumerations, or protocols without modifying the original source code. This can be particularly useful for organizing code, adding convenience methods, or conforming to protocols in a modular way.

Extensions can also be used to add computed properties, define nested types, and provide default implementations for protocol methods. However, they cannot add stored properties or change the existing behavior of the type they extend. By leveraging extensions effectively, you can keep your codebase clean, maintainable, and flexible.

### Example

```swift
extension String {
    var reversedString: String {
        return String(self.reversed())
    }
}

let greeting = "Hello"
print(greeting.reversedString) // Output: "olleH"
```

### Retroactive Modeling

Swift extensions enable retroactive modeling, allowing you to add functionality to types for which you do not have the original source code. This is particularly useful when working with third-party libraries or system types, as you can extend their capabilities without modifying their implementation. Retroactive modeling promotes code reuse and helps maintain a clean separation of concerns.

### Example of Retroactive Modeling

```swift
protocol Describable {
    var description: String { get }
}

extension Int: Describable {
    var description: String {
        return "The number is \(self)"
    }
}

let number: Describable = 42
print(number.description) // Output: "The number is 42"
```

## Decision

Clawr extensions add methods and trait/role conformances to nominal `data`, `object`, and `service` types declared in the current program. They do not add stored properties, initializers, or other state, and they do not override existing methods. The first implementation does not support extending primitive or separately imported types.

Each extension is represented by an `EXTENSION_DECL` CIR node that names its target, methods, and any conformance fulfillment tables. Extension methods and conformances are not merged into the target's `RC_TYPE_DECL`.

An extension may add a conformance only when the target type or the trait/role is declared in the current program. The current program includes all source files analyzed together, as defined by [ADR-038](./adr-038.md); separately imported packages are not yet supported.

Unlike Swift protocols, Clawr distinguishes traits (value properties) from roles (capabilities). Extensions follow that distinction: value types may conform to traits or roles, while services may conform to roles only. Clawr extensions add methods rather than computed properties.

A method-only extension adds methods without adding conformance:

```clawr
data Rectangle {
    width: integer
    height: integer
}

extension Rectangle {
    func area() => self->width * self->height
}

const rectangle: Rectangle = {width: 4, height: 3}
print(rectangle.area()) // Output: 12
```

A conformance extension supplies the required methods:

```clawr
trait HasArea {
    func area() -> integer
}

extension Rectangle: HasArea {
    func area() => self->width * self->height
}

func measure(_ shape: HasArea) -> integer {
    return shape.area()
}
```

### Eligibility

Only value-types may add conformance to traits. Both value-types and services can add conformance to roles. See [Traits and Roles](../spec/language/user-types/trait-role.md) for more details.

A `data` type remains property-only in its declaration, apart from the existing `serialize:` JSON hook. Other methods and trait/role conformances for `data` types `MUST` be added through extensions. This preserves the distinction between the data structure and its behavior without changing the existing serialization design.

### Ineligibility and Coherence

Extensions cannot add conformance when neither the target type nor the trait/role is declared in the current program.

There `MUST` never be duplicate methods with the same base name and labels for one type in the current program, whether the methods appear in the type declaration or in extensions. Extension methods are resolved from the receiver's static nominal type and its supertype chain, then called directly using their declaring type; they do not add vtable slots and cannot override type-declared or inherited methods.

There `MUST` never be more than one explicit conformance per canonical (type, trait-or-role) pair in the current program. Duplicate explicit conformances are compile-time errors, not resolved by declaration or load order. Compiler-synthesized conformances are outside this ADR.

Conflict resolution across separately imported packages is deferred with package imports.

### Value Types and Mutability

Extensions on `data` and `object` types use the same read-only and `mutating:` sections as object declarations. A mutating extension method may modify its receiver; before calling it on an isolated value, the frontend injects `ENSURE_UNIQUE` to preserve copy-on-write semantics. Shared (`ref`) receivers are not copied.

Extension methods on services do not use a `mutating:` section: services are shared capabilities, not isolated values.

## Consequences

### Positive

- Promotes modularity while keeping extension lookup and conformance ownership deterministic within the current program.
- Reduces the risk of conflicts and ambiguities arising from multiple extensions in different modules.
- Encourages explicitness and clarity in type modifications, making the codebase easier to understand and maintain.

### Negative

- Limits the flexibility of extensions, as developers cannot add trait or role conformance to types and traits defined entirely in other modules.
- Can make it harder to extend third-party types in a seamless way, potentially limiting interoperability with external libraries.

## Rationale

By restricting conformance extensions to cases where the target type or interface is declared in the current program, Clawr avoids conflicting retroactive conformances. One method identity and one explicit conformance per canonical type/interface pair are enforced across all source files compiled together. Separately imported packages and primitive-type extensions remain deferred.

Additionally, this approach aligns with the principle of explicitness in Clawr, ensuring that any modifications to type behavior are clearly defined within the module where the type or trait/role is introduced. This reduces the risk of unexpected side effects and makes the codebase easier to understand and reason about.

By following these guidelines, Clawr maintains a balance between flexibility and safety, allowing developers to extend types in a controlled manner while preserving the integrity and predictability of the overall system.
