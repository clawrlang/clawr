# ADR-026: Backend Execution Mechanics and Lowering for Reals

[ADRs](../README.md)

## Status

💡 **Proposed**:

> An idea to be considered for adoption

## Context

ADR-025 defines the type system, boundaries, and user-facing semantics of reals. This document outlines how backends represent exact intermediates, perform lowering, and handle cross-base computations.

## Decision

### 1. The Exact Intermediate Engine

To support single rounding at storage and explicit cross-base conversions without intermediate precision loss, backends must support exact intermediate representations.

- **Denominator Rule:** Addition and subtraction produce values over $\text{lcm}(d(x), d(y))$. Multiplication produces a value over $d(x) \cdot d(y)$.
- **Representation:** Realized as a whole number times $2^i \cdot 3^j \cdot 5^k$ (with integer mantissa $m$ and small integer exponents).
- **Lifecycle:** Intermediates are ephemeral—created for one rounding operation and never stored directly in variables. Backends should canonicalize $m$ to be coprime to $30$ when comparing raw intermediates.

### 2. Lowering Strategies by Grid Type

Backends map declared precisions to native hardware or software structures:

- **`scale n base b`:** Lowers to an integer $k$ meaning $k \cdot b^{n}$. It is fast and exact on every backend via basic integer math or shifts.
- **`sig n base b`:** Lowers to an integer mantissa $m$ ($\lvert m \rvert < b^n$) times $b^e$. When the grid base matches the hardware base (e.g., `sig 53 bin` on binary hardware), it maps to native types (`float`/`double`). When bases differ, it uses software rounding routines.
- **`Real*` Lowering:** Any `sig n` or wide-exponent literal whose range or digit count exceeds a fixed format lowers to heap-allocated arbitrary-precision storage (`Real*`).

### 3. Exactness Checks and CIR Nodes

- **Exactness validation** compiles down to a distinct CIR (Compiler Intermediate Representation) node.
- For **`bin → dec` no-op conversions**, the exactness check is marked as vacuously true by the compiler and elided entirely. For runtime-dependent values or narrowing conversions, an explicit check is injected that panics on failure.

## Rationale

- The bases and denominators are all known at compile-time and the LCM calculations can be done during static analysis.
- If the bases are limited to 2, 3, 10, the LCM can be drastically simplified: just take the maximum of the scales/sigs.
  - `ter` has no common factor with `bin` or `dec` and the LCM is simply the product of the denominators.
  - `bin` and `dec` have a common factor of 2, and the LCM is the `dec` scale times the difference `bin - dec` if the `bin` scale is larger, times 1 if not.

## Consequences

### Negative

- Increased complexity in the backend due to the need for exact intermediate representations and additional lowering logic.
- Potential performance overhead from managing exact intermediates and performing runtime exactness checks.

### Positive

- Ensures correctness of computations involving different bases by maintaining exact intermediates.
- Enables single rounding at storage and explicit cross-base conversions without intermediate precision loss.
- Provides a clear and consistent framework for backends to handle exact arithmetic, reducing the likelihood of subtle bugs.

## Alternatives Considered

- **Ignoring exact intermediates:** One alternative is to not maintain exact intermediates and rely solely on hardware rounding. This simplifies the backend but sacrifices correctness for cross-base computations.
- **Using only binary intermediates:** Another alternative is to convert all values to binary intermediates. This can simplify the implementation but may introduce rounding errors when converting to decimal or ternary bases.
- **Hybrid approach:** Maintain exact intermediates only for critical computations or when cross-base conversions are detected. This reduces overhead but adds complexity in determining when exact intermediates are necessary.
- Allow base 6 and base 30 scales for storing exact intermediates (even in variables).
  - Such bases are, however, unintuitive to the programmer and may complicate both the implementation and the understanding of the code
  - It might not be a problem for `const` variables, but `mut` variables. (Except when reporting their type in an IDE or at runtime.)
- Arbitrary denominators, a.k.a fractions or rational numbers. (This might be considered for a future ADR.)
