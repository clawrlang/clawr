# ADR-001: Per-Variable Isolation

[ADRs](./README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

Early compiler designs typically choose between value semantics (stack-based, copied)
or reference semantics (heap-based, shared pointers) at the _type_ level using
constructs like `class` vs `struct`. This conflates two orthogonal concerns:

- **Inheritance vs Composition** (`class` typically allow inheritance while `struct` does not)
- **Memory semantics** (`class` instances are shared reference, `struct` values are deep-copied and isolated)

This approach makes it impossible to create copy-semantics objects that support inheritance. Is that purposeful of just an awkward accident of the design? Even Swift (that uses copy-on-write to maintain isolation) disallows `struct` inheritance!

## Decision

Eschew the `class` and `struct` keywords for declaring types with fixed semantics. instead, introduce two **isolation levels** selected using four distinct variable declaration keywords:

- `const` / `mut`: `ISOLATED`, value semantics (stack-allocated or copy-on-write)
- `ref`/`mutref`: `SHARED`, reference semantics (heap-allocated)

The `const` and `ref` keywords signal immutability. In the first case that means the entire structure. In the second case it means only that the (shared) structure cannot be reassigned. The `mut` and `mutref` keywords signal mutability by the same definitions.

In nested structures, a `mut` field in a `const` variable will be “effectively const.” A `ref` field on the other hand ignores the semantics of its container. It disrupts both isolation and immutability (except for a `mutref` becoming effectively `ref` in a `const` structure). There is a mental model of [drawers and boxes](../lang-reference/semantics/index.md#a-better-mental-model-drawers-and-boxes) that might help.

Memory allocation and semantics are determined by the variable declaration,
not the type. A single type can be used in both isolation and sharing contexts.

## Rationale

1. **Orthogonal concerns**: Inheritance capability and semantics are separate decisions. Conflating them limits expressiveness.
2. **Flexibility**: Developers can choose the right semantics per use case without creating parallel type hierarchies.
3. **ARC integration**: Works naturally with automatic reference counting —`ref` variables are ARC-managed, `const`/`mut` can be stack-allocated.
4. **Clarity**: The variable declaration explicitly states the intended usage pattern,
   reducing hidden assumptions.

## Alternatives Considered

- **Type-level semantics (class/struct)**: Simpler to understand initially, but forces
  awkward workarounds when a type needs both isolation and sharing patterns.
- **Explicit ownership annotations (Rust-style)**: More explicit, but adds significant
  cognitive load and annotation burden for the user.
- **Implicit inference**: Automatic inference of semantics could work, but makes code
  behavior less obvious and harder to reason about.
- Only one keyword (`ref`) for reference semantic variables.

Regarding keyword naming, some prior art was considered and rejected:

- Kotlin’s `var`/`val` duo is considered hard to distinguish without IDE formatting assistance.
- Swift uses `let` for immutables, but JavaScript and TypeScript use the same keyword for mutables which can confuse programmers from that tradition.
- The `var` keyword could replace `mut`, but `mut` — being short for “mutable” feels more expressive (and it can be reflected in the `mutref` keyword).

The `const` keyword is used in many languages to mean immutable (though not often deep immutability). The term `ref` is often used in variable- and type names to indicate references. It is not commonly used as a keyword — which might indicate that per-variable isolation is an entirely new idea (or at least not tried in practice).

## Consequences

### Positive

- Single types are more reusable across different use cases
- Clear intent at the point of declaration
- Integrates naturally with ARC and isolation guarantees
- Allows object-oriented and functional patterns without fighting the type system
- Allows local reasoning (for `ISOLATED` data) with strong guarantees

### Negative

- Developers must understand the semantic difference (learning curve)
- Potential for misuse if semantics aren't clearly documented
- Completely disallows direct interactions between `ISOLATED` and `SHARED` variables.
- Requires explicit `copy(of:)` to bridge semantic paradigms.
