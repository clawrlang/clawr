# ADR-027: The `real` Datatype: Per-Operation Rounding

> Status: ✅ Adopted

## Context

This ADR is part of a series that defines the `real` datatype.

`integer` represents all of $\mathbb{Z}$. A range constraint lets the backend choose a native representation. `real` should likewise mean all of $\mathbb{R}$, but irrational numbers like $\pi$ and $\sqrt {2}$ cannot be stored exactly in finite memory, so a stored `real` needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

## Decision: Per-Operation Rounding

Every real-valued operation rounds its result to a precision derived from its operands. Arithmetic does not retain an exact result through the rest of an expression. Stored values also have a declared precision, and assignment rounds to that precision when it differs from the operation result's precision.

- **Every real has a finite precision.** The value's magnitude is not bounded by the precision; its representation may grow as needed, limited in practice by available memory.
- **Bounded `sig` ranges have a precision-guarantee boundary.** At and above $x_{\text{guarantee}}$ the full declared significant precision is required; below it, precision may decrease as specified in [ADR-025](./adr-025.md).
- **Implicit promotion is limited to unambiguous cases.** An integer converts to the real operand's precision. An exact decimal literal adopts the other real operand's precision, kind, and base, then rounds once to that precision. Binary operands with different widths or storage representations combine at the higher precision; the narrower binary value converts exactly. Other mixtures of precision kinds or bases are compile errors unless explicitly converted via `round(x, to: ...)`.
- **Non-exact operations round like every other operation.** Division and square root produce results at the precision derived from their operands.
- **NaN, ±∞ and signed zero do not exist** for reals. Division by zero is an error. Resource exhaustion may prevent an operation from completing.
- **Rounding:** One default mode (round to nearest, ties to even), plus an explicit `round(x, mode: ...)`.

When both real operands have the same precision kind and base, the result uses the higher operand precision: the larger `n` for either `scale n` or `sig n`. An integer operand converts to the real operand's precision, preserving the integer's unbounded magnitude.

Every operation's result is rounded before it is used by a later operation. Implementations must not reassociate operations, contract them into fused operations, or otherwise remove an observable rounding step.

**Results may differ across platforms.** Two backends may produce different values for the same source expression if their permitted storage grids differ. Equality compares stored values exactly within a platform; cross-platform result identity is not promised. `dec` requires decimal representation, and `scale` uses an integer numerator, but per-operation rounding still applies.

## Rationale

Rounding after each operation avoids requiring arbitrary-precision exact intermediates. Choosing the higher precision for compatible operands avoids an implicit dependency on the eventual assignment target. Implicit conversions are allowed only where they are unambiguous: integers follow the real operand, exact decimal literals can adopt its precision, and binary values can be widened without loss.

## Consequences

- Intermediate results are rounded, so results can differ from exact arithmetic and can accumulate rounding error.
- Rejecting cross-base operands without explicit conversion prevents hidden performance costs and maintains clarity in arithmetic expressions.
- By not supporting NaN, ±∞, and signed zero, the model enforces strict correctness and eliminates special-case handling in numerical computations.
- Every operation's rounding point is semantically observable and must be preserved by optimizations.
- Cross-platform result identity is not promised because storage grids for `bin` and `ter` may differ.

## Alternatives Considered

- Retaining exact intermediates and rounding only at storage, which would require arbitrary-precision arithmetic.
- Allowing implicit cross-base conversions, which would improve convenience but could introduce hidden performance costs and reduce clarity.
- Supporting NaN, ±∞, and signed zero, which would increase compatibility with standard floating-point semantics but complicate reasoning and special-case handling.
- Requiring storage base to match declared base for all types: forces emulation for non-decimal non-native hardware; rejected for `bin`/`ter` in favour of implementation-agnosticism.
