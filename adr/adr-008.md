# ADR-008 Encapsulation vs Data

## Status

> Status: ✅ Adopted

## Context

[ADR-002](./adr-002.md) decided to forgo the `class` and `struct` keywords. We need a set of keywords for defining types without declaring copy- vs reference semantics.

Robert C. “Uncle Bob” Martin defined a useful separation:

> [!quote]
>
> - An **Object** is a set of functions that operate upon implied data elements.
> - A **Data Structure** is a set of data elements operated upon by implied functions
>
> — [Robert C. “Uncle Bob” Martin](https://blog.cleancoder.com/uncle-bob/2019/06/16/ObjectsAndDataStructures.html)

## Decision

Introduce three distinct keywords for structured information:

- `data`: naked data structures without behavior (methods)
- `object`: encapsulated (hidden) data structures only accessed through methods
- `service`: `object`-like structures that operate on the environment

They follow these rules:

- `data` properties are openly accessible and cannot be hidden/private
- `data` properties `MUST` be `mut`/`mutref`, never `const`/`ref`
- `object` and `service` properties can be `const` and/or have default values
- `object` and `service` types have methods for interaction
- `service` variables and properties cannot be `ISOLATED`

### The `data` Structure: an Aggregate of Related Properties

Inspired by Uncle Bob’s definitions, a `data` structure is only a set of related elements of information (“properties”). It has no methods and must be passed around to functions that read or manipulate its contents.

The properties of a `data` structure are always public and directly accessible. They cannot be hidden or private. They cannot have default/initial values, and they must be mutable (`mut`/`mutref`) rather than constant (`const`/`ref`).

### The `object` Structure: Encapsulated `data` with a Functional Interface

An `object` is an encapsulated data-structure. It is defined by — and exposes only — its methods. The data elements are hidden and cannot be directly exposed. The type is intended to be designed outside-in and its state can be structurally redesigned (refactored) without affecting referencing code.

An `object` is still a data structure, though. It is not allowed to access the internet, open files or read sensors. Or to otherwise access the environment it operates in. It is limited to its internal state only.

A `const`/`mut` variable stores an `ISOLATED` instance of an `object` or `data` structure. This ensures that the variable has exclusive access to its contents and can safely manipulate its internal state without interference from other parts of the program. The structure can store `ref` properties that reference other `object` or `data` (or even `service`) instances. The state of referenced entities is not owned by the structure itself and not included in its isolation guarantees.

### Service Types for Interaction with the Environment

A `service` type looks very much like an `object` type to user code, but it can start background processes, open file handles and do anything at all to the environment, as long as it has an interface to operate.

Because every `service` variable’s “state” is the entire computing system/environment they cannot be `ISOLATED` from each other. Therefore `service` precludes `const`/`mut`, and variables `MUST` always be declared using the `ref` or `mutref` keywords.

An `object` can store references to `service` instances in its `ref` properties, allowing it to propagate events and decouple components from the environment.

## Open Questions

Review consequences if a `service` referenced by an `object` can start concurrent operations. Can the `object` call the `service` safely without violating isolation rules?

## Rationale

1. The `data`/`object` separation is conceptually more useful than the `class`/`struct` one.
2. Forced encapsulation means that invariants can be protected AND users are fully decoupled from the internal structure.
3. The `data` construct can be used for big-data computations, read-only systems and DTOs.
4. The `object` can be chosen for rich DDD models, to protect invariants, and as secure domain primitives.
5. Conflating data/state with external operation can add undue cognitive pressure.

## Alternatives Considered

- None. This is a founding idea for the language.

## Consequences

### Positive

- A good companion to [ADR-002](./adr-002.md) (Per-Variable Isolation)
- Clarifies intent: simple data vs encapsulated state with behaviour vs system-wide state
- Clarifies intent: What is a DTO and what is the domain model

### Negative

- Might be confusing to programmers coming from the `class`/`struct` tradition.
- Might be inflexible and requires new refactoring patterns such as “Encapsulate `data`” and its (as yet unnamed) reverse.
