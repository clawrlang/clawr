# ADR-028: The `real` Datatype: Assignment, Equality, and Literals

> Status: 💡 Proposed

## Context

This ADR is part of a series that defines the `real` datatype.

`integer` represents all of $\mathbb{Z}$. A range constraint lets the backend choose a native representation. `real` likewise represents all of $\mathbb{R}$, with magnitudes limited in practice by available memory. Since irrational numbers like $\pi$ and $\sqrt {2}$ cannot be stored exactly in finite memory, every stored `real` needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

## Decision

- **Range is checked as type compatibility** (compile-time where provable, otherwise dynamic panic).
- **Precision at assignment** is the destination's declared precision. If it differs from the expression result's precision, assignment rounds to the destination precision. The magnitude is not restricted by the precision, subject to available memory.
- **Precision conversions across bases are explicit**, with `round(x, to: ...)`. Across precision bases (`dec`, `bin`, `ter`), `round` is required at compile time. Within one base, operations still round according to [ADR-027](./adr-027.md).
- **Equality** compares stored values exactly within a platform, making it transitive and independent of representation _within that platform_. Cross-platform equality may differ if stored values differ; result identity is not promised until operation-precision derivation is fully specified. “Equality” tests should be on the form `abs(a - b) < tolerance`.
- **Literals** denote exact rational values and have a precision inferred from their spelling or explicit context. A literal is rounded to that precision; constant folding must preserve the rounding after each operation required by [ADR-027](./adr-027.md).

## Rationale

- Assignment converts an operation result to the destination's declared precision when those precisions differ.
- Equality checks are exact within a platform, providing predictable and consistent behavior regardless of the underlying representation.
- Literals and constant expressions can be evaluated at compile time while preserving per-operation rounding.

## Consequences

- Inferring a singleton subset for `const` declarations allows the compiler to optimize aggressively while ensuring constant values remain unchanged.
- Requiring explicit precision for `mut` declarations prevents unintended precision loss and enforces clarity in variable representation.
- This approach provides a balance between safety and flexibility, enabling efficient and correct numerical code while maintaining control over precision and representation.
- Cross-platform equality is not guaranteed until operation-precision derivation is fully specified; `scale` and `dec` do not override the per-operation rounding rules.

## Alternatives Considered

- Not inferring a singleton subset for `const` declarations, which would reduce compiler optimizations but simplify the type system.
- Allowing implicit precision for `mut` declarations, which would increase convenience but could lead to unintended precision loss and less predictable behavior.
