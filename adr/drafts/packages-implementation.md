Clawr should not require a particular implementation for how packages are built, named and linked. It should be possible to choose an implementation depending on what works best on the target platform.

That said, there should probably be some consistent structure, but I do not yet know what it should look like. It should preferably allow multiple installed versions of each library and resolving the “diamond problem” where the same library is referenced by multiple libraries that require different versions, all loaded in the same process.

`@rpath` is a **placeholder token** that gets resolved at runtime (or link time) — it's not a variable you assign on the command line directly, but rather a prefix that tells dyld "look up the actual path using the `LC_RPATH` entries baked into the loading binary."

## How it works

When you link an executable or dylib, you can embed one or more **runpath search paths** via:

```plain
-install_name @rpath/libClawr.A.dylib
-rpath @loader_path/../Frameworks
-rpath /opt/myapp/lib
```

These `-rpath` entries become `LC_RPATH` load commands in the Mach-O. At load time, dyld substitutes each `@rpath` in an install name with each `LC_RPATH` entry, in order, until it finds a file that exists.

So if your client binary has `LC_RPATH = @loader_path/../Frameworks`, then:

```plain
@rpath/libClawr.A.dylib  →  @loader_path/../Frameworks/libClawr.A.dylib
```

(`@loader_path` itself is another token meaning "directory of the binary doing the loading".)

## Why you needed it

Before, your dylib's install name was probably an absolute path (e.g. `/Users/you/build/dist/libClawr.A.dylib`) or a bare filename. Clients linked against it recorded that literal string in their `LC_LOAD_DYLIB`, and at runtime dyld would look for exactly that path.

By switching the install name to `@rpath/libClawr.A.dylib` and adding an `-rpath` to the client, you made the location **relocatable** — the client finds the dylib relative to itself (or wherever you point the rpath), rather than an absolute build-machine path.

## The three @-tokens

| Token              | Resolves to                                                        |
| ------------------ | ------------------------------------------------------------------ |
| `@rpath`           | Each `LC_RPATH` entry in the loading binary, tried in order        |
| `@loader_path`     | Directory containing the binary that has the `LC_LOAD_DYLIB` entry |
| `@executable_path` | Directory containing the main executable                           |

## Inspecting them

```shell
# rpaths embedded in a binary
otool -l client | grep -A2 LC_RPATH

# what a binary will actually load (simulates dyld resolution)
dyld_info -dependents client
# or
otool -l client | grep -A2 LC_LOAD_DYLIB
```

## Is it "assigned on the command line"?

Sort of — but the assignment is **per-binary at link time**, not a shell variable. Each binary carries its own list of rpaths, and the resolution happens independently for each `@rpath/...` reference. Two different binaries can have different rpaths and thus resolve the same `@rpath/libClawr.A.dylib` to different files. That's the whole point: it decouples the dylib's install name from its physical location.

## What actually happened

When you link a dylib with `clang -dynamiclib -o dist/libClawr.A.dylib ...`, and you **don't** pass `-install_name`, the linker defaults the install name to **the `-o` argument verbatim** — i.e. the literal string `dist/libClawr.A.dylib` (a relative path, not even resolved to an absolute one).

That install name gets baked into the dylib's `LC_ID_DYLIB` load command. You can see it:

```shell
otool -D dist/libClawr.A.dylib
# dist/libClawr.A.dylib   ← no leading slash, relative!
```

## Why that broke linking

When a client links against your dylib, the linker copies the dylib's **install name** (not the path you passed on the command line) into the client's `LC_LOAD_DYLIB`. So even though you did:

```plain
clang client.o /Users/johan/Arbete/Clawr/Clawr/dist/libClawr.A.dylib -o client
```

the client recorded:

```plain
LC_LOAD_DYLIB  dist/libClawr.A.dylib
```

At runtime (or at link time when resolving the dylib's own dependencies), dyld tries to open `dist/libClawr.A.dylib` **relative to the process's current working directory** — which is essentially never where you want it. Hence "not found."

The confusing part is that the _linker_ was perfectly happy — it read the file you pointed at, got its install name, and wrote that into the client. The failure shows up later.

## The fix

Override the install name at build time:

```shell
clang -dynamiclib ... -o dist/libClawr.A.dylib \
    -install_name @rpath/libClawr.A.dylib
```

Then when you link clients, add an rpath so `@rpath` resolves to a real directory:

```shell
clang client.o -L dist -lClawr.A -o client \
    -rpath @loader_path/../dist      # or wherever, e.g. @executable_path
```

You can also patch an already-built dylib in place:

```shell
install_name_tool -id @rpath/libClawr.A.dylib dist/libClawr.A.dylib
```

(and if a client already has the bad `dist/libClawr.A.dylib` reference baked in, `install_name_tool -change dist/libClawr.A.dylib @rpath/libClawr.A.dylib client` fixes it too — no relink needed.)

## The mental model

- `-o` sets the **output filename** on disk. It's a fallback for the install name only because Apple's linker is lazy about defaults.
- `-install_name` sets the **identity string** that goes into `LC_ID_DYLIB` and that clients copy into their `LC_LOAD_DYLIB`. This is what dyld actually uses.
- These two are independent, and you almost always want them to differ: on-disk name can be anything, identity should be `@rpath/…` (or an absolute path like `/usr/local/lib/…` if it's a system-wide install).

So to your original question — `@rpath` isn't a shell variable, but it _is_ a token that fills the role "the install name" was always playing; it just defers the actual path to rpath entries in the loading binary instead of hard-coding it.

>
> Could it work if I had set the install-name to 'libClawr.A.dylib'? I.e. without dist/ (or rpath)?

Short answer: **it would "work" only in the sense that the string is valid — but it would still fail to load at runtime unless the file happens to be in a directory dyld searches for bare filenames.**

## What dyld does with a bare filename

If the install name is `libClawr.A.dylib` (no slash, no `@`-prefix), dyld treats it as a **leaf name** and searches the standard fallback paths, in order:

1. `$DYLD_LIBRARY_PATH` (if set, and not in a SIP-restricted context)
2. `$LD_LIBRARY_PATH` (legacy alias)
3. The **current working directory** — _only_ if `$DYLD_FALLBACK_LIBRARY_PATH` is unset and the process isn't restricted... actually no, CWD is _not_ searched by default on macOS for security reasons in modern versions.
4. The default fallback paths: `~/lib`, `/usr/local/lib`, `/usr/lib`

So a bare `libClawr.A.dylib` will be found **only if** you install it into `~/lib`, `/usr/local/lib`, or `/usr/lib` — or if the user sets `DYLD_LIBRARY_PATH` / `DYLD_FALLBACK_LIBRARY_PATH` to include its directory.

It is _not_ found relative to the client binary, not relative to CWD (on modern macOS), and not relative to where you built it.

## So compared to what you had

- `dist/libClawr.A.dylib` (your original): relative path → dyld resolves it **relative to CWD** → almost always fails.
- `libClawr.A.dylib` (bare): dyld falls back to the system search paths → fails unless you `cp` it to `/usr/local/lib` or similar.
- `@rpath/libClawr.A.dylib`: dyld looks in the rpaths baked into the _loading_ binary → works if you set `-rpath` correctly. This is the relocatable, self-contained option.

## When a bare name is actually fine

The bare-name pattern is exactly what Apple uses for system libraries:

```plain
/usr/lib/libSystem.B.dylib
```

but note that's an **absolute** path, not bare. True bare names show up for things like `/usr/lib/libc++.1.dylib` referenced as... no, also absolute. Bare names are rare in practice precisely because they're fragile.

The one place a bare install name is idiomatic: **plugins/bundles** that are loaded by a host which already knows the full path (via `dlopen("/full/path/to/plugin.dylib")`). In that case the install name is irrelevant because the host never resolves it — it just opens the file directly. That's why you sometimes see Xcode-produced bundles with bare install names and it "works fine."

## Bottom line

If your goal is "client finds the dylib next to itself / in a known relative location," a bare `libClawr.A.dylib` won't do it — you'd need `@rpath/…` + `-rpath`, or `@loader_path/…`, or an absolute path. The bare name only works if you're willing to install the dylib into one of dyld's default search directories (or rely on `DYLD_LIBRARY_PATH`, which is fragile and increasingly restricted by SIP).

> I'm wondering because I'm used to DLL files that are linked through some kind of repository (like the .Net CLR). The client does not usually know where the library is located in the file system.

Right — that's a good instinct, and it highlights a real difference between the **.NET / CLR model** and the **native Mach-O / ELF model**.

## The .NET model: identity ≠ location

In .NET, an assembly has an **identity**: name + version + culture + public key token. The CLR resolves that identity through _its own_ search rules (app base dir, `deps.json`, NuGet cache, GAC, `AssemblyLoadContext`, `AppDomain.AssemblyResolve`, etc.). The path on disk is an _implementation detail_ of the resolver. A referencing assembly never records a filesystem path — just `"Clawr.A, Version=0.0.1, Culture=neutral, PublicKeyToken=..."`.

Same idea in Java (classpath + `ClassLoader`), Python (module name + `sys.path`), Node (`require` + `node_modules` resolution), etc. These are all **late-bound, name-based** systems.

## The native model: location is part of identity

Mach-O (and ELF, and PE for that matter) is **path-based**, not name-based. The linker writes a literal string into `LC_LOAD_DYLIB` — the install name — and dyld tries to `open()` that string (after `@`-token substitution). There's no registry, no manifest, no resolver hook by default. The closest things are:

- `@rpath` — a _deferred_ path, resolved via `LC_RPATH` entries in the loading binary.
- `DYLD_*_PATH` env vars — a global search path, insecure and SIP-restricted.
- Default dirs (`/usr/lib`, `/usr/local/lib`, `~/lib`).
- `dlopen()` at runtime with a path you computed yourself.

Notice all of these are still _path_-shaped. There's no "give me the library named libClawr.A, any version, whoever provides it" call.

## Why the difference

It's mostly historical + process-model:

- **.NET/Java/etc.** run inside a VM that owns the loading process. The VM can impose whatever resolution policy it wants, and it can afford to be name-based because it controls _everything_ — metadata, versioning, strong names, load contexts.
- **Native dynamic linking** is done by the OS loader (dyld / ld.so), which is deliberately dumb and fast. It doesn't parse symbol metadata to make decisions; it just resolves strings to paths and `mmap`s files. Adding a name-based registry would mean a global namespace, versioning, and policy — all things Unix/macOS deliberately push to the packaging layer (Homebrew, apt, `pkg-config`, rpaths, etc.).

## The closest native analogues

If you want "client doesn't hard-code a path," the native idioms are:

1. **`@rpath` + `-rpath`** — this is _the_ answer. The client records `@rpath/libClawr.A.dylib` (a name, effectively), and each _loading context_ provides its own search dirs via `LC_RPATH`. Change where things live? Just change the `-rpath`. Different apps can map the same `@rpath` name to different files. That's the deferred-resolution mechanism.
2. **Framework bundles** (`Foo.framework/Foo`) — a name-based-ish convention where the _layout_ is standardized, but resolution is still via paths/rpaths.
3. **`dlopen("libClawr.A.dylib", RTLD_LAZY)`** — dynamic loading by name, using the default search paths. This is the closest to `Assembly.Load("Clawr.A")`, but it's fragile on macOS because CWD isn't searched and `DYLD_LIBRARY_PATH` is restricted under SIP.
4. **Package managers** — Homebrew/apt/etc. install into a well-known prefix (`/opt/homebrew/lib`, `/usr/lib`) so a bare or absolute name resolves. The "repository" is the package manager, not the loader.

## So to your underlying question

> The client does not usually know where the library is located in the file system.

In the native world, the client _does_ effectively know — it knows an install name, which is a path or a `@`-token that expands to a path. The design philosophy is: **the build system / package manager is responsible for making that path correct**, not the runtime loader. `@rpath` is the escape hatch that lets you defer _which_ path until link time of the _consumer_, which is about as close to "late binding by name" as Mach-O gets.

So when you set `-install_name @rpath/libClawr.A.dylib`, you're saying: "my identity is `libClawr.A.dylib`, and whoever loads me decides where that lives via their rpaths." That's the native analogue of the CLR's name-based resolution — just without a central resolver, and with the search list supplied per-binary instead of globally.

That philosophy is exactly the right lens for this decision, and it points at a fairly specific answer: **your compiler should emit `@rpath/<name>` as the install name by default, and emit an `LC_RPATH` pointing at the build output directory (or `@loader_path/…`) into every executable and dylib it produces.** Then the programmer never sees linking at all.

Let me walk through why, and where the sharp edges are.

## What "the programmer doesn't think about linking" has to mean concretely

In .NET/Java, the _toolchain_ picked a resolution policy and made it uniform:

- Every assembly is named. The name is its identity.
- The build produces a manifest (`deps.json`, the jar's `Class-Path`, etc.) that records _what_ is needed, not _where_.
- The runtime has a resolver that combines the manifest with a small set of well-known locations.

You can do the same thing in Mach-O, you just have to be the one that picks the policy. The two knobs are: **install name** and **rpath**. Your compiler controls both, because it's the one invoking `ld`.

## Suggested policy

For every dylib your compiler produces:

```plain
-install_name @rpath/<dylib-name>
```

For every executable _and_ every dylib your compiler produces (yes, dylibs too — they can have their own rpaths):

```plain
-rpath @loader_path/<relative-path-to-lib-dir>
```

where `<relative-path-to-lib-dir>` is computed from the _output location of the artifact being linked_ to wherever your compiler decided to put its libraries. If you follow a "everything for one build lands in the same `dist/` or `build/` tree" convention, this is a fixed relative path like `@loader_path/../lib`.

The result:

- Programmer writes code, uses modules, never sees a linker.
- Your compiler knows the convention (libs go in `<build>/lib`, binaries in `<build>/bin`), so it can emit the right `-install_name` and `-rpath` on every invocation.
- Moving the whole build tree anywhere still works, because everything is relative to `@loader_path`.
- Vendoring/copying one dylib next to a binary also works, because the rpath is relative to the loader.

This is exactly the "relocatable install" pattern that CMake, Meson, and Xcode's `@rpath` mode use. You're just hiding it from the user, which is the point.

## The sharp edges you'll hit

A few things worth deciding up front, because they leak if you don't:

**1. Same-name collisions.** `@rpath/libfoo.dylib` is resolved by the _first_ matching rpath entry. If two dependencies both provide `libfoo.dylib`, you get whichever comes first. The CLR dodges this with strong names / public key tokens. You don't have that. Practical mitigations: namespace dylib filenames by module (e.g. `libClawr.A.dylib`, `libClawr.B.dylib` — which you're already doing with the `Clawr.A` naming), and/or have your compiler control the entire rpath list so ordering is deterministic.

**2. Transitive dependencies.** If `libA.dylib` depends on `libB.dylib`, then `libA` needs its own `LC_RPATH` (or `@loader_path`) to find `libB` when _libA_ is loaded. `@rpath` is resolved per-loading-binary, so each dylib in your build tree needs to carry the same `-rpath @loader_path/../lib` (or whatever) that your executables do. Your compiler should apply the rpath to _every_ artifact it links, not just executables.

**3. Relative output paths.** If you invoke `ld` with `-o dist/libClawr.A.dylib` and forget `-install_name`, you get the bug you already hit. So: never let the compiler emit a link command without an explicit `-install_name`. This is a one-line invariant in your codegen: `-install_name @rpath/$(basename $output)`.

**4. `@loader_path` vs `@executable_path`.** `@executable_path` is the directory of the _main executable_, which is wrong for dylibs loaded by other dylibs. `@loader_path` is the directory of the binary that has the `LC_LOAD_DYLIB` — correct in all cases. Use `@loader_path`.

**5. Distribution beyond the build tree.** If the user wants to ship the binary to someone else, the relative layout has to be preserved. That's fine and is how macOS app bundles work, but it's a thing your docs should say. If they want a "single self-contained binary," you eventually need to either statically link (if your compiler supports it) or produce a bundle/`.app`/installer. That's the same tradeoff every native toolchain has; you can't make it disappear, only make it a _tooling_ decision rather than a _programmer_ decision.

**6. Hardened runtime / code signing.** On macOS, if the binary is signed (even ad-hoc), `DYLD_*` env vars are ignored, which is another reason to bake the rpath in at link time rather than relying on env vars. `@rpath` is unaffected by this.

## Where your language's philosophy can go further than C

C makes the programmer see link flags because C's compilation model is "one translation unit → one object file → link them all manually." Your compiler presumably sees a whole module graph. That means you can:

- Compute the full transitive dependency list at compile time.
- Decide the output layout (e.g. `<build>/lib/`, `<build>/bin/`).
- Emit exactly one link command per artifact, with the correct `-install_name`, `-rpath`, and `-l` flags, all derived from the module graph.
- Never expose `-rpath`, `-install_name`, `-L`, or `LD_LIBRARY_PATH` to the user.

The programmer's mental model becomes: "I imported module `Clawr.A`; it works." The technical complexity hasn't vanished — it's been moved into your compiler's link driver, which is exactly where it belongs if your philosophy is that the language should own it.

## Concrete recommendation

If I were implementing this in your compiler, the invariant I'd write on the wall is:

> Every Mach-O artifact my compiler produces is linked with an explicit `-install_name @rpath/<basename>` and with `-rpath @loader_path/<rel-path-to-lib-dir>`, where `<rel-path-to-lib-dir>` is computed from the artifact's output path to the build's lib directory.

That single rule is what makes "the programmer never thinks about linking" actually true on macOS, instead of aspirational. It's also why you had to add `@rpath` — you were manually doing what your compiler should have been doing for you all along. Now you can teach it to do it.

Good question, and the `A` in your name is probably not what you think it is. Let me unpack both the naming convention and the versioning question separately, because they're actually orthogonal.

## Where the `.A` convention comes from

In C toolchain land there's a long-standing convention of **libtool versioning**, which produces something like:

```plain
libfoo.so.1.2.3          # real file, SONAME = libfoo.so.1
libfoo.so.1    -> ...    # symlink for the major version
libfoo.so      -> ...    # symlink for the linker (dev package)
```

On macOS the equivalent is:

```plain
libfoo.1.2.3.dylib
libfoo.1.dylib   -> ...
libfoo.dylib     -> ...
```

where `1` is the **major / ABI version** and `1.2.3` is the current version. The number is not a letter. `libClawr.A.dylib` looks like someone adapted this pattern but substituted a **letter** for a number — probably because:

- Their language uses letters for "generations" of modules, or
- They're mimicking a specific ecosystem's convention (some JVM langs, some older module systems use letters), or
- It's just an idiosyncratic choice.

There's no Mach-O rule that says the name must be `libX.A.dylib`. The only _rules_ Mach-O cares about are: install name must be a string, and it must match what clients record in `LC_LOAD_DYLIB`. Everything else is convention.

## Two distinct things you might be conflating

You're asking about two different problems:

1. **Naming the file** — what string goes after `libClawr.` and before `.dylib`.
2. **Recording the version** — where the version number lives so the loader and tooling can act on it.

Mach-O supports both, and they serve different purposes.

### Versioning, the Mach-O way

Every dylib carries two version fields in its `LC_ID_DYLIB`:

```plain
compatibility version X.Y.Z    # the ABI it's compatible with
current version X.Y.Z          # the actual version of this build
```

You set them at link time:

```plain
-current_version 1.0.0
-compatibility_version 1.0.0
```

And clients record the _compatibility version they were linked against_ in their `LC_LOAD_DYLIB`. At runtime dyld refuses to load a dylib whose compatibility version is _lower_ than what the client requires. That's the actual versioning mechanism — the filename is just a human-facing convention layered on top.

You can inspect:

```shell
otool -L dist/libClawr.A.dylib
# shows "(compatibility version X.Y.Z, current version X.Y.Z)"
```

### Naming, the convention way

The convention `libfoo.<major>.dylib` exists so that:

- Multiple major versions can coexist on disk (`libfoo.1.dylib` and `libfoo.2.dylib`).
- The client records `libfoo.1.dylib` — so upgrading to `libfoo.2.dylib` doesn't silently break ABI.
- Package managers install all three symlinks so that `-lfoo` at link time resolves to the current major.

But **this is optional**. Plenty of dylibs ship with no version in the name at all (frameworks often don't; Homebrew's dylibs usually do; Apple's system dylibs do). What matters is that the install name is stable and that the compatibility version machinery is used correctly.

## What this means for your compiler

You have three reasonable policies, and your philosophy ("programmer focuses on domain, not technical") should drive the choice.

### Policy 1: semver in the filename

```plain
libClawr.1.0.0.dylib
install_name = @rpath/libClawr.1.dylib    # or full semver
```

This gives you multi-version coexistence and ABI safety. Cost: your compiler has to manage symlinks or duplicate files, decide when the major bumps, and ensure the whole build tree uses consistent names. That's real complexity — but _you_ own it, not the programmer, which is fine.

### Policy 2: semver only in the version fields, stable filename

```plain
libClawr.dylib
install_name = @rpath/libClawr.dylib
-current_version 1.0.0
-compatibility_version 1.0.0
```

The filename never changes; the version lives in the Mach-O headers. You can bump the compatibility version when you make an ABI break, and dyld will enforce it. Simpler layout, no symlinks, no filename churn. Cost: you can't have `libClawr` v1 and v2 installed side by side in the same directory — but if your language is a single coherent toolchain (not a system package consumed by unrelated third parties), you probably never need that.

### Policy 3: hash or content-addressed names

```plain
libClawr-<content-hash>.dylib
```

This is what some newer build systems do (Buck2, Bazel-ish, some Rust workflows). The name is opaque, changes whenever the content changes, and the compiler manages it entirely. Programmers never see it. Downside: makes manual inspection painful and doesn't play well with system package managers.

## My actual recommendation for your case

Given your philosophy and that this is **your language's compiler**, not a C library shipped to the system:

- **Use Policy 2.** Stable filename `libClawr.dylib` (or `libClawr.<module>.dylib` if you have per-module dylibs). Put the version in `-current_version` / `-compatibility_version`. Let the compiler manage those from the module's declared version.
- **Skip semver in the filename.** It exists to solve the "unrelated consumers need to mix major versions of a C library" problem — a problem you don't have, because your compiler produces the whole dependency graph together.
- **If you later want coexistence** (e.g. a system-installed runtime that multiple compiled apps share), _then_ introduce `libClawr.<major>.dylib` with symlinks, and make it a runtime-versioning policy rather than a per-build naming policy.

## On the `.A` specifically

If `.A` is currently doing work in your system — e.g. it distinguishes module generations, or your loader keys off it — keep it, but understand it's _your_ convention, not an industry one. The industry convention is numeric: `.1`, `.1.2.3`. If `.A` is just leftover from an example you copied, drop it in favor of either nothing (`libClawr.dylib`) or the Mach-O version fields.

The key invariant that _does_ matter, regardless of which policy you pick:

> Whatever string you put in `-install_name` at link time is the string every client will record and every loader will try to resolve. Changing it later means relinking everything.

Since your compiler relinks everything anyway on every build, you have more freedom than a C project does — you can change the convention later without breaking the world. So pick the simplest thing that works now (Policy 2), and defer semver-in-filename until you actually need side-by-side versions.

Maybe libA needs an earlier version (say 1.x) but the program needs the latest (2.3). Then both need to be installed in the file system as different binaries and linked separately. And usages in the program must resolve to the new binary, while usages in libA must link to the old one.

This is the classic **"diamond dependency"** problem, and it's exactly the case where name-in-filename versioning earns its keep. Let me walk through how it actually works, because the mechanics are subtle and they'll directly shape what your compiler needs to emit.

## The problem, concretely

```plain
app  → libB 2.3
app  → libA
       libA → libB 1.x
```

You need two `libB` binaries on disk, and — critically — the _references_ to `libB` inside `app` must resolve to 2.3 while the references inside `libA` resolve to 1.x. Same symbol name `libB`, two different files, two different loaders' worth of context.

## Why this is genuinely impossible in the naive scheme

If both `libA` and `app` record `@rpath/libB.dylib` in their `LC_LOAD_DYLIB`, then at load time dyld walks the rpaths of _whichever binary is loading_ and opens the first `libB.dylib` it finds. If `app` and `libA` have the same rpath, they get the same file. You cannot have them resolve to different files by rpath alone — rpath is a _directory list_, not a version selector.

So for diamond dependencies to work, **the version must be part of the install name**, not just part of the directory. That's the whole reason `libfoo.1.dylib` vs `libfoo.2.dylib` exists.

## How it's done in the C world

```plain
/usr/local/lib/libB.1.4.dylib     # install_name = /usr/local/lib/libB.1.dylib
/usr/local/lib/libB.1.dylib   ->  libB.1.4.dylib
/usr/local/lib/libB.2.3.dylib     # install_name = /usr/local/lib/libB.2.dylib
/usr/local/lib/libB.2.dylib   ->  libB.2.3.dylib
/usr/local/lib/libB.dylib     ->  libB.2.dylib   # dev symlink for -lB
```

- `libA` was linked against `libB.1.dylib` → its `LC_LOAD_DYLIB` says `libB.1.dylib` → dyld opens the 1.x line.
- `app` was linked against `libB.2.dylib` → its `LC_LOAD_DYLIB` says `libB.2.dylib` → dyld opens the 2.x line.
- Both files coexist; dyld loads both into the process if needed.

The **major version is the ABI version**. `1.4` and `1.5` are assumed ABI-compatible and the client just asks for `libB.1.dylib`; the specific patch is whatever the symlink points to. `2.3` is a different ABI and gets its own file and its own name.

On macOS with `@rpath`:

```plain
install_name = @rpath/libB.1.dylib
install_name = @rpath/libB.2.dylib
```

and each loader's `LC_RPATH` points at a directory that contains both. The `@rpath` prefix is orthogonal — it says _where_ to look; the `.1`/`.2` in the leaf name says _which one_.

## The hard truth: this still doesn't fully solve the diamond

Even with the above, you can hit a wall: **if `libA` and `app` both need `libB` but with incompatible ABIs, and `libB` has global state or symbol collisions, you cannot have both loaded into one process cleanly.** dyld will happily load `libB.1.dylib` and `libB.2.dylib` as two distinct images, but:

- C symbol resolution at runtime is per-image, so that part works.
- But if either library registers something globally (a signal handler, a plugin registry, a `atexit` handler, a global allocator hook), the two copies fight.
- Objective-C class names, C++ RTTI/`type_info`, and `static` initializers can collide across the two copies.

This is the fundamental reason the C/C++ world invented the "soname major version" convention _and_ the reason it's still fragile. Rust's `-C prefer-dynamic` has the same problem; that's a big reason Rust defaults to static linking of dependencies and mangles symbol names into the ABI.

## What this means for your language

You have a design choice here, and your philosophy ("programmer focuses on domain, not technical") argues strongly for one of two paths:

### Path A: Follow C, expose version in the name

```plain
libClawr.B.1.dylib
libClawr.B.2.dylib
install_name = @rpath/libClawr.B.1.dylib
```

Your compiler:

- Knows each module's ABI version (from the module's declared version, semver-major or whatever your versioning scheme is).
- Emits `-install_name @rpath/lib<Module>.<abi-major>.dylib` for every dylib.
- Records the required version in the client's `LC_LOAD_DYLIB` (which happens automatically — the linker copies the install name).
- Puts all of them in one lib directory and gives every binary the same `-rpath @loader_path/../lib`.

Result: diamond dependencies "just work" for the simple case, and you inherit the same fragile edge cases as C when global state is involved.

### Path B: Side-by-side install _per build_, no system-wide versions

If your language compiles whole programs (not libraries that third parties link), you can sidestep the diamond entirely by treating every build as a closed world:

- Each build produces one lib directory containing exactly one version of each module.
- Because `app` and `libA` are built **together**, your compiler can resolve the conflict _at compile time_: pick a single version of `libB` that satisfies both, or error out if impossible.
- No `libB.1` / `libB.2` needed; no coexistence problem.

This is what Go, Rust (default), and most modern build systems do. It's strictly more powerful for the "one program, one build" case because the compiler can _see_ the whole graph and can do real version resolution instead of punting to the loader.

### Path C: Both, with the compiler deciding

The clean design, and the one I'd recommend for you:

- **Within a build**, everything is resolved statically. One version of each module. If two dependents need incompatible versions, you either upgrade the old one or the compile fails with a clear message. No diamond.
- **Across builds**, if you ever ship a "shared runtime" or a precompiled module that other builds consume, _then_ you introduce `.major` in the filename and the `compatibility_version` field, so unrelated builds can coexist. But this is a packaging concern, not a per-build concern.
- Your compiler tracks the ABI version of each module and stamps it into `-compatibility_version`, so dyld enforces it _if_ two builds ever meet at runtime.

## The specific answer to your scenario

> What if a program uses two libraries libA and libB, and libA has a dependency on libB 1.x but the program needs 2.3? Then both need to be installed as different binaries and linked separately.

Yes — **that is exactly how you'd have to do it in the Mach-O model**, and it requires:

1. Version in the install name (`libB.1.dylib` vs `libB.2.dylib`).
2. Both files on disk.
3. `app` and `libA` each built against the correct install name, so their `LC_LOAD_DYLIB` entries differ.
4. Both versions coexisting in the process without fighting over global state (the fragile part).

Your compiler's job, if you go this route, is to hide all of (1)–(3) and to _warn or error_ on (4) whenever it can detect it. But note that this is a lot of machinery to build for a case that, in a single-toolchain language, you usually don't need — because you control the whole graph.

## What I'd actually do

If your language is a "compile the world" language (like Go or Rust), **don't build version-in-filename at all initially.** Resolve versions statically at build time; error on conflicts. Add `compatibility_version` stamps so that if a dylib _does_ get shared across builds, dyld catches incompatibility. Only introduce `libX.<major>.dylib` coexistence if and when you actually ship a stable, third-party-linkable runtime — at which point you're in C-package-manager territory and the naming convention comes along for the ride.

The `libClawr.A.dylib` naming you have now is neither the C convention nor the modern-build-system convention; it's a homegrown one. If you keep it, be explicit in your docs that `.A` is _your_ ABI-generation marker and that it works the same way `libfoo.1.dylib` does in C — that way future-you (and future contributors) knows which model you're playing in.

> I don't understand the Path B case. Won't there be conflicts if we pick a single version? If we choose libB.2, libA might use deprecated APIs that have been removed, and if we choose libB.1, some APIs the program needs might not exist yet.

You're right — and this is the key realization. **Path B doesn't magically make the conflict go away. It makes the conflict a compile-time error instead of a runtime accident.** That's the actual value, and whether it's enough depends on your language's design.

Let me be precise, because I hand-waved.

## What "resolve statically" really means

There are only four possible outcomes when `app` wants `libB 2.3` and `libA` wants `libB 1.x`:

1. **A version exists that satisfies both.** If `libB 2.3` still exposes every symbol `libA` uses, then picking 2.3 works. This is the common case _if_ the library author maintains backward compatibility across majors — which they often don't, but sometimes do.

2. **No single version satisfies both, but the APIs are actually disjoint.** `libA` uses only symbols that exist in _both_ 1.x and 2.3. Then it doesn't matter which you pick; pick 2.3 and `libA` is fine. This is also common, and the compiler can prove it by checking which symbols `libA` actually references against `libB 2.3`'s exports.

3. **No single version satisfies both, and the APIs genuinely conflict.** `libA` calls `foo()` with old semantics; `app` calls `foo()` with new semantics; there is no `foo()` that satisfies both. Now you have a real problem.

4. **Two majors must coexist.** You genuinely need `libB.1` and `libB.2` loaded in the same process.

Path B handles cases 1 and 2 by _picking correctly at build time_. In case 1 or 2, you never see a diamond — the compiler just picks one version and it works. Cases 3 and 4 are the ones that require Path A (version in the filename, two copies on disk).

So the honest framing is:

- **Path B handles the diamonds that are resolvable** — which is most of them, in practice.
- **Cases 3 and 4 are the actual hard cases**, and Path B _refuses to build_ rather than silently producing a broken binary.

## Why "refuse to build" is often the right answer

You may be thinking: "but a compiler that can't build my program is worse than a runtime that loads it." Sometimes yes, sometimes no.

In the C world, case 3 doesn't fail at link time. It links fine — both `app` and `libA` record `libB.1.dylib` (or whatever), and at runtime you get **one** copy of `libB` in the process, and whichever ABI it happens to be, one of the callers is silently wrong. You get memory corruption, missing symbols resolved to garbage, or a crash three hours later. That's the failure mode Path B is designed to prevent.

So the trade is:

|           | Path A (version in name)                                  | Path B (static resolution)         |
| --------- | --------------------------------------------------------- | ---------------------------------- |
| Case 1, 2 | works                                                     | works                              |
| Case 3    | loads both, undefined behavior when global state collides | compile error with a clear message |
| Case 4    | loads both, works if no global state                      | compile error                      |

The question is which failure mode you prefer. A compile error is loud, reproducible, and points at the source. A runtime collision is silent, environment-dependent, and points at nothing. For a language whose philosophy is "don't make the programmer think about linking," a compile error that says _"libA requires libB 1.x, app requires libB 2.3, no compatible version exists"_ is arguably the correct UX — the programmer can then fix their dependency graph consciously.

## Case 4 is the interesting one

Case 4 (two majors genuinely needed in one process) is where Path B is genuinely insufficient and Path A is genuinely necessary. But case 4 is also **the case that C handles worst**, for the global-state reasons I mentioned. Loading two copies of `libB` into one process and hoping they don't fight over a global registry, a signal handler, or a memory allocator hook is the kind of thing that works 95% of the time and then corrupts memory in production.

In practice, most ecosystems decide that case 4 is _not allowed_ — Go, Rust (by default), and most modern languages would rather you restructure your dependency graph than ship two copies of a library into one process. They treat it as a code smell, not a feature.

## So what's actually true about Path B

I should have said it more carefully. Path B isn't "the conflict goes away." Path B is:

> The compiler resolves the conflict statically when a satisfying version exists, and **errors out loudly when it doesn't**, rather than punting the ambiguity to the dynamic loader where it becomes silent undefined behavior.

That's the design claim. It's not magic; it's a bet that:

- Cases 1 and 2 are the common cases (true in practice for well-maintained libraries).
- Case 3 is rare and, when it happens, is better surfaced as a compile error than as runtime corruption.
- Case 4 is rare enough to not be worth supporting, or should be supported explicitly when your language grows a way to express it (e.g. a "I really want two isolated copies" escape hatch, which is essentially what OSGi, AssemblyLoadContext, and some Wasm component models do).

If your language's users will regularly have `libA` depending on an old `libB` while the app depends on a new incompatible `libB`, then you _do_ need Path A (versioned filenames + coexistence), and you'll inherit the global-state fragility of C. But I'd start with Path B and only add Path A when a real user case forces it — because Path A is easy to add later (rename the dylib, emit the right install names) and Path B is easy to weaken later (just allow two copies when the compiler detects a genuine conflict), but starting with the complexity of Path A is a lot of machinery to maintain for a case that might never occur.

## One more thing your compiler could do

There's a middle path worth mentioning. Your compiler sees the full graph, so it could:

- Detect the conflict at compile time.
- _Try_ to resolve it (pick a common satisfying version, check symbol usage).
- If it can't, **report the exact symbols that conflict** — "libA uses `B.parse()` which was removed in 2.0; app uses `B.format()` which was added in 2.0." That's diagnostic quality C can never offer, because the C linker never sees both sides at once.
- Let the user decide: upgrade libA, downgrade the app's expectation, or explicitly allow two copies (if you support that mode).

That's the "programmer focuses on domain" version of this problem: don't hide the technical complexity, _explain_ it in domain terms and let the programmer make an informed choice. Hiding it entirely is actually the wrong goal here, because sometimes the right answer genuinely is "you have incompatible requirements, you need to restructure" — and no linker flag can fix that.

## Why dyld is dumb about this

dyld resolves `LC_LOAD_DYLIB` entries by literally walking the rpath list and `open()`-ing the first match. It doesn't parse symbol tables to check compatibility. It doesn't know that `libB.1.dylib` and `libB.2.dylib` are two majors of the same library. It doesn't know which symbols each caller uses. All it knows is: here's a string, find a file, load it.

That's a deliberate choice — dyld runs before your process has a heap, before C++ constructors, in a constrained environment, and its job is to `mmap` files fast. Adding "parse symbol requirements and match against available versions" to dyld would make every process startup slower and every loader bug scarier.

The version fields (`compatibility_version`) are the one concession: dyld checks that the loaded dylib's compatibility version is ≥ what the client requested, and _refuses to load_ if not. But it doesn't _search_ for a compatible one — if the first path it tries has an incompatible version, it errors out, it doesn't keep looking.

## Where the "smart resolver" actually lives

The symbol-aware, version-aware resolution you're describing **cannot happen in dyld**. It has to happen in something that:

1. Sees all the candidate dylibs on disk.
2. Can read their symbol tables.
3. Knows which symbols each client needs.
4. Can pick a version that satisfies everyone, or report exactly which requirement can't be met.

In the C world, that "something" is the _linker_, at link time — and it's why C's answer to this problem is "make the client record a symbol set and let the link editor sort it out." Except C's linker doesn't actually do that either; it just resolves `-lfoo` to whatever `libfoo.dylib` symlinks to at link time and trusts you.

For your language, this "something" is your compiler. You have all four pieces of information:

- Your module graph knows which module depends on which, and which symbols each use.
- Your compiler just built every dylib, so it knows each one's exported symbols and its declared ABI version.
- Your compiler controls the link command it emits, so it can choose install names deliberately rather than by rpath accident.

So the design you're reaching for is:

> At build time, the compiler resolves each `libB` reference to a _specific concrete dylib file_ that satisfies that reference's requirements — not a `@rpath` wildcard that might resolve to anything.

That means the install name in the client's `LC_LOAD_DYLIB` is not `@rpath/libB.dylib` (ambiguous) but something unambiguous — either an absolute path, or a versioned leaf name like `@rpath/libB.2.3.dylib`, or a content-addressed name. Then dyld has no choice to make; it just loads exactly what the compiler decided.

## Two regimes for "unambiguous"

There are two ways to make the reference unambiguous, and they correspond to your Path A / Path B discussion:

**Within one build (Path B):** The compiler picks one version of `libB` for the whole build. If `libA` needs symbols in 1.x and the app needs symbols in 2.3 and no single version has both, _that's the case where the compiler must either find a version that has both or report the conflict_. Your point stands: **if such a version exists, the compiler should pick it** — and it can, because it sees the full symbol requirement set. That's strictly better than what dyld does, and it's the whole reason a whole-program compiler beats a C-style linker here.

**Across builds (Path A):** If you ship modules that other people's builds consume, the compiler can't see the full graph. Then you fall back to version-in-filename and rely on the _package manager or build system_ to pick concrete files. Your compiler can still generate a "manifest" (like `deps.json`) recording which concrete version each dependency was resolved to, and a loader shim (a small executable wrapper, a `DYLD_INSERT_LIBRARIES` preload, or a custom `dlopen` orchestrator) can read that manifest and load exactly those files. But at that point you're reimplementing the CLR's assembly resolver — which is fine, and is basically what OSGi, AssemblyLoadContext, and every modern plugin system does.

## So the rule becomes

Instead of "emit `@rpath/libB.dylib` and hope dyld picks right," the compiler emits:

- A **concrete reference** to a specific file, computed at build time from symbol-level compatibility checking.
- An **rpath** that points at the directory where that file lives.

If two different clients in the same build genuinely need two different majors, and no single version satisfies both, then:

- If you want to support that, the compiler emits two concrete references (`libB.1.dylib` and `libB.2.dylib`), both files exist, and both load. You're in Path A with all its global-state caveats.
- If you don't want to support that, the compiler errors and tells the programmer exactly which symbols conflict.

Your instinct — "if a compatible version exists, don't error" — is exactly right, and it's achievable _precisely because_ your compiler is doing the resolution instead of dyld. The version-in-filename convention in C exists because C's resolution happens too late (at load time) to do symbol-aware matching. Yours happens early enough to do it properly. That's the advantage of owning the whole pipeline.

## The one caveat worth stating

The compiler can only pick a compatible version if it can _see_ that a version is compatible, which requires a notion of "compatible" more precise than "same major number." Two options:

- **Symbol-set compatibility**: `libB 2.3` is compatible with `libA`'s needs if it exports every symbol `libA` references (with compatible signatures). Your compiler can check this mechanically.
- **Declared ABI compatibility**: the library author declares "2.x is backward-compatible with 1.x" (like semver's major rule), and the compiler trusts that declaration.

The first is stronger and is what you get for free if your compiler is checking symbols anyway. The second is what semver gives you and is what C's soname convention approximates. A hybrid is common: use the declared compatibility to shortlist candidates, then verify the actual symbol references to confirm.

Either way, the decision happens at **build time**, in your compiler, with full information — which is exactly where it should be, and exactly what dyld can't do. Your "don't error if a compatible version exists" rule is implementable, and it's a stronger guarantee than any dynamic loader gives.

>
> It would have to be the second one I suppose. The absolute path could vary depending on computer. By the way: this is only used when linking? What about runtime? Can I build a program on one computer and have it run on another (where installation paths might be different)?

Yes — and you've put your finger on exactly why `@rpath` + a relative layout exists. An absolute install name bakes your build machine's paths into the binary; it will not survive a copy to another machine. Let me trace the two moments in time separately, because they're often conflated.

## Two moments: link time and run time

**Link time** is when your compiler invokes `ld` and it writes `LC_LOAD_DYLIB` entries into the client's Mach-O. The _string_ it writes is the dylib's **install name**, not the path you passed to the linker on the command line. That distinction is what bit you earlier with `dist/libClawr.A.dylib`.

**Run time** is when dyld reads those `LC_LOAD_DYLIB` entries and resolves them. It substitutes `@rpath` against the `LC_RPATH` entries in the _loading binary_ (the executable or dylib doing the loading), then `open()`s the result.

So the chain is:

```plain
link time:  ld writes  "@rpath/libB.2.3.dylib"  into app's LC_LOAD_DYLIB
            ld writes  "@loader_path/../lib"     into app's LC_RPATH
            (both strings; no path resolution yet)

run time:   dyld reads "@rpath/libB.2.3.dylib"
            sees "@rpath" token
            substitutes "@loader_path/../lib" -> "/wherever/app/is/../lib"
            opens "/wherever/app/is/../lib/libB.2.3.dylib"
```

The resolution happens **entirely at run time**, on the machine where the program is running, using that machine's actual filesystem. Nothing about the build machine's paths is baked in — _as long as_ the install name uses `@rpath` (or `@loader_path` / `@executable_path`) rather than an absolute path.

## What survives a copy to another machine

| Install name form                                     | Survives copy to another machine?                                                       |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------- |
| `/Users/johan/build/libB.2.3.dylib`                   | No — that path won't exist there                                                        |
| `@rpath/libB.2.3.dylib` + rpath `@loader_path/../lib` | Yes — relative to wherever the binary lands                                             |
| `@loader_path/../lib/libB.2.3.dylib`                  | Yes — relative to the loading binary                                                    |
| `@executable_path/../lib/libB.2.3.dylib`              | Yes for executables, **wrong for dylibs** (uses the executable's dir, not the loader's) |
| `libB.2.3.dylib` (bare)                               | Only if it's in `~/lib`, `/usr/local/lib`, or `/usr/lib`                                |

So your instinct is right: use `@rpath/libB.2.3.dylib` (versioned leaf name) and pair it with an rpath that's relative to the loading binary. Then you can `rsync` the whole build tree to another Mac with the same architecture and it just works.

## The layout matters as much as the tokens

For "copy to another machine" to work, the _relative layout_ of binaries and libraries must be preserved. If you have:

```plain
build/
  bin/app
  lib/libA.1.0.0.dylib
  lib/libB.2.3.0.dylib
```

and `app` has rpath `@loader_path/../lib`, then copying `build/` anywhere works, because `app` finds `../lib` relative to itself. Copy _just_ `app` without the `lib/` directory and it fails — because the layout that the rpath assumes is broken.

This is why macOS `.app` bundles exist: they're a standardized layout (executable in `Contents/MacOS/`, dylibs in `Contents/Frameworks/`, rpaths pointing `@loader_path/../Frameworks`) so "copy the `.app`" works as a unit. You don't need to use bundles, but you do need _a_ convention for "what's the unit of copyability" — usually "the whole build output directory."

## What `@rpath` gives you that `@loader_path` alone doesn't

You could skip `@rpath` entirely and just write `@loader_path/../lib/libB.2.3.dylib` as the install name. That also survives copying. The reason to prefer `@rpath/<name>` is **flexibility for the _consumer_**:

- With `@loader_path/...`, the location of `libB` is decided by the _producer_ of `libB` (it's baked into every client's `LC_LOAD_DYLIB` when they link).
- With `@rpath/<name>`, the location is decided by the _loading binary's_ rpath list. Different apps can map the same `@rpath/libB.2.3.dylib` to different directories. An app bundle can keep it in `Contents/Frameworks/`; a CLI tool can keep it in `/usr/local/lib`; a test harness can keep it next to the test binary. Same install name, different resolution per consumer.

This is the whole point of `@rpath`: **defer the directory choice to the consumer, while fixing the identity (name + version) at link time.** It's the closest native equivalent to "the assembly is identified by name, and the resolver decides where to find it."

## For your compiler specifically

The recipe that gives you "build anywhere, run anywhere" is:

1. **Install name** of every dylib: `@rpath/<name>.<abi-version>.dylib` (e.g. `@rpath/libClawr.B.2.dylib`). Fixed string, no absolute paths, version embedded so diamond deps can coexist.
2. **Rpath** of every executable _and_ every dylib your compiler produces: `@loader_path/<relative-path-from-this-artifact-to-the-lib-dir>`. Relative, so it moves with the tree.
3. **Layout convention**: your compiler decides where libs go relative to binaries (e.g. `bin/` and `lib/` side by side, or `lib/` under the executable's dir, or a `.app` bundle layout). It's an invariant of your toolchain, not something the programmer configures.
4. **Copyability unit**: document that "copying the whole build output directory preserves the ability to run." Within that directory, nothing is absolute.

Then:

- Build on machine A, copy the output directory to machine B, it runs — as long as B has a compatible OS version and CPU architecture.
- Build on A, and if you want to install to a system location on B, you can still `cp` the pieces into `/usr/local/lib` and `/usr/local/bin` — but only if the rpaths happen to cover that. Usually you'd instead ship the whole directory and let users run it in place, or build a `.pkg`/`.app`/installer that preserves the layout.

## The one remaining absolute-path hazard

There's a subtle way an absolute path can sneak back in: if you link a client with `-L /absolute/path/to/lib -lB`, the _linker_ reads the dylib and copies its **install name** into the client. It does not copy the `-L` path. So as long as the dylib's install name is `@rpath/...`, the client is portable — even though your build command used an absolute path during linking. The install name is what matters, and it's the thing you already fixed.

That's why the earlier bug was so confusing: everything _looked_ relative, but the install name was the literal `-o` argument, which is what got baked in. Once the install name is `@rpath/...`, the build-machine path is irrelevant at runtime.

## Short answer to your question

> Can I build a program on one computer and have it run on another (where installation paths might be different)?

Yes — if the install names are `@rpath/<name>` and the rpaths are `@loader_path/...`. Those two strings together mean "resolve at run time, relative to where I am," so the build machine's filesystem layout is irrelevant to the runtime machine. If any install name is an absolute path, the answer is no — that path must exist verbatim on the target machine. Your compiler should never emit an absolute install name for its own dylibs; that's the invariant that makes the whole thing portable.
