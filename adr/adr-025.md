# ADR-025: The `real` Datatype

[ADRs](../README.md)

## Status

✍🏼 **Draft**

> A rough sketch of an idea

## Context

Clawr supports `integer` as arbitrarily sized `Integer*` or `bigint` representing all of ℤ. A range constraint allows the backend to optimize the representation as `uint64_t`, `int`, `char` or whatever it finds appropriate. Even ternary `btint27` — or whatever such might be called — could be chosen if the platform is ternary.

The `real` keyword should mean “all of ℝ.” In order to represent a `real` at runtime, however, the declaration will need a precision constraint, since irrational numbers like $\pi$ and $\sqrt 2$ cannot be stored exactly in finite memory. An unconstrained `real` might or might not be permissible; that is a question for another time. It is technically possible to define an arbitrarily sized `decimal`, but that does not mean it should necessarily be allowed.

## Decision

a `subset` of `real` should be defined akin to `subset probability = real (0.0...1.0)`. It does not specify precision, because that is not its job. Instead, the precision comes into play when the subset is applied: `mut a: probability scale 3` or `mut b: real (0.0...1.0) scale 5`.

In the CIR, the `RealRange` *type* should maybe, maybe not, include precision. The `value` and `domain`properties, however, `MUST` include it, or the backend would not know how to perform the lowering.

### Precision Kinds

There are three kinds of precision: scale, significant digits and maximum error. (Or maybe four, because the maximum error could be absolute or relative.)

The annotation `scale 5` means that values are multiples of $10^{-5}$. These can be stored as `integer` values by multiplying the actual value with $100{,}000$.

A `sig 5` annotation (spelling proposed by AI) means that the representation `MUST` maintain 5 correct decimal digits such as $2.3456\cdot 10^{7}$.

Finally, an annotation like `within 0.02` sets a maximum absolute “error.” It will probably be implemented similarly to `scale`, but not necessarily with the storage factor $10^n$.

It could for example be

```clawr
const x: real (10.0...100.0) within 20
```

```c
int x;

x = 0; // 20
x = 1; // 40
x = 4; // 100
```

## Alternatives Considered

- unknown keyword: sets a maximum relative “error”

It seems unclear what a “relative error” should even mean. A percentage A single-precision `float` is already much better than 1% precision (relative to the most significant digit), though its range is limited. A `quadruple` — not to mention `octuple` — in IEEE std 754 has *extremely* high precision and an arbitrary-precision `decimal` might not be needed at all.

You’re right. Precision does not belong in the subset declaration. A subset should be a pure predicate on values:

```clawr
subset probability = real (0.0...1.0)
```

That says only: “the value is a real in $[0,1]$.” It should not say how many digits the backend keeps, how it rounds, or how much error is tolerated. Those are contracts at the point where a value is stored, passed, returned, or read.

So I would attach precision to the binding/signature:

```clawr
mut c: probability scale 2
mut y: probability scale 5

fn normalize(x: probability scale 5) -> probability scale 5
```

That reads well: `c` is a probability rounded/quantized to 2 decimal places; `y` is a probability quantized to 5 decimal places. The subset stays reusable and pure.

## But “precision” is not one thing

You should distinguish at least two meanings, because they behave differently.

### 1. Exact decimal quantization: `scale d`

```clawr
mut c: probability scale 2
```

Means: the value is an exact multiple of `10^-2`.
So `0.00, 0.01, 0.02, ..., 1.00` are allowed. `0.123` is not.

This is value-like, not representation-like. The backend can lower it as an integer `n` in `[0, 10^d]`, where the represented value is `n / 10^d`. On binary or ternary chips, it is just an integer with a known scale.

### 2. Accuracy/error bound: `within ε`

```clawr
mut p: probability within 1e-10
```

Means: the value is a real in [0,1], known/required to be within `1e-10` of the true value. The backend must track error, use interval arithmetic, or use enough guard digits to guarantee the bound.

### 3. Significant digits: `sig d`

```clawr
mut p: probability sig 10
```

Means: about 10 significant decimal digits of accuracy. This is closer to floating-point semantics and needs magnitude-dependent error tracking.

For your examples, `scale` is the cleanest if you want the programmer to think “values with a fixed decimal granularity.”

## What should lowering require?

For `probability scale d`:

- Range comes from the subset: `[0, 1]`.
- Representation: integer `n` in `[0, 10^d]`.
- Value: `n / 10^d`.
- Addition: align scales, add integers.
- Multiplication: multiply integers and add scales.
  `scale d1 * scale d2 -> scale d1 + d2`.
- Assignment to a `scale d` variable: must be exactly representable, or require an explicit rounding operation.
- Backend can choose machine int, bigint, or a range-optimized integer. The scale is independent of binary/ternary.

For `within ε` or `sig d`, lowering is an error-bound contract: operations must propagate error and the backend must prove the result stays within the declared bound.

## Your specific questions

### Multiplying two `scale 10` numbers

If both operands are `scale 10`, the exact product is `scale 20`.

```clawr
let a: probability scale 10
let b: probability scale 10
let p = a * b              // inferred scale 20
let q: probability scale 10 = p   // lossy: requires rounding
```

The backend does **not** need to reserve 20 digits in `q` if `q` is declared `scale 10`. But then you are rounding. That is a value change. For abstract-value semantics, I would keep the intermediate exact and infer `scale 20`, then require an explicit rounding when assigning to `scale 10`.

If you instead mean “10 significant digits of accuracy,” then the product does not simply have 20 meaningful digits. Error grows, and you need guard digits and error analysis. Rounding back to 10 may be acceptable only if it still meets the declared accuracy.

### Assigning a 10-digit value to a 12-digit variable

If “10-digit” means `scale 10` and “12-digit” means `scale 12`:

```clawr
let x: probability scale 10 = 0.1234567891
let y: probability scale 12 = x
// y = 0.123456789100
```

This is not an error. It is exact. Every multiple of `10^-10` is also a multiple of `10^-12`, so you just pad with zeros. `scale 10` is a subtype of `scale 12` in the exact-quantization sense.

If “10-digit” means `within 1e-10` and “12-digit” means `within 1e-12`, then it is different. A value known only to 10 digits does not become known to 12 digits by storing it in a more accurate variable. The extra digits are not zeros; they are unknown. That should be an error or require an explicit cast that keeps the weaker accuracy.

## What makes the most sense to a programmer?

Programmers naturally think values are exact. So:

- `0.1` is the rational `1/10`, not a binary float.
- `x * y` means the mathematical product.
- Precision is a rounding/accuracy contract at variable boundaries, not part of the subset.
- Coarser exact to finer exact is free: `scale 10 -> scale 12` pads zeros.
- Finer exact to coarser exact requires rounding: `scale 12 -> scale 10` is lossy.
- More accurate to less accurate is free: `within 1e-12 -> within 1e-10`.
- Less accurate to more accurate is an error unless explicitly cast.
- Multiplication should infer a wider exact scale, e.g. `scale 10 * scale 10 -> scale 20`, unless the destination says otherwise.

So my recommendation is:

```clawr
subset probability = real (0.0...1.0)

mut c: probability scale 2
mut y: probability scale 5
```

Keep the subset pure. Put precision on variables, parameters, and returns. Use `scale` for exact decimal quantization, `within` for error bounds, and `sig` for significant digits. Default to exact values, and make rounding an explicit boundary event. That gives the backend a clear lowering requirement while preserving the programmer’s abstract-value mental model.
