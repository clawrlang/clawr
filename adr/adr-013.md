# ADR-013: Currying and Labels

> Status: ✍🏼 Draft

## Context

Haskell has a feature called currying.

```haskell
map :: (a -> b) -> [a] -> [b]
map f list = -- ...

double :: [a] -> [b]
double = map (*2)

double [1, 2, 3] -- -> [2, 4, 6]

double_list_1 = map (*2) [1, 2, 3] -- -> [2, 4, 6]
double_list_2 = double [1, 2, 3] -- -> [2, 4, 6]
```

Currying can be a very nice feature, but it can also be awkward. There is probably a reason why Swift for example does not support it. Which is more readable?

```swift
let doubledList = map({$0 * 2}, [1, 2, 3])
let doubledList = map([1, 2, 3], using: {$0 * 2})
```

Swift adds parameter labels which add clarity to a function call, but if the function should be used in currying, the ordering requirement makes the uncurried version less readable.

## Decision

Clawr supports currying by label rather than by position. Currying is resolved by the frontend, and the CIR contains only uncurried calls.

> [!note]
> The rules themselves are defined in the specification: [Currying](../spec/language/semantics/function-parameters.md#currying). This ADR records only the reasoning.
## Rationale

1. Currying can be complex and unfathomable. And the positioning requirement makes it awkward to employ effectively. But if currying is done by label instead of on the first argument(s), it might be easier to understand and use.

## Alternatives Considered

- No currying support at all
- Currying

## Consequences

### Positive

- Might encourage adoption.
- Since labeled parameters are identified by their label (not their position), they can be curried regardless of where they appear in the parameter list.

### Negative

- Might feel restrictive.
