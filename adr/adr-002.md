# ADR-002 Encapsulation vs Data

[ADRs](./README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

[ADR-001](./adr-001.md) decided to forgo the `class` and `struct` keywords. We need a set of keywords for defining types without declaring copy- vs reference semantics.

Robert C. “Uncle Bob” Martin defined a useful separation:

> [!quote]
>
> - An **Object** is a set of functions that operate upon implied data elements.
> - A **Data Structure** is a set of data elements operated upon by implied functions
>
> — <https://blog.cleancoder.com/uncle-bob/2019/06/16/ObjectsAndDataStructures.html>

## Decision

Introduce three distinct keywords for structured information:

- `data`: naked data structures without behavior (methods)
- `object`: encapsulated (hidden) data structures only accessed through methods
- `service`: `object`-like structures that operate on the environment

Inspired by Uncle Bob’s definitions, a `data` structure is only a set of related elements of information. It has no methods and must be passed around to functions that read or manipulate its contents.

The `object` is an encapsulated data-structure. It is defined by — and exposes only — its methods. The data elements are hidden and cannot be directly exposed. The type is intended to be designed outside-in and its state can be structurally redesigned (refactored) without affecting referencing code.

The `object` is still a data structure, though. It is not allowed to access the internet, open files or read sensors. Or to otherwise access the environment it operates in. It is limited to its internal state only.

A `service` type looks very much like an `object` type, but it can start background processes, open file handles and do anything at all to the environment, as long as it has an interface to operate.

Because every `service` variable’s “state” is the entire computing system/environment they cannot be `ISOLATED` from each other. Therefore `service` precludes `const`/`mut`, and variables `MUST` always be declared using the `ref` or `mutref` keywords.

## Rationale

1. The `data`/`object` separation is conceptually more useful than the `class`/`struct` one.
2. Forced encapsulation means that invariants can be protected AND users are fully decoupled from the internal structure.
3. The `data` construct can be used for big-data computations, read-only systems and DTOs.
4. The `object` can be chosen for rich DDD models, to protect invariants and as secure domain primitives.
5. Conflating data/state with external operation can add undue cognitive pressure.

## Alternatives Considered

- None. This is a founding idea for the language.

## Consequences

### Positive

- Single types are more reusable across different use cases
- Clear intent at the point of declaration
- Integrates naturally with ARC and isolation guarantees
- Allows object-oriented and functional patterns without fighting the type system
- Allows local reasoning (for `ISOLATED` data) with strong guarantees

### Negative

- Might be confusing to programmers coming from the `class`/`struct` tradition.
- Might be inflexible and requires new refactoring patterns such as “Encapsulate `data`,” and its opposite.
