# ADR-037: Hashing and `HashEquatable`

> Status: ✍🏼 Draft

## Context

The standard-library sketch proposes `HashEquatable`, a backend-defined
`HashCode` and a `HashBuilder`. Hash-based sets and dictionaries will need
compatible equality and hashing, but Clawr does not yet have collections.
The [standard-library proposal](https://clawrlang.github.io/clawr-doc/std-lib/)
leaves the hash representation and algorithm to the backend.

An application should be able to describe which parts of a value determine
its equality without selecting a machine word size, a numeric base, or
implementing its own hash mixing. In particular, the frontend should not
need to know the range, base, or representation of a backend's hash codes.

The hashing API is **layered**. Only `HashEquatable` is user-facing.
`HashBuilder`, `HashCode`,
`bucketIndex` and the builder factory are library- and runtime-facing, and
are opaque to ordinary programs.

## Proposed direction

### Layering

Three layers, with strict visibility boundaries:

1. **User-facing.** `HashEquatable.hash(into:)`. The only hashing
   signature ordinary programs see or implement.
2. **Library-facing.** `HashBuilder`, `HashCode`, `bucketIndex`, and the
   builder factory. Named by collection implementations (when collections
   exist) and by the standard library. Not intended for ordinary programs.
3. **Backend/runtime.** The opaque representations, mixing algorithm,
   seeding, and canonical encodings behind layer 2.

`HashCode` and `HashBuilder` are **opaque builtin types**, not traits.
Programs cannot conform to them. The only operation exposed on `HashCode`
is `Equatable`. This is what preserves backend freedom over width, base
and representation; it also means a ternary backend needs no source-level
changes.

The visibility mechanism for layer 2 is not yet designed. Until it is,
these declarations are visible to all programs; that is a temporary
concession, not a design goal.

### `HashEquatable`

`HashEquatable` requires `Equatable`. Its hashing requirement contributes a
value's equality-relevant components to a runtime-provided builder. The
collection or runtime creates and finalizes the builder; the conforming
value never chooses the algorithm and never returns a hash code.

Equal values are assumed to produce the same hash when contributed to a
builder using the same hashing context. Since the implementation is
programmer-provided, this is not guaranteed. Both frontend and backend MAY
assume the programmer upholds the contract.

```clawr
trait HashEquatable: Equatable {
    func hash(into builder: HashBuilder)
}
```

`hash(into:)` MUST call `builder.add(value: property)` for each property
that contributes to the final hash, in a stable order.

### `HashBuilder`

Opaque, runtime-provided, not constructible by user code. User code calls
`add` only from inside `hash(into:)`. Only the runtime creates and
finalizes builders.

```clawr
// Opaque. Value type. Not constructible by user code.
// Sketch syntax; not currently implemented.
opaque type HashBuilder {

    // Generic form once generics land; the existential form is the v1 fallback.
    func add(value: HashEquatable)      // MUST call value.hash(into: self)

    // Leaf contributions. The choice of generics, overloads, or distinct
    // operations is deferred; see "Implementation considerations".
    func add(value: truthvalue)
    func add(value: integer)
    func add(value: real)
    func add(value: string)

    // Consumes the builder. After this call, the builder is invalid.
    func finish() -> HashCode
}
```

Builder contract:

- `add(value: HashEquatable)` MUST be implemented to simply call
  `value.hash(into: self)`.
- Each `add` MUST frame its contribution canonically (for example, a type
  tag plus a length prefix, or an unambiguous encoding), so that
  `add("ab"); add("c")` and `add("a"); add("bc")` contribute differently.
  Framing belongs to the builder, not to user code.
- `finish()` consumes the builder. Double-finalization is a programmer
  error; its behavior is unspecified or trapped.

### Factory

```clawr
extern func newHashBuilder() -> HashBuilder
```

A free `extern` function is the initial approach. A companion object is a
natural long-term home for the factory but adds frontend and runtime
complexity without user-visible benefit; it is deferred. The free factory
should be hidden from ordinary programs once visibility support exists;
hiding it may also be deferred.

This declaration depends on `extern` being able to return an opaque type
(or on an equivalent builtin-declaration path). If `extern` does not yet
support opaque return types, an interim builtin-declaration mechanism is
required; this is tracked in implementation considerations.

### `HashCode`

Opaque value type. `Equatable` within a hashing context. No arithmetic,
no ordering, no conversion to integer, no serialization. Not constructible
by user code.

```clawr
// Opaque. Value type. Not constructible by user code.
opaque type HashCode: Equatable {}
```

The backend chooses the representation: a bounded integer, a field, or
something else. No width, range, base, or storage form is part of the
frontend contract. A `HashCode` from one context (one seed) is not
comparable to a `HashCode` from another; a collection MUST use a single
compatible context across insertion, lookup, removal and resizing.

### `bucketIndex`

```clawr
// Result MUST satisfy 0 <= result < max.
extern func bucketIndex(hash: HashCode, max: integer) -> integer
```

The backend implements this. The frontend cannot perform modular
reduction on an opaque `HashCode`; only the backend can map one to a
frontend `integer` suitable for indexing collection storage. The
postcondition is trusted because the backend implements the operation;
implementations may debug-assert it.

`max` is a runtime value, not a type parameter. A dependent signature such
as `func bucketIndex<Max: integer>(...) -> integer (0..<Max)` would require
value-indexed types and could not express a runtime capacity, so it is
rejected. Returning `HashCode` is also rejected, because the collection
needs a frontend `integer` to index storage.

If a collection context object is introduced later, `bucketIndex` becomes
a method on it; a free function is sufficient for now.

### Backend-owned hashing

The backend and runtime choose the internal hash representation, mixing
algorithm and seed. A backend may use a bounded integer or a field; no
particular range, width, base or storage form is part of the frontend
contract. Hash results are not portable or stable across processes,
backends or runtime versions, and must not be used as persistent
identifiers.

The runtime must make compatible contexts available to every hash
operation within a collection, including insertion, lookup, removal and
resizing. Independently seeded builders for the same collection would
break lookup. A possible initial design uses a securely generated
process-wide key, with each `newHashBuilder()` starting fresh state under
that key; a later collection-specific context is possible, but its API is
not yet specified.

For hash tables exposed to adversarial keys, the backend should use a
well-established keyed hash with a secret generated by an appropriate
secure random source. Randomizing a multiplier alone is not a sufficient
design. The choice of algorithm, entropy-failure behavior, and whether
the public builder can expose a finalized result require further design.

## Implementation considerations

1. Define trait inheritance and `HashEquatable`'s conformance rules:
   today the interface parser does not accept a supertrait list. Decide
   how inherited requirements and witness dispatch are represented.
2. Define the builder's Clawr-facing interface, ownership and mutation
   semantics, and creation/finalization lifecycle. Decide which builder
   operations can be declared and called without generics or overloading,
   and how nested conformances contribute values.
3. Specify the builder's canonical component framing (type tag and/or
   length prefix per contribution). Specify equality-consistent behavior
   for each primitive before claiming its conformance, especially where
   different representations denote equal values.
4. Add a backend/runtime builder with a compatible hashing context.
   Confirm that `extern` can return an opaque type (or specify the interim
   builtin-declaration path), and that `bucketIndex` can return a
   frontend `integer`.
5. Prove the path end-to-end with a user-defined value containing an
   integer field. Test equal values, unequal values, deliberate collisions,
   component order and framing, nested contributions, and repeated fresh
   builders in the same context. Test backend-specific seed behavior
   without relying on hashes differing by chance.
6. Defer collections, collection key ownership, source-level visibility
   of layer 2, a public `HashCode`, and companion constructors. Test the
   runtime contract directly until collections exist.

## Alternatives considered

- **Return `HashCode` from each value.** Exposes a backend-dependent
  result to the frontend and makes combining components and managing
  seeds harder to centralize.
- **Fix an integer range and hash algorithm in Clawr.** Simplifies the
  interface but unnecessarily restricts backends and invites reliance on
  a stable result.
- **Use the documented `hashCode(using:) -> HashCode` sketch.** Passes a
  builder but still makes each value return a finalized code; contributing
  into a shared builder makes nested composition more direct.
- **`HashCode` as a trait.** Would allow user conformances and defeat
  opacity; the frontend would then need to reason about representations
  it cannot see.
- **`HashBuilder` as a trait.** Same problem: user conformances would
  bypass the runtime's canonical framing and context handling.
- **`bucketIndex<Max: integer>` with a dependent return type.** Requires
  value-indexed types and cannot express a runtime table capacity.
- **`bucketIndex` returning `HashCode`.** The frontend cannot index
  storage with an opaque token; the conversion to a frontend `integer`
  belongs in the backend.
- **Companion-based factory.** Feels natural but couples the design to
  companion objects and adds runtime integration complexity; a free
  `extern` factory is simpler for now.

## Consequences

- User code describes equality-relevant components; the runtime controls
  representation, seeding and mixing.
- The frontend reasons about conformance and method signatures without
  knowing the set of possible hash codes, their width, or their base.
- Base-agnosticism follows from opacity: ternary and non-binary backends
  need no source-level changes.
- Layer 2 (`HashBuilder`, `HashCode`, `bucketIndex`, factory) is visible
  to all programs until a visibility mechanism exists. This is a
  temporary concession.
- The design depends on `extern` returning opaque types, or on an interim
  builtin-declaration mechanism.
- This is a draft: none of the sketched hashing API, trait inheritance or
  collection behavior should be treated as implemented or adopted.
