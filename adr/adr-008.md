# ADR-008: Protocol Types

## Status

💡 **Proposed**

> A proposed idea

## Context

Most object-oriented languages afford mechanisms for defining abstract types: `trait`, `protocol`, `interface` and maybe other forms. They all work similarly in that they define requirements for conforming types, and extensions can be used to add implemented functionality to all conforming types.

Clawr has a complication in that `service` types may not be `ISOLATED`.

## Decision

Add two keywords for abstract types: `trait` and `role`. A `trait` applies to `data`/`object` types, but cannot be used for `service` types. It may also be used for boxable types such as `integer` and `truthvalue`.

 A `role` might be added to any type.

## Rationale

1. Because `service` types must be `SHARED`, and `trait`s should be allowed on `ISOLATED` values, `service` needs a reference-only trait (the `role`).
2. Because any value (if sometimes boxed) can be a reference-type, there is not reason to restrict `role`.
3. A `role` that is expected to access a repository could store all of its data in memory — particularly useful in tests — which would make an `object` more suitable than a `service`.

## Alternatives Considered

- Eschew abstract types entirely.
- Only a single keyword (which would require `SHARED`use  only).

## Consequences

### Positive

- Flexible and expressive: a `trait` describes inherent properties of data. A `role` describes a capability that can be exploited.

### Negative

- Might be confusing that a `service` cannot conform to a `trait`.
