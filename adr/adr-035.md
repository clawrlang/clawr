# ADR-035: Separating Mutability from Isolation in Declaration Syntax

[ADRs](./README.md)

> Adopted

## Context

Clawr currently expresses semantic modes via a four-token prefix on declarations:

```clawr
const x: T      // isolated, immutable variable
mut x: T        // isolated, mutable variable (copy-on-write)
ref x: T        // reference to shared mutable state, not re-bindable
mutref x: T     // reference to shared mutable state, re-bindable
```

This syntax fuses two orthogonal axes — **mutability** and **isolation** (`ISOLATED` vs `SHARED`) — into a single keyword slot. This creates three problems:

1. **The fused tokens are not compositional.** `mutref` is a portmanteau rather than a modifier; readers cannot derive its meaning from its parts.
2. **`mut` is ambiguous at a glance.** On an isolated variable it means "structurally mutable (COW)"; on a shared handle it means "rebindable." The two senses are unrelated.
3. **Isolation cannot be expressed in type position.** A collection such as `List<T>` needs to know statically whether its items are isolated or shared — otherwise code holding an item cannot know whether it may hand it out. The current prefix-only syntax has no way to say `List<ref T>`.

[ADR-002](./adr-002.md) established that a type _structure_ must be reusable across isolation modes; it did not preclude the _type syntax at a use site_ from carrying an isolation modifier. This ADR formalizes that distinction and changes the declaration grammar accordingly.

## Decision

### Grammar

The declaration prefix is reduced to `const` and `mut`. Isolation is moved to a type modifier:

```clawr
declaration := (const | mut)? name ":" type
type        := (ref | cow)? typeConstructor
```

Each axis now occupies its own slot. Every declaration is the composition of the two axes plus a site-specific defaulting rule.

Examples:

| Declaration      | Replaces      | Isolation          | Mutability             | Comment                             |
| ---------------- | ------------- | ------------------ | ---------------------- | ----------------------------------- |
| `const x: cow T` | `const x: T`  | ISOLATED           | structurally immutable | Even `mut` properties are immutable |
| `mut x: cow T`   | `mut x: T`    | ISOLATED           | mutable                | copy-on-write                       |
| `const x: ref T` | `ref x: T`    | SHARED             | immutable binding      | shared mutable state                |
| `mut x: ref T`   | `mutref x: T` | SHARED             | re-bindable            | shared mutable state                |
| `const x: T`     | `const x: T`  | ISOLATED / UNKNOWN | structurally immutable |                                     |
| `mut x: T`       | `mut x: T`    | ISOLATED           | mutable                | Not allowed for parameters          |

As before, properties can be declared without the `mut` keyword and still be implicitly mutable. Now, however, they can be declared `p: ref T` and be re-bindable references rather than isolated with copy-on-write. Parameters may omit `const` and still be implicitly immutable.

For a `UNIQUE` return value (see [ADR-003](./adr-003.md)), you can append `as cow` after the expression (e.g. `const x = copy(of: y) as cow`) to infer the type but specify that the variable should be `ISOLATED` (or `as ref` for a shared-reference variable).

For variable-declarations and properties, omitting the isolation keyword implies `ISOLATED` isolation. For function parameters on the other hand, the same omission implies `UNKNOWN` isolation (see [ADR-004](./adr-004.md)). To explicitly specify isolation, use `ref` for shared references or `cow` for copy-on-write isolated values. Explicitly stated isolation yields the same result for all declarations.

## Consequences

### Positive

- **Simpler grammar.** Two axes, each with its own slot. No portmanteau keywords.
- **Type-level isolation.** `List<ref T>` becomes expressible. Containers can declare item isolation statically, which is required for their safe use.
- **Unambiguous `mut`.** On isolated values it means structural mutability; on shared handles it means re-bindability. The two senses never overlap because the isolation modifier is visible in the type.
- **Consistent mental model.** `const`/`mut` always answers "can this name be used to change something?"—what _something_ is (the value or the binding) is determined by the type modifier.
- **Clear removal of a confused feature.** The C++ `T* const` / `T const*` distinction is not replicated; immutability lives in the type where it can be enforced.

### Negative / Risks

- **Hard syntax break.** Every `ref`/`mutref` declaration in existing ADRs, examples, and documentation must be migrated. Acceptable pre-users; note in migration guidance.

### Amendments required

## Alternatives considered

1. **Keep the four-token syntax.** Rejected: it cannot express `List<ref T>`, and it fuses two orthogonal axes into one keyword slot.
2. **Add a fifth keyword (`cow`) to the existing four-token set.** Rejected: multiplies keywords without removing the fusion problem, and still cannot express isolation in type position.
3. **Type-level semantics à la `Shared<T>` / `Isolated<T>` constructors.** Rejected: this is the design ADR-002 considered and rejected—it forces awkward workarounds when a type needs both patterns. The modifier syntax keeps the type structure (`T`) uniform and reusable; only the _use-site modifier_ differs.
4. **Make bare `p: T` mean isolated and require an explicit `unknown` keyword for the flexible case.** Rejected: inverts the default so the common, flexible case pays the annotation cost. The `UNKNOWN` case is the more common one for parameters.
