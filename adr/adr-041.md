# ADR-041: Binary and Ternary Fields

> Status: 📝 Proposed

## Context

I/O formats and algorithms can specify sequences of binary or ternary states, independently of the hardware executing the program. Clawr needs to represent and manipulate those sequences without treating the storage representation of an `integer` as part of the language.

## Decision

**Proposed, not adopted:** binary and ternary fields are distinct kinds of ordered lane sequences, both available on every platform. Their meaning is independent of how a backend stores them.

The first implementation uses `bitfield` and `tritfield` as the field kinds. In a type declaration, `bitfield(32)` and `tritfield(27)` constrain the exact number of lanes; unqualified `bitfield` and `tritfield` allow any length. These constraints do not require generics or general-purpose arrays.

The initial constructors `bitfield("1001")` and `tritfield("T01")` take a string in displayed lane order. Binary `0` and `1` mean `false` and `true`; ternary `T`, `0`, and `1` mean `false`, `ambiguous`, and `true`. Empty strings construct empty fields. These textual forms are not wire formats.

`fieldLength(field)` returns the lane count as an `integer`. The initial pointwise ternary functions are `tritwiseAdjust(a, b)`, `tritwiseRotate(a, b)` and `tritwiseModulate(a, b)`. These names refer to state operations, not lane-position rotation. A user-declared function with the same name, arity, and argument labels takes precedence over the built-in, regardless of parameter types.

The current compiler accepts fixed length constraints written as non-negative integer literals up to 2⁵³−1; allocation may fail much earlier. This is an implementation limit, not a native word size or a wire-format rule.

### Values and widths

- A binary lane is `false` or `true`; a ternary lane is `false`, `ambiguous`, or `true`. A field is an ordered, finite sequence of lanes of one kind.
- A field's length is its number of lanes. Fields of different kinds are not interchangeable, even when their lengths match. Equality requires the same kind, length, and lane values in the same order.
- A field can have any non-negative length, including zero. A fixed-length field constrains the length as part of its value set. A variable-length field can represent buffers and messages of varying lengths. Generic width parameters remain open.
- Algorithm-specified widths are exact and portable: a 32-lane binary field is still 32 lanes on a ternary machine. Native word size is an implementation detail, not the default semantic width. The runtime's current 64-lane word limit is not a proposed language limit.

The ordered positions are indexed from 0 to length minus one, in sequence order. In examples, fields are displayed in that order. For example, binary `1001` has `true` at positions 0 and 3. This ordering does not by itself assign numeric significance to a position.

### Manipulation

The initial vocabulary should allow constructing fields, querying their length, accessing and replacing lanes, slicing, and concatenating fields of the same kind. Indexing and slicing must specify bounds and report invalid ranges rather than silently truncating. Exact APIs and error behavior are still to be designed.

Pointwise operations require equal kinds and lengths and preserve both. Binary AND, OR, XOR, and NOT use the usual Boolean truth tables. For ternary AND and OR, use minimum and maximum under `false < ambiguous < true`; ternary NOT exchanges `false` and `true` and leaves `ambiguous` unchanged. Binary XOR does not determine a unique ternary XOR; additional ternary operations need their own explicitly specified truth tables.

The pointwise operators are `&`, `|`, and `!` on both kinds, and `^` on binary fields only. Numeric `^` remains exponentiation. Both uses of `^` have the existing exponentiation precedence and right associativity, so `a & b ^ c` groups as `a & (b ^ c)`. Equality and inequality compare fields of the same kind; different lengths are unequal. Comparing different field kinds is a type error.

Ternary fields also support pointwise `adjust`, `rotate`, and `modulate`, using the corresponding [truthvalue functions and truth tables](../spec/language/builtin-types/truthvalue.md#truth-tables). Each operation applies the scalar function to corresponding lanes of two equal-length ternary fields:

- `adjust` moves each lane one step towards the corresponding control lane, staying at an extreme and leaving the lane unchanged for `ambiguous`.
- `rotate` moves each lane one step in the direction indicated by the corresponding control lane, wrapping at the extremes and leaving the lane unchanged for `ambiguous`.
- `modulate` negates a lane for a `false` control lane, leaves it unchanged for `true`, and produces `ambiguous` for `ambiguous`.

For example, `tritwiseRotate(tritfield("T01"), tritfield("1T0"))` yields `tritfield("0T1")`. These operations retain the scalar semantics independently of the field's representation. Whether a scalar control value can be broadcast remains open.

Shifts and rotations operate on the sequence, not on an integer. A left shift moves lanes towards lower indices and a right shift moves them towards higher indices. The `<<` and `>>` operators discard lanes shifted out and fill vacated positions with `false` for either kind. A shift by at least the field length yields a field entirely of `false` lanes; a negative count is invalid. For example, `bitfield("1001") << 1` yields `0010`. A left rotation by one yields `0011`; rotations wrap rather than discard lanes, reduce a non-negative count modulo the length, and leave an empty field empty. Lane rotation syntax remains open.

Shift operators bind more tightly than field AND and OR, but less tightly than addition. A caller-selectable shift fill can be considered separately.

Invalid constructors, negative shifts, incompatible fixed-length assignments, and pointwise operations on unequal lengths are reported at compile time when provable; otherwise they panic at runtime until structured error handling is available. Resource exhaustion also fails explicitly.

Pointwise ternary _state rotation_ is a different operation from rotating lane positions. The runtime's filter operation is a potential library operation, not automatically part of the initial language contract.

### Encodings and I/O

A field is not an integer or a physical buffer. Reading or writing requires an explicit format and an I/O interface; neither the field type nor the host architecture implicitly determines a wire representation. An encoding must specify lane order, grouping, symbol mapping, length or framing, padding, and what happens to malformed input. Endianness belongs to an encoding of multi-lane values, not to the field's storage.

For example, an octet-oriented binary protocol can define each octet as eight binary lanes, with the first lane corresponding to the octet's most significant bit. Under that particular convention, `10000000` is octet `0x80`. Another protocol may specify a different ordering. A non-multiple of eight lanes needs an explicit length and padding rule; an arbitrary octet stream does not carry that bit length on its own. I/O must not expose the backend's in-memory packing as the protocol encoding.

Ternary fields also require a specified encoding. For illustration, a binary transport could encode each lane using two bits: `false` as `00`, `ambiguous` as `01`, and `true` as `10`, rejecting `11` as invalid. This is just an example format, **not** the runtime's internal mapping or a standard wire format. A ternary transport can use a different mapping and framing. A binary-to-ternary encoding must preserve all binary lanes; discarding one physical trit state is one possible implementation, not a portable wire protocol or a requirement on hardware.

Encoding and decoding numeric values are explicit operations whose format defines radix, digit mapping, significance order, signedness and out-of-range behavior. They are mathematical mappings, not casts of the backend's integer storage. For example, unsigned binary decoding of `1001` with the first lane most significant yields integer 9 on either kind of machine. One ternary field kind is sufficient for balanced and unbalanced ternary encodings: each encoding specifies how its three states map to digits. Clawr's `integer` includes negative values. Whether numeric codecs are part of the initial I/O library and which error APIs they use remain open; silent clamping, wrapping, or taking an absolute value must not be assumed.

### Algorithms and representation

Structural operations and pointwise logic can express many data transforms, but algorithms may also require operations with explicitly defined numeric interpretations. For example, SHA-256 and ChaCha20 use addition modulo 2³²; field logic alone does not make that addition automatic. It can be implemented as a lane algorithm, or by an explicit codec and wrapping operation. Such operations belong in libraries or separately specified abstractions, not implicitly on abstract `integer` storage. Correctness, performance, and constant-time behavior for cryptographic code require separate implementation guarantees.

Ternary algorithms may need different logic, carry rules, rotations of lane states, or encodings; binary XOR is not a universal ternary primitive. This proposal does not claim that the initial operations cover every ternary algorithm. Lane access and construction provide a way to express additional truth tables without committing to a particular ternary machine.

On binary hardware the existing runtime packs up to 64 ternary lanes into two binary words and reserves one of the four bit pairs as invalid. On ternary hardware a backend could represent binary lanes using two of three physical states, or use another representation. Backends may pack or chunk fields differently, but must preserve the same observable sequences and operations. Internal invalid states must not become observable field values.

### Open questions before implementation

- How should generic widths, lane rotation and caller-selectable shift fill be expressed?
- Which operations are language primitives and which are library functions, and how should structured errors eventually be exposed?
- What stream and buffer interfaces are needed for the first I/O use case, and which concrete binary and ternary encodings should they support?
- How should explicit numeric codecs expose width, signedness and overflow or malformed-data errors?
- Which additional ternary truth tables are useful, and what guarantees should an eventual crypto-oriented library provide?

## Rationale

1. [ADR-000](./adr-000.md) mandates platform agnosticity
2. Reading ternary data on a binary computer (and vice versa) should be possible
3. I/O formats and algorithms can specify a lane count and encoding without depending on the host's native word size or radix.
4. Both field kinds can be emulated on hardware with a different radix, though their performance and implementation costs will vary.

> [!tip]
>
> Ternary fields can be emulated using two separate binary fields. One bit from each field (in the same relative positions) would emulate the same ternary bit (or trit). This makes it easy to perform lane-wise operations using standard bit-wise operations.
>
> Two bits model four states — not just three — so one state per position would have to either be considered invalid or equal to another.

## Alternatives Considered

- Allow ternary fields only on ternary platforms. Allow binary fields on both.

## Consequences

### Positive

- Code can be made more reusable
- Binary computers can understand raw ternary data

### Negative

- Emulation, packing, and conversions may cost time and space.
- Portable semantics do not by themselves define a wire format or guarantee efficient or constant-time implementations.
