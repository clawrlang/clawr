# ADR-025s: The `real` Datatype: Precision axes and bases

[ADRs](../README.md)

## Status

💡 **Proposed**:

> An idea to be considered for adoption

## Context

`integer` represents all of ℤ. A range constraint lets the backend choose a native representation. `real` should likewise mean all of ℝ, but irrational numbers like π and √2 cannot be stored exactly in finite memory, so a stored `real` needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

![taxonomy](./images/type-taxonomy.svg)

**One principle governs the rest.** A declared precision is a _minimum_ requirement on resolution, never an exact specification of storage. Lowering may be finer than declared; it is never coarser, and "finer" means _in the same base_ — a grid of another base is not a finer grid, it is a different value set. A declared grid is nonetheless the value set: a value must lie on it even when the backing store could hold more. This splits cleanly into storage, where a same-base finer grid is free, and computation, where nothing may be guessed.

**The base word names the grid, not the hardware.** `sig 53 bin` is the value set `{m × 2ᵉ}`. On a ternary backend it is stored as an integer mantissa plus a small integer exponent and rounded to 53 binary significand digits at storage. That is the same grid and the same results, computed in software. A hardware base that matches the grid base is a fast path, not a precondition. This is what lets source written for a binary machine run unchanged on a ternary one.

## Decision

### 1. Compatibility is universe and range; precision is representation

A `subset` of `real` is an exact range, as for `integer`:

```clawr
subset probability = real (0.0...1.0)
```

What makes a value a probability is its range alone. A low-precision value is no less a probability than a high-precision one. Precision is therefore written where storage is declared (variables, `data` fields, array elements, parameters, returns), not in the `subset`:

```clawr
mut p: probability scale 5            // multiples of 0.00001
mut q: probability sig 5              // 5 significant digits
mut y: real (1.0...1000.0) sig 15     // bounded and away from zero
mut balance: real scale 2             // unbounded range: lowered to an arbitrary-size integer
mut d: real big                       // arbitrary-size decimal
```

A `type` is a subset plus a representation. **Compatibility is decided by the universe and the range only.** Precision never makes two types incompatible: it matters for lowering, and for one check at assignment (Decision 4). Equality also compares values and ignores representation, so `1.20` at `scale 2` equals `1.200` at `scale 5`.

A parameter with no precision accepts any precision, like an integer parameter with no range. A return type that must be bound declares its precision.

**Lowering finer is legal and invisible.** A backend may store a value in any grid that _contains the declared grid as a subset_ — same base, at least as fine. A `scale 2` value may live in `scale 5` storage; a narrow-range `sig n` value may live in a heap-allocated decimal (`Real*` in the C runtime). A grid of a different base is not a superset — `{k × 10⁻²}` is not contained in `{k × 2⁻⁵}`, since `0.01` is not dyadic — so cross-base lowering is not a valid storage substitution. The value set, the exactness check, equality, and compatibility are those of the declared grid; the storage grid only pads with zeros and never participates in arithmetic. Rounding is into the _declared_ grid, once (Decision 3), never into the storage grid. Because of this, `0.10 + 0.20 == 0.30` holds regardless of how much finer the store is, and `==` remains exact rather than a tolerance.

`Real*` is therefore not the exclusive property of `real big`; it is the lowering any representation needs when its exponent range or digit count exceeds a fixed format. Decision 6 keeps the type distinct from the lowering. Heavy lowering is a _cost_ surprise, not a semantic one, and is reported by lint (Open Question 3) rather than forbidden, because the source already says what it wants.

### 2. Two axes, three bases

Any `real` number can be expressed on the form $m \cdot b^e$ (though it might need infinitely many digits to store exactly). The base, $b$, is determined by the declared precision and does not need to be stored in the representation. The mantissa, $m$, is stored in the bits (or trits) of the representation. The exponent, $e$, can be defined by the precision declaration or in the representation data depending on which kind is used.

There are two precision kinds, and the base is one of a closed set:

| Kind      | Meaning                                       | Example           |
| --------- | --------------------------------------------- | ----------------- |
| `scale n` | **Absolute** resolution: multiples of base⁻ⁿ  | `scale 2` (cents) |
| `sig n`   | **Relative** resolution: n significant digits | `sig 15`          |

The base is a trailing keyword, not a free numeric parameter. A free base would imply that any base works, which no backend can honour, and the three grids differ in ways a number cannot express.

| Keyword | Meaning                          | Base |
| ------- | -------------------------------- | ---: |
| `dec`   | Decimal (the default if omitted) |   10 |
| `bin`   | Binary                           |    2 |
| `ter`   | Balanced ternary (reserved)      |    3 |

```clawr
sig 15      // decimal, default base
sig 15 dec  // same, explicit
sig 53 bin  // binary significand
scale 3     // multiples of 0.001
scale 8 bin // reserved: multiples of 2⁻⁸
```

> [!note]
>
> The `53 bin` example matches IEEE 754 `double` (aka `float64` or `binary64`), which stores 52 bits in its mantissa, and defines an implicit digit `1` that is not stored.

**Counting convention.** `n` counts _all_ significant digits including the leading one. This matches IEEE (binary64 is 53 bits including the implicit bit).

**Bounds.** `scale` alone needs no bound: its grid is uniform, so it is equally fine everywhere and lowers to a fixed-size integer for any range. A `sig` grid is relative, so it is infinitely fine near zero and needs a ceiling on the range; in the MVP, `sig` therefore requires a bounded range.

**The floor near zero is a machine delta, not a declaration.** A `sig n` grid cannot extend to arbitrarily small magnitudes in fixed-size storage, so the representation guarantees a documented floor:

> `delta(n, b, range)` is the smallest positive representable magnitude. It is no larger than the smallest positive subnormal of the smallest standard format in base `b` that has at least `n` digits and covers `range` with headroom. A backend may use a smaller delta, never a larger one.

`delta` is a _guarantee of fineness_, which is why it fits the principle above, and it is a property of the _grid_: `sig 53 bin` has the same `delta` on ternary as on binary. Values in `(0, delta)` are not in the grid: literals there are compile errors, and a computed value that lands there panics at storage, consistent with Decision 3. There are no subnormals and no flush-to-zero. A programmer who needs to go below the guarantee writes `real big` or a narrower range, which moves `delta` down.

`sig n bin` names a canonical grid, not an IEEE type. It shares binary64's grid at `n = 53` and its values compare and hash equal, but it rounds once at storage rather than after every operation. The IEEE binary types in the `subset` ADR are the ones that round after each operation; converting between the two families is explicit.

### 3. Semantics: exact values, one rounding at storage

Every representation is a **canonical grid**. Arithmetic (+, −, ×) computes the exact result, and rounding happens once, when a value is stored in a grid. There are no promotion rules between `scale` and `sig`: same-base values can be mixed freely in one expression — rescaling to a common exponent is an exact integer operation — and only storing the result needs a grid. Types that define their own operation semantics (the IEEE binary types, see the `subset` ADR) are the exception: they round after each operation.

- **Cross-base operands are rejected in the MVP.** An arithmetic expression whose operands' bases differ is a compile error unless one operand is explicitly converted (`round(x, to: sig 20 dec)`). Even the inexact case requires an exact intermediate to honour "one rounding at storage," which is the deferred work of Open Question 1, and a silent convention would reintroduce the ambient working precision this ADR forbids. Same-base mixing, including `scale`/`sig` and differing `n`, remains free.
- **Division and square root are not exact.** A bare `/` between `real big` values is a compile error unless the target grid is declared or the call names one (`divide(a, by: b, to: sig 20 dec)`). The target is exact and carries its base; no ambient working precision is allowed, since it would be hidden global state and conflicts with the isolation guarantee of `const`/`mut`. `digits: n` is accepted as sugar for `to: sig n dec` only where the operands are decimal; the base is never translated silently. Where a translation is wanted, the documented convention is `ceil(d / log₁₀(base))` digits in the other base — 20 decimal digits is 67 binary or 42 ternary — and the programmer writes it.
- **NaN, ±∞ and signed zero do not exist** for reals. Division by zero, overflow of a bounded grid, and underflow below `delta` panic, like out-of-range integers, and the value lattice removes the check where it can prove the divisor is nonzero or the result in range.
- **Rounding:** one default mode (round to nearest, ties to even), plus an explicit `round(x, mode: ...)`. Rounding mode is not a declaration annotation.

### 4. Assignment, equality and literals

- **Range is checked as type compatibility.** A provable violation is a compile error (`-200` into `(0.0...)`). Otherwise a runtime check is injected and panics on failure, as for integers.
- **Precision is never a type error.** The check at assignment is _exactness_: the value must lie on the target grid. `1.20` at `scale 2` into `scale 5` is always fine. `scale 5` into `scale 2` is fine when the lattice proves the value exact (a literal, say), and otherwise gets an injected check that panics if the value has too many digits.
- **Precision is lost only explicitly**, with `round(x, to: ...)`. Across bases (`dec`, `bin`, `ter`) `round` is required at compile time, because exactness there is rarely met and a runtime panic is a worse outcome than a compile error. The same explicit conversion is required to mix bases in an expression (Decision 3).
- **Equality** compares values exactly, so it is transitive and independent of representation. **Hashing** hashes the value, not the representation. `isclose(a, b, tol)` is a library function and is not spelled `==`.
- **Literals** are exact values and go through the same exactness check, with an optional lint for inexact literals. `const` real arithmetic is folded in exact rationals.

### 5. Inference

- `const x = 1.25` infers a singleton subset plus the literal's own precision: `sig n`, where `n` counts the digits the literal writes, including trailing zeros (`1.24` is `sig 3`, `1.20` is `sig 3`, `1.1e-1000` is `sig 2`). `sig` is canonical because it needs no special case for exponents.
- An inferred type is never `real big`. A literal with an extreme exponent or many digits is still a `sig n` type in the frontend and CIR; it is the _lowering_ that reaches for `Real*`. Cost tracks what the literal spells, not a blanket policy.
- The inferred precision binds only where the const is materialized without a target grid, such as an argument to a parameter with no declared precision. Where a target grid exists it governs, and the literal is checked for exactness against it.
- `mut` declarations require an explicit precision. This is a deliberate asymmetry with `integer`: a variable needs a representation for every future assignment, not just its initializer, so the programmer must choose one. It is not a cost argument — the cost argument is now confined to lint on the specific lowering.
- An unconstrained `mut a: real` is rejected. Parameters may omit precision, which means any representation.

### 6. `real big`

`real big` is an arbitrary-size decimal. It stays in the `real` universe, like `integer`, and needs no explicit `box`: values are isolated with copy-on-write, and the backend chooses the heap layout (`Real*` in the C runtime). It is the unbounded-precision case of the same machinery that lowers a narrow-range `sig n` or a wide-exponent literal. `sig n dec` beyond a platform's native width uses it too.

## Notes for backends (non-normative)

The semantics above are what a backend must preserve. How it does so is its own choice.

- **Lowering is by grid, on any hardware.** `scale n base b` lowers to an integer `k` meaning `k × b⁻ⁿ`. `sig n base b` lowers to an integer mantissa `m`, `|m| < bⁿ`, times `bᵉ`. Both are exact integer representations and are available on every backend. The mantissa uses the widest native integer register that fits it. A float register may hold a scaled integer mantissa — `(-1...1) scale 2` has mantissa in [-100, 100] and fits a byte — but a float is _never_ the value: `{k × 10⁻²}` is not dyadic, so a `scale 2 dec` value stored as a `double` would fail the exactness check and is not a valid lowering.
- **Fast path is grid base == hardware base.** On a binary target, `sig n bin` lowers to `float`/`double` and is native. On a ternary target, `sig n ter` is native. When the bases differ the grid is still honoured, via integer mantissa plus integer exponent, but significand rounding in a foreign base is software work: normalising to `n` digits of a base the hardware does not count in. The known worst case is decimal significand on binary hardware, the `_Decimal64`-class cost of roughly 10–100×. `sig 53 bin` on ternary is correct and slower than native; it is not a portability failure, it is a deliberate choice of grid.
- **`scale` is fast on every backend.** Its mantissa is an integer and rescaling is integer multiply or shift, so `scale 2 dec` on binary is exact and cheap even though the base differs. The base-mismatch cost is specific to `sig`, where rounding is _relative_ to the grid base. The only slow `scale` case is a range whose mantissa outgrows i64 (`2⁶³ × 10⁻ⁿ` wide), which needs `Real*`.
- **`Real*` is a lowering, not a type.** `sig n` whose range or digit count exceeds a fixed format lowers to `Real*`, as does a wide-exponent literal. This is expected, not a fallback to apologize for; report it by lint.
- **The `delta` table is a published property of the grid.** For example, `sig 15 dec` over a moderate range is no worse than decimal64's `1e-398`, and `sig 53 bin` is no worse than binary64's `4.9e-324`; a ternary backend publishes its own. The value is the same on every backend; only the speed of reaching it differs. Nothing about the table is implementation-defined beyond "no larger than".
- **Software decimal arithmetic is slower than hardware `double` on targets without a decimal unit** (for example Apple M1). Native decimal hardware is used where it exists.
- There is no default precision. Programmers choose a family: `scale` for exact fixed point (money and most business values), `sig dec` for decimal intent across magnitudes, `real big` for arbitrary precision, and the standard binary types (see the `subset` ADR) for numerics and interop.

## Consequences

- Compatibility rests on universe and range only. Precision never makes types incompatible; it drives lowering and one assignment-time exactness check.
- Declared precision bounds resolution from below. Finer lowering _within the same base_ is invisible, so a backend can pick native widths or the heap without changing meaning; a different base is not a finer lowering, and is not substituted silently.
- The base word pins the value grid, not the chip. The same source computes the same values on binary and ternary; the difference is speed, surfaced by lint.
- Near zero, `sig` is bounded by a documented `delta` rather than a second declaration. Underflow panics; it never flushes to zero.
- Arithmetic and equality act on values, not on representations. `0.10 + 0.20 == 0.30` holds, and `==` is exact.
- Losing precision always needs an explicit `round`, and across bases it is required at compile time. Naming a division target is likewise exact and base-tagged; mixed-base operands need an explicit conversion.
- Equality is well-defined, transitive and hashable across all families.
- The C backend maps `scale` and `sig dec` to integer mantissa structures, native-base `sig` to `float`/`double`, and any representation that outgrows them to `Real*`.
- The vocabulary speaks of resolution and precision, which describe storage, not measurement.

## Open Questions

1. **Exact arithmetic across bases.** MVP rule: operands of differing bases in one arithmetic expression are a compile error in favour of an explicit conversion, because even inexact mixing needs an exact intermediate. Same-base mixing stays free via exact rescaling. The deferred work is exact rational or bignum-decimal intermediates; a future `rational` universe (integer, rational, real) may be the right foundation. `ter` arithmetic waits on both.
2. **Boxing `real big`.** Does it need an explicit `box`? Current lean: no (Decision 6). Revisit only for a semantic reason such as identity or aliasing.
3. **Precision and cost lints.** Static analyses that warn when a declared precision cannot represent the range, when addition loses the smaller operand, when `==` is applied where `isclose` was probably intended, when a representation lowers to `Real*`, when a `sig` mantissa outgrows the native register, and when the grid base differs from the target hardware base. The last two are the honest home for the `_Decimal64`-class cost. Separate tooling, out of scope for the type system.
4. **The `delta` table.** Publish `delta(n, b, range)` per base, anchored to the smallest standard format with at least `n` digits that covers the range with headroom, and state the headroom rule. Ternary needs a standard ternary format before its table can be anchored. Flushing to zero remains rejected because it breaks the exactness story; panic is the rule.
5. **Non-C backends.** The CIR must carry the universe, range, precision kinds (`sig` and/or `scale`), base and digit counts so a ternary or other backend can map them. `delta` is derived from those fields by the documented function and need not be stored. Define these fields.
6. **Exactness check.** Confirm the panic within a base and the compile error across bases, and whether the check is a distinct CIR node.
7. **Relationship to the IEEE types.** `sig n bin` deliberately duplicates binary64's grid with different rounding. Decide whether the two families need an explicit conversion operator in the MVP or whether assignment plus `round` suffices.
8. **Staging.** Reserve `scale n bin` (binary fixed point, rescaled with shifts) and implement it later. Ternary grids (`ter`) wait for hardware and a standard ternary format.

**Revision notes (not part of the ADR).** The `sig n scale m` floor is removed. It was a ceiling on resolution expressed in a minimum's grammar, and it read backwards — `scale 10` suggested "at least ten places" rather than "no finer than." A documented machine `delta(n, b, range)` replaces it, restoring a single principle: declarations bound resolution from below.

"Finer" is tightened to _same base, superset grid_. Different-base storage is not a finer lowering (`{k × 10⁻²}` is not dyadic), so `scale n dec` is never stored as a float value, and `0.10 + 0.20 == 0.30` survives any amount of same-base padding. Rounding is stated to be into the declared grid, not the storage grid.

The base word is stated to name the grid, not the hardware. Any grid lowers on any backend via integer mantissa plus exponent; a matching hardware base is a fast path. This preserves the ternary vision: `sig 53 bin` runs on ternary, more slowly, not differently.

Cross-base operands in arithmetic are rejected in the MVP in favour of explicit conversion, since even the inexact case needs an exact intermediate; Open Question 1 is reworded accordingly. Same-base `scale`/`sig` mixing stays free.

`Real*` is reframed as a legal lowering for any representation that outgrows fixed formats, so Decision 3 is untouched and the cost moves to lint. Decision 5's justification now says why `mut` requires explicit precision (future assignments) and how an inferred singleton is built. Notes are reorganised into grid-based lowering, fast-path, `scale`-everywhere, `Real*`-as-lowering, and delta-as-grid-property bullets, with the `_Decimal64` cost named.
