# ADR-017: Inheritance Allocation

[ADRs](../README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

Constructors in other languages have complex rules. The super-constructor typically must complete before the subclass constructor is allowed to perform any operation — including initializing its fields.

That means that the super-constructor executes on partially initialized memory and executing abstract/virtual method can cause undefined behavior.

## Decision

Clawr supports inheritance.

The memory layout of a type includes its entire inheritance stack from supertype to subtype in strict order. Initialization of fields starts with the subtype and ends with the supertype. Secondary setup is performed in the opposite order once all fields are initialized.

1. The memory is allocated.
2. All of the subtype’s fields are initialized.
3. In initializer in the supertype is invoked.
4. The supertype’s fields are all initialized and if there is another super, its initializer is invoked.
5. After the top supertype initializes its fields, the entire allocation has been initialized.
6. Each initializer invokes optional setup before returning to the calling subtype initializer.
7. Once a supertype has returned from initialization, the subtype can perform its own secondary setup before it returns to its subtype.

Each invocation of allocation/initialization is done syntactically in the form of a data literal. That literal includes zero or one calls to a supertype initializer as well as all field values. All fields of the type (at that level in the hierarchy) `MUST` be included. Field names `MUST` not be repeated, and all specified names `MUST` match actual fields.

## Rationale

- Performing setup on partially initialized memory is complex.

## Consequences

### Negative

- New rules for initialization might be confusing.

### Positive

- It becomes impossible to execute operations on partially initialized memory.
