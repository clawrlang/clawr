# ADR-012: Parameters Labels and Ordering

[ADRs](./README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

Swift inherited *labeled parameters* from Objective C. Early versions of Swift (not sure about modern versions) required all labeled parameters to appear after unlabeled parameters. The [Swift API Design Guidelines](https://www.swift.org/documentation/api-design-guidelines/#naming) — while calling out specific situations — seems to recommend using labels rather liberally.

## Decision

All labeled function parameters must appear after all unlabeled parameters in declarations. When calling a function without currying, the arguments must be ordered to match the parameters.

The canonical name of a function includes its parameter labels so that two functions can have the same base name and yet be distinguishable. The name `copy(to:)` would refer to a different function than `copy(of:)` — they `MUST NOT` conflict even if declared in the same module/namespace.

## Rationale

1. Labels mitigate the cognitive pressure from multi-parameter functions. Were languages like Java recommend staying with monadic and dyadic functions only, a language like Swift can be readable with many more parameters.
2. The ordering rule is inspired from prior art (early versions of Swift), but also from the fact that it can make currying ([ADR-013](./adr-013.md)) more fathomable.

## Alternatives Considered

- Unlabeled functions as in Java.
- Optional labels like C#.

## Consequences

Function overloading (if supported) will have to be label-dependent. Two functions with the same “base name,” and labels — just ordered differently — will have the exact same signature. That `MUST` trigger a compile-time error.

### Positive

- Forces a structured clarity in the choice of labels.
- Enables currrying by labels.
- Might encourage the adoption of currying.

### Negative

- Might feel restrictive.
