# ADR-031: Backend Execution Mechanics and Lowering for Reals

> Status: ✅ Adopted

## Context

[ADR-025](./adr-025.md) establishes that the `real` datatype separates universe/range (`subset`) from precision and representation (`type`), introducing `scale n` (absolute) and `sig n` (relative) across bases (`dec`, `bin`, `ter`).

Following the policy update, a critical distinction applies to storage bases:

- For bounded `bin` and `ter` values, the storage base is backend-defined as long as the declared precision is satisfied at and above $x_{\text{guarantee}}$; below it, precision may decrease. Unbounded ranges require a scalable exponent.
- For `dec`, the storage and representation model must strictly be base-10 to ensure exact decimal arithmetic semantics (such as `0.1 + 0.2 == 0.3`).

This ADR defines how backends must lower real arithmetic, round after each operation, handle assignments, and manage conversions across different bases.

## Decision

Backends lower `dec` values to a strict base-10 representation, may choose any sufficiently precise representation for `bin` and `ter`, and must round after every operation. Mixing bases requires an explicit conversion.

> [!note]
> The rules themselves are defined in the specification: [`real`](../spec/cir/lattices/real.md#rules-for-backend).

## Rationale

- Mandating base-10 storage for `dec` preserves decimal-exact values and operations (including expressions like `0.1 + 0.2 == 0.3` when their precision permits), aligning with user expectations for decimal types.
- Allowing flexible storage bases for `bin` and `ter` preserves hardware efficiency and true implementation-agnosticism on non-binary architectures without forcing emulation.
- Rounding after each operation avoids the requirement for arbitrary-precision exact intermediates.

## Consequences

- Backend implementers for `dec` must support base-10 representations with magnitude limited by available memory rather than relying on binary floating-point approximations or fixed-exponent formats.
- Binary and ternary backends retain freedom to optimize representation as long as precision is respected at and above $x_{\text{guarantee}}$ for bounded ranges, with reduced precision allowed below it.
- Clear compile-time rejection of mixed-base expressions prevents hidden performance penalties and ambiguous rounding behaviors.
