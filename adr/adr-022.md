# ADR-022: `integer` Exponentiation

[ADRs](./README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

Binary operators should include exponentiation (`^`). A negative exponent will never yield an `integer` result.

Some programming languages convert the result to `double`, restrict the exponent to `unsigned` integers, or simply trap at runtime.

## Decision

Exponentiation applies to numeric operands (`integer` and `real`). When both operands are `integer`, the result is also `integer`. If at least one operand is `real`, the output is `real`.

When the operands are both `integer`, the exponent may not be negative as a negative exponent cannot yield an `integer` result.

`0^0` is an error. If the lattice evaluation produces singleton operands, the frontend `MUST` report it. Otherwise, it `MUST` be reported at runtime.

## Rationale

- $0^0$ is undefined in maths as $x^0 = 1$, but $0^x = 0$ for $x \not = 0$.
- Clawr supports arbitrary precision `integer`. It makes sense to not switch to `real` unless needed.

## Consequences

### Negative

- Might be considered inconsistent?

### Positive

- Makes sense mathematically.

## Alternatives Considered

For result type:

- Always yield a `real` result even if both operands are `integer`.
- Yield a `real` result if the exponent value-set includes negative integers.
- Introduce `rational` type and yield that for negative `integer` exponents.

For $0^0$:

- Define $0^0 = 1$ as is customary though mathematically incorrect.
