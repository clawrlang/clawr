# ADR-010: Serializable `data`

> Status: ✅ Adopted

## Context

In many programming languages, serializing and deserializing data structures often requires manually implementing serialization methods. This can be error-prone and tedious, especially for complex data structures. Automating serialization can improve code reliability and reduce boilerplate code.

Data structures are often used as DTOs or for persistence.

## Decision

Pure `data` types implicitly conform to the format-independent `Serializable` trait when every property is recursively pure data or a supported primitive. An `object` or `ref` property anywhere in that structure prevents implicit conformance, even if the property's type has a custom serializer. Explicit `Serializable` conformance supplies a custom representation and suppresses synthesis, including for otherwise-pure data. Data customizations use ordinary extensions, not a special `serialize:` section.

> [!note]
>
> The rules themselves are defined in the specification: [Rules for `data`](../spec/language/user-types/object-data.md#rules-for-data). This ADR records only the reasoning.

The initial built-in format is JSON:

- A `data` value maps to a JSON object; property names become object keys.
- A `string` maps to a JSON string.
- An `integer` maps to a JSON number token using its exact decimal value.
- A `real` maps to a JSON number token with enough decimal digits to round-trip at its declared Clawr precision.
- `false` and `true` map to JSON booleans. `ambiguous` maps to JSON `null` only when encoding a `truthvalue`; this does not add general nullability to Clawr.
- JSON arrays and general JSON `null` values are not implicitly supported until Clawr has corresponding collection and nullable value types.

The default numeric encoding preserves Clawr-to-Clawr round trips and does not impose a language-level digit limit. Consumers that use IEEE 754 binary64 may lose precision for some valid JSON numbers.

Deserialization is deferred until Clawr defines its general error-handling contract.

Serialization uses the following protocol. The compiler synthesizes ordinary extension methods that describe structures and their fields; the backend does not generate JSON-specific serializers.

```clawr
trait Serializable {
    func serialize(into serializer: ref Serializer)
}

role Serializer {
    func writeString(_ value: string)
    func writeInteger(_ value: integer)
    func writeReal(_ value: real)
    func writeTruthvalue(_ value: truthvalue)
    func beginStructure(_ typeName: string, fieldCount: integer)
    func writeField(_ name: string, value: Serializable)
    func endStructure()
}
```

`JSONSerializer` is a Clawr service implementing this role with runtime-backed buffering, escaping, numeric formatting, and nested writer-state validation. Its convenience `serialize(_:) -> string` writes one root value and finalizes the document. Alternatively, callers use `value.serialize(into: serializer)` followed by `serializer.result()`. Both operations use a single-use service: finalization requires one complete root, and subsequent writes or finalization are programmer errors.

```clawr
const serializer: ref JSONSerializer = {JSONSerializer.new()}
const json: string = serializer.serialize(value)
```

The former `serializeJSON(_:)` function remains as a convenience wrapper that constructs a fresh serializer for each call. `JSONSerializable`, `toJSON()`, and the custom data section are replaced rather than maintained as a parallel protocol.

Each structure writes its declared number of fields in order. A field recursively serializes exactly one value into the same serializer. Empty structures are supported. Invalid ordering, counts, incomplete values, and reuse are reported using the runtime's programmer-error mechanism.

Strings, integers, reals, and truthvalues have runtime-provided `Serializable` conformance. Precision-unspecified `real` formal parameters transport the original precision without rounding; arithmetic still requires a known precision, and stored/result declarations still require explicit precision.

The generic role has no string-result requirement. JSON returns a string for now; future binary formats need not do so. Interface extensions, collections, byte fields, and other built-in formats remain out of scope. Structure names and field counts alone do not provide the schema or field identifiers needed for every possible format.

The complete contract is specified in [Serialization](../spec/stdlib/serialization.md).

## Rationale

1. Persistence and communication (DTO/DAO) is the main purpose [^big-data] for a data structure. And serialisation is a fundamental strategy for that use case.
2. If encapsulated objects are persisted, it is assumed that the developer will want to define the strategy themself.
3. Shared references do not describe self-contained data and must not be followed implicitly during serialization.

[^big-data]: Data structures actually exist to support **two** main use cases: the other case is easy readonly access for computations on — and filtering of — big data.

An encapsulated `object` is defined by its behavior, not by its properties. Its state may be structurally redesigned after persistence, making automatic serialization unreliable. If serialization is required, it must be implemented explicitly through a `trait`.

A `data` structure is a simple container of exposed data elements, typically used as DTO (Data Transfer Object). Automatic serialization supports that use when the data is self-contained. References to shared state and encapsulated objects require an explicit strategy because they cannot be faithfully serialized as ordinary exposed values. Data declarations remain property-only; extensions attach custom `Serializable` implementations without changing that distinction.

## Alternatives Considered

- Requiring explicit annotation and implementation for all serialized types.
- Requiring explicit annotation, but providing a default implementation based on declared properties (like Swift).

## Consequences

### Positive

- Simple and automatic serialization for pure data

### Negative

- Custom implementations must follow the writer lifecycle; misuse is a programmer error.
