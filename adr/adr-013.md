# ADR-013: Currying and Labels

## Status

✍🏼 **Draft**

> A rough sketch of an idea

## Context

Haskell has a feature called currying.

```haskell
map :: (a -> b) -> [a] -> [b]
map f list = -- ...

double :: [a] -> [b]
double = map (*2)

double [1, 2, 3] -- -> [2, 4, 6]

double_list_1 = map (*2) [1, 2, 3] -- -> [2, 4, 6]
double_list_2 = double [1, 2, 3] -- -> [2, 4, 6]
```

Currying can be a very nice feature, but it can also be awkward. There is probably a reason why Swift for example does not support it. Which is more readable?

```swift
let doubledList = map({$0 * 2}, [1, 2, 3])
let doubledList = map([1, 2, 3], using: {$0 * 2})
```

Swift adds parameter labels which add clarity to a function call, but if the function should be used in currying, the ordering requirement makes the uncurried version less readable.

## Decision

Clawr will support currying. The basis will however not be by parameter position as in Haskell. Instead it will use labels to inject values on arbitrary positions.

```clawr
curry rotateUp = rotate(by: true) // syntax not final
curry rotateDown = rotate(by: false)

const a = rotateUp(false) // ambiguous
const b = rotateUp(ambiguous) // true
const c = rotateUp(true) // false
```

Currying will be resolved on the frontend. The CIR will represent the uncurried versions, i.e. the equivalent of:

```clawr
const a = rotate(false, by: true)
const b = rotate(ambiguous, by: true)
const c = rotate(true, by: true)
```

### Rules

1. All unlabelled parameters must appear before any labelled parameters in the parameter list.
2. Unlabelled arguments must be provided at call time in parameter order.
3. Labelled arguments can appear in any order after the unlabelled arguments.
4. Only labeled parameters can be curried.
5. Curried functions preserve parameter defaults and optionality for unspecified parameters.

## Rationale

1. Currying can be complex and unfathomable. And the positioning requirement makes it awkward to employ effectively. But if currying is done by label instead of on the first argument(s), it might be easier to understand and use.

## Consequences

### Positive

- Might encourage adoption.
- Since labeled parameters are identified by their label (not their position), they can be curried regardless of where they appear in the parameter list.

### Negative

- Might feel restrictive.
