# ADR-025: The `real` Datatype: Precision Kinds and Bases

> Status: 💡 Proposed

## Context

This ADR is the first in a series that defines the `real` datatype.

`integer` represents all of $\mathbb{Z}$. A range constraint lets the backend choose a native representation. `real` likewise represents all of $\mathbb{R}$. The range constraint is however not enough to select a representation. Since irrational numbers like $\pi$ and $\sqrt {2}$ cannot be stored exactly in finite memory, every stored `real` also needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

## Decision

There are two precision kinds over a closed set of bases:

| Kind      | Meaning                                         | Example           |
| --------- | ----------------------------------------------- | ----------------- |
| `scale n` | **Absolute** resolution: multiples of $b^{-n}$  | `scale 2` (cents) |
| `sig n`   | **Relative** resolution: $n$ significant digits | `sig 15`          |

| Keyword | Meaning                          | Base |
| ------- | -------------------------------- | ---: |
| `dec`   | Decimal (the default if omitted) |   10 |
| `bin`   | Binary                           |    2 |
| `ter`   | Balanced ternary (reserved)      |    3 |

Every stored `real` and real-valued operation has a precision. For `sig n b`, the base $b$ determines the precision rules. For `bin` and `ter`, $b$ is the precision base, and the storage base is a backend property as long as precision guarantees are met. For `dec`, however, $b$ is both the precision base and a strict requirement for a base-10 storage/representation model.

### `scale n`

A `scale n` precision implies a rational value ($\text{numerator} / \text{denominator}$) where the denominator is $b^n$ (the declared precision parameters) and only the numerator is stored. The numerator may grow as large as available memory permits. A `scale n` grid includes $0$; the smallest non-zero magnitude is exactly $b^{-n}$, fully specified and platform-independent. No lower or upper range boundary is imposed by the representation.

### `sig n`

A `sig n` precision does not imply any specific storage layout for `bin` and `ter`. For a bounded declaration `real (a...c) sig n base`, let $M = \max(\vert a\vert,\vert c\vert)$ and let $q$ be the precision base:

$$x_{\text{guarantee}} = \min\!\left({M \over q^{2n}},\ \frac{q^2}{M}\right)$$

For every stored value with $\vert x\vert \ge x_{\text{guarantee}}$, the backend must provide at least $n$ significant digits in base $q$. Below this boundary, precision may decrease; a backend may represent such values with reduced precision (for example, as subnormals), represent them exactly if they happen to lie on its grid, or reject a value it cannot represent. This permits finite-exponent formats for bounded ranges while documenting where their precision may degrade.

For a range containing only zero ($M=0$), define $x_{\text{guarantee}}=0$. An unbounded range has no finite $M$; its backend must support the requested precision across magnitudes with a scalable exponent, subject to available memory.

#### Binary storage of `ter` precisions

Binary hardware cannot represent `ter` grids exactly, so a backend without ternary storage must use a binary (or decimal) grid that is _at least as precise_ as the declaration. A binary storage format with $p$ significand bits and a finite exponent range satisfies `real (a...c) sig n ter` if:

- **Precision:** $2^{1-p} \le 3^{-n}$, i.e. $p \ge 1 + \lceil n \log_2 3 \rceil$. The worst-case relative spacing of the binary grid ($2^{1-p}$) is then no coarser than the best-case relative spacing of an $n$-trit significand ($3^{-n}$), so every value is represented with at least $n$ significant trits.
- **Range:** the largest finite magnitude is at least $M$, and the smallest magnitude at which $p$ bits are still guaranteed is at most $x_{\text{guarantee}}$, computed with $q = 3$. For an unbounded range the exponent must be scalable.

The same estimate applies in reverse for `sig n bin` stored in a decimal grid: $d$ digits suffice if $10^{1-d} \le 2^{-n}$. Choosing a wider format than required is always permitted. Because the stored grid is not the declared grid, conversions and results at the storage boundary may vary between backends, as stated below. Rounding to the declared precision (`round(x, to: ...)`) is performed on the storage grid; it guarantees at least the declared number of trits but not ternary-exact results.

> [!warning] Implementation-agnostic, not necessarily result-identical (for `bin`/`ter`).
>
> A backend may store a `bin` or `ter` `sig` value in any grid that delivers the declared precision at and above $x_{\text{guarantee}}$; below it, reduced precision is permitted. `dec` types strictly require a base-10 representation. The storage base for `bin` and `ter` need not match the declared base, so results may differ between platforms. `scale` stores an integer numerator and is exact on every base. For bounded ranges, $x_{\text{guarantee}}$ identifies where reduced precision may begin; an unbounded range requires a scalable exponent.

## Rationale

- Any `real` number can be expressed on the form $m \cdot b^e = m / b^{-e}$.
- Separating declared range from representation lets an unbounded value's exponent or numerator grow with available memory instead of imposing an implicit machine-format magnitude limit.
- The $x_{\text{guarantee}}$ boundary allows bounded `sig` types to use finite-exponent representations while stating exactly where full significant precision is required.
- The distinction between absolute (`scale n`) and relative (`sig n`) precision allows developers to choose the appropriate trade-off between fixed resolution and significant digits.

## Consequences

- Enforces a consistent and predictable behaviour for arithmetic operations _within a platform_, reducing the likelihood of subtle bugs related to precision and rounding.
- Arithmetic rounds after each operation, so results reflect the declared operation precision rather than retaining exact intermediates until storage.
- May introduce cross-platform variation in results for `sig` types using `bin` or `ter`. This is documented and deliberate. `dec` types guarantee base-10 exactness.
- Unbounded `real` ranges require a representation whose exponent can grow with the value, subject to available memory. Bounded ranges may use finite-exponent representations, with reduced precision permitted below $x_{\text{guarantee}}$.
- The precision derived for an operation from its operands must be specified; see [ADR-027](./adr-027.md).

## Alternatives Considered

- Imposing IEEE-like fixed exponent limits on unbounded `real` values: rejected because range is a logical constraint, not an implicit storage-width choice. Bounded ranges may intentionally match such formats.
