# ADR-021: Binary Operators and Precedence

> Status: ✅ Adopted

## Context

Binary operators are a staple of programming. This is generally how calculations are done in computers.

Operator notation requires an order-of-precedence to be unambiguous. When the intent is to perform operations in a different order than the default (or to emphasize the order for clarity), the strategy is typically to group operands in parentheses.

## Decision

Define a twelve-level operator precedence table. Operators are left-associative, except exponentiation (right-associative) and comparisons (non-associative).

> [!note]
>
> The rules themselves are defined in the specification: [Built-in Types](../spec/language/types.md#operator-precedence). This ADR records only the reasoning.

## Rationale

- Field operators precede comparison operators. Where C would treat `x & 5 == 5` with confusion, Clawr should chose the sensical interpretation.
- Shift operators precede logical field operators according to established prior art. There is no reason to contradict it.
- Comparison operators make no sense read from left to right: `a == b == c` can be interpreted three ways: `(a == b) == c` (where `c` must be a truth-value), `a == (b == c)` (a is the truth) or `a == b && b == c` . For a parser that does not know the types of the operands, neither interpretation is more likely than the others.
- Exponentiation distributes in maths: $\left (a ^ b \right )^c = a^{bc}$, so it makes sense for $a^{b^c}$ to be interpreted as $a^{(b^c)}$.

## Consequences

### Negative

- Programmers used to C might find the precedence order inconsistent and confusing.

### Positive

- This precedence order should appeal to mathematicians and logicians.
