# ADR-009: Interface Types

> Status: 📝 Proposed

## Context

Most object-oriented languages afford mechanisms for defining abstract types: `trait`, `protocol`, `interface` and maybe other variations. They all work similarly in that they define requirements for conforming types, and extensions can be used to add implemented functionality to all conforming types in one go.

Clawr has a complication in that `service` types may not be `ISOLATED`.

## Decision

Two keywords for abstract types are added: `trait` and `role`. They work the same way at runtime, and the difference is conceptual. A `trait` describes the constitution of a value type; a `role` describes a capability.

> [!note]
> The rules themselves are defined in the specification: [Traits and Roles](../spec/language/user-types/trait-role.md). This ADR records only the reasoning.

## Rationale

1. Because `service` types must be `SHARED`, and `trait`s should be allowed on `ISOLATED` values, `service` needs a reference-only trait (the `role`).
2. Because any value (if sometimes boxed) can be a reference-type, there is no reason to restrict `role` embodiment.
3. A `role` that is expected to access a repository could store all of its data in memory — particularly useful in tests — which would make an `object` more suitable than a `service`.

## Alternatives Considered

- Eschew abstract types entirely.
- Only a single keyword (which would require `SHARED`use only).

## Consequences

### Positive

- Flexible and expressive: a `trait` describes inherent properties of data. A `role` describes a capability that can be exploited.

### Negative

- Might be confusing that a `service` cannot conform to a `trait`.
