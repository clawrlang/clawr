# ADR-018: Object Initialization

[ADRs](../README.md)

## Status

✅ **Adopted**

> Principle is in use in the ecosystem, or the feature has been implemented in the example implementation

## Context

[ADR-017](./adr-017.md) defines how memory is laid out and the order by which initialization and setup happens: Fields are initialized from subtype to supertype and all fields are initialized before any operations can be invoked.

In the current scheme, allocation is always performed by a companion factory method which initializes the fields of the most concrete subtype as well as kicking off the initializer invocations by calling the second lowest type’s initializer. There is no initializer for the concrete type.

## Decision

Remove companion factories from the initialization process. They can still be used to simplify construction for callers, but they are not required.

Rename the “inheritance initializer” concept to just plain “initializer.” Initializers are used whether the type is the concrete floor or called by a subtype.

Use the syntax `{Type.initMethod(parameters)}` as the default way to instantiate an `object`/`service`. The braces signal that a new allocation is performed. A companion can hide this invocation. The fields are still hidden and may not be specified in this literal.

## Rationale

- Braces are a strong signal for `ALLOCATION` and initializaition.
- Express intent by freely naming initializers.

## Consequences

### Negative

- Reusing braces in supertype initialization might incorrectly signal multiple allocations.
- Requiring braces to invoke a constructor might feel weird.

### Positive

- Allocation becomes more explicit.
- Convenience factories are still allowed/possible.
- Initializers still read like methods (explicit and intentional) while distinct (with the brace syntax).
