# ADR-026: The `real` Datatype: Compatibility and Precision

> Status: ✅ Adopted

## Context

This ADR is part of a series that defines the `real` datatype.

`integer` represents all of $\mathbb{Z}$. A range constraint lets the backend choose a native representation. `real` likewise represents all of $\mathbb{R}$, with magnitudes limited in practice by available memory. Since irrational numbers like $\pi$ and $\sqrt {2}$ cannot be stored exactly in finite memory, every stored `real` needs a precision.

Three concerns must stay separate:

1. The **universe and range** (the `subset`): which values a variable may hold. This decides compatibility.
2. The **representation** (the precision): the grid of exactly representable values the backend lowers to.
3. The **operation semantics**: how arithmetic and rounding behave on those values.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation. A variable has a `type`, which defines what values it can store and how the backend lowers it.

## Decision

Compatibility is universe and range; precision is representation

A `subset` of `real` is an exact range, as for `integer`:

```clawr
subset probability = real (0.0...1.0)
```

Precision is written where storage is declared (variables, `data` fields, array elements, parameters, returns), not in the `subset`:

```clawr
mut p: probability scale 5            // multiples of 0.00001
mut q: probability sig 5              // 5 significant digits
mut y: real (1.0...1000.0) sig 15     // bounded and away from zero
mut balance: real scale 2             // unbounded range: lowered to an arbitrary-size integer
```

A `type` is a subset plus a representation. **Compatibility is decided by the universe and the range only.** Precision never makes two types incompatible. Equality also compares values and ignores representation, so `1.20` at `scale 2` equals `1.20000` at `scale 5` _within the same storage base_.

**Lowering may use a different base for `bin`/`ter`.** A backend may store a bounded `sig` value (see [ADR-025](./adr-025.md)) in any grid that delivers at least the declared precision ($n$ significant digits in base $b$) at and above $x_{\text{guarantee}}$. Below that boundary, precision may decrease. An unbounded range requires a representation whose exponent can grow as needed, subject to available memory. `dec` types must be stored using a base-10 representation. For `bin` and `ter`, the storage base need not match $b$: a `sig 15 bin` value may use a binary or ternary representation as long as it satisfies the precision guarantee.

`scale` stores an integer numerator, which is exact on every base. Per-operation rounding still applies to arithmetic. Operation precision is specified in [ADR-027](./adr-027.md), but cross-platform result identity is not promised because permitted storage grids may differ.

Each arithmetic operation rounds its result to a precision derived from its operands (see [ADR-027](./adr-027.md)); assignment rounds to the destination's declared precision when needed (see [ADR-028](./adr-028.md)).

## Rationale

- Compatibility is determined solely by the universe and range, ensuring that different representations of the same logical type are considered equal.
- Allowing any storage base that meets the precision requirement for `bin`/`ter` makes the specification implementation-agnostic across hardware formats, while requiring base-10 representation for `dec` preserves decimal exactness (e.g. `0.1 + 0.2 == 0.3`).
- Requiring precision for every stored real makes the representation explicit while leaving its magnitude range unconstrained unless a subset narrows it; bounded ranges can use $x_{\text{guarantee}}$ to specify where precision may decrease.
- The distinction between compatibility and precision allows developers to reason about correctness independently of performance optimizations related to storage and computation.
- `scale` uses an implementation-independent value grid. `sig` with `bin`/`ter` is precision-portable but not necessarily result-identical across storage bases.

## Consequences

- Ensures that different representations of the same logical type are treated consistently _within a platform_, improving reliability and predictability.
- Allows backends to use native formats for `bin`/`ter` that satisfy precision requirements without emulation, while mandating base-10 storage for `dec`.
- Arithmetic results are rounded per operation; assigning a result to a different precision can round again.
- Cross-platform result identity is not promised: `bin`/`ter` storage-base variation can change stored values and results.
- Provides a clear distinction between compatibility and precision, aiding developers in reasoning about correctness and performance optimizations.

## Alternatives Considered

- Requiring the storage base to match the declared base for all bases: simpler semantics, but forces binary hardware to emulate ternary types and vice versa; rejected for `bin`/`ter` in favour of implementation-agnosticism.
- Allowing `dec` to be lowered to binary floating-point: rejected because `0.1 + 0.2 == 0.3` must hold for decimal representations.
- Not distinguishing between compatibility and precision, which would simplify the type system but could lead to unexpected behavior when different representations of the same logical type are compared.
- Allowing multiple roundings at different stages of computation, which could provide more flexibility but would complicate reasoning about numerical accuracy.
