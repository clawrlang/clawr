# ADR-031: Backend Execution Mechanics and Lowering for Reals

> Status: ✅ Adopted

## Context

[ADR-025](./adr-025.md) establishes that the `real` datatype separates universe/range (`subset`) from precision and representation (`type`), introducing `scale n` (absolute) and `sig n` (relative) across bases (`dec`, `bin`, `ter`).

Following the policy update, a critical distinction applies to storage bases:

- For bounded `bin` and `ter` values, the storage base is backend-defined as long as the declared precision is satisfied at and above $x_{\text{guarantee}}$; below it, precision may decrease. Unbounded ranges require a scalable exponent.
- For `dec`, the storage and representation model must strictly be base-10 to ensure exact decimal arithmetic semantics (such as `0.1 + 0.2 == 0.3`).

This ADR defines how backends must lower real arithmetic, round after each operation, handle assignments, and manage conversions across different bases.

## Decision: Lowering and Execution Rules

### 1. Representation and Base Constraints in Backends

- **`dec` Backends:** Must use a base-10 representation, such as a decimal significand and exponent, that preserves decimal-exact behavior over the declared range. Unbounded ranges need a scalable exponent; bounded ranges may use finite exponent formats consistent with their $x_{\text{guarantee}}$.
- **`bin` and `ter` Backends:** May lower bounded `sig` types to any representation that delivers at least the requested $n$ significant digits at and above $x_{\text{guarantee}}$; reduced precision is allowed below it. Unbounded ranges need a scalable exponent.
- **`scale` Types:** Always lowered using an integer numerator corresponding to $b^{-n}$. The numerator may grow as needed, subject to available memory.

### 2. Rounding After Each Operation

Every real-valued arithmetic operation rounds its result to a precision derived from its operands, as specified by [ADR-027](./adr-027.md). Exact intermediates are not required.

- Assignment rounds to the destination's declared precision if it differs from the operation result's precision.
- Backends must preserve each operation's rounding point. Reassociation, contraction into fused operations, and other optimizations that remove a rounding step are not permitted unless they preserve the same observable result.

### 3. Cross-Base Operations and Conversions

- Arithmetic operations mixing different precision bases (`dec`, `bin`, `ter`) are disallowed at compile time unless an explicit conversion via `round(x, to: ...)` is provided. An exact decimal literal may adopt the other operand's precision and base as specified in [ADR-027](./adr-027.md).
- Because `dec` enforces a strict base-10 representation while `bin`/`ter` may vary, cross-base conversions require explicit lowering steps handled by the backend's runtime or compiler-generated conversion routines.

## Rationale

- Mandating base-10 storage for `dec` preserves decimal-exact values and operations (including expressions like `0.1 + 0.2 == 0.3` when their precision permits), aligning with user expectations for decimal types.
- Allowing flexible storage bases for `bin` and `ter` preserves hardware efficiency and true implementation-agnosticism on non-binary architectures without forcing emulation.
- Rounding after each operation avoids the requirement for arbitrary-precision exact intermediates.

## Consequences

- Backend implementers for `dec` must support base-10 representations with magnitude limited by available memory rather than relying on binary floating-point approximations or fixed-exponent formats.
- Binary and ternary backends retain freedom to optimize representation as long as precision is respected at and above $x_{\text{guarantee}}$ for bounded ranges, with reduced precision allowed below it.
- Clear compile-time rejection of mixed-base expressions prevents hidden performance penalties and ambiguous rounding behaviors.
