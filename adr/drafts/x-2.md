## The real problem is not the file table — it's type identity

You are circling the standard linking problem, and there is one decision inside it that is genuinely architectural and cannot be deferred: **what makes a type "the same type" across packages?**

Right now your CIR has:

```ts
type RCTypeLattice = { type: 'rc-type'; namespace?: string; name: string }
```

That is enough for one module. It is not enough the moment two independently compiled packages both define `List`, or both consume a stdlib `List`, or one consumes stdlib `List@1.2` and another consumes `List@2.0`.

If identity is `(namespace, name)`, then the moment two packages bundle their own stdlib, the linker sees two `List` types and either (a) merges them — which is wrong if they are different versions — or (b) keeps them separate — which is wrong if they are the same version. There is no correct behaviour without a package identity.

Everything else you are worrying about — duplication, version skew, hiding — follows from this decision. So decide this first, then let the rest fall out.

## What I would do

Adopt the Rust/Cargo model, which is the one that has been most thoroughly pressure-tested for exactly this scenario:

1. **One CIR per module (source file).** Matches ADR-001 ("CIR can be distributed and reused"). Enables partial compilation. Each CIR has its own `source`.

2. **A package is a named, versioned collection of CIR modules plus a manifest.** The package has a stable identity: `(name, major-version)` or `(name, version)` depending on how strict you want. Modules are namespaced inside the package.

3. **Type identity is `(package-id, module, name)`.** Not `(namespace, name)`. Add a package field to `RCTypeLattice` and `InterfaceLattice`.

4. **Semver-compatible versions unify; incompatible versions coexist.** Two packages depending on stdlib `1.x` share one stdlib. If one needs `2.x`, you get both, and the types are distinct. This is what Rust does and it works.

5. **A "bundled" CIR is a separate artifact.** When you want to distribute a single self-contained file (for shipping, for a debugger, for a final backend input), the linker produces a bundled CIR that references multiple `sources`. That is where the file table lives. The per-module CIRs stay single-source.

So you end up with:

- **Module CIR**: one file, one `source`, no `sources` table.
- **Bundled CIR**: multiple files, `sources[]`, `Span.file`.
- **Same schema**, `sources` optional, `Span.file` optional. A module CIR is the degenerate case.

That answers your "one CIR or many" question: both, and the schema treats the many-file case as a superset of the one-file case.

## The stdlib duplication question

> If they all include the std library, won't that cause problems?

Only if you bundle it into every module's CIR. Do not do that.

- The stdlib is a **package** (or a set of packages like Rust's `core`/`alloc`/`std`).
- Each package's CIRs reference stdlib types by package identity, not by copying stdlib code into themselves.
- The linker resolves the reference: one stdlib module shared by every consumer.
- If a consumer _does_ inline a stdlib function (which your frontend will want to do for pure functions), the inlined code carries provenance pointing at the stdlib's source — and the bundled CIR includes the stdlib's file in `sources`. The code is duplicated; the _type identity_ is not.

The reason type identity matters here: even if `map` is inlined into twelve different call sites, all of them still refer to the same `List` type, because the type is identified by `(stdlib-package-id, List-module, List)`. Duplication of code is fine. Duplication of type identity is not.

This is exactly the problem Go had before modules and that C++ has always had with ODR. Rust solved it by making crate identity part of the type's mangled name. You should do the same.

## "But then dependencies need to be hidden"

Yes, and this is a feature, not a cost. The model is:

- A module declares its **exports** (public entities). Non-exported entities are not addressable from outside.
- A package declares its **public API**: which modules, which types, which functions are visible to consumers.
- A consumer can reference only the public API. It cannot see the private modules its dependencies use internally.
- The linker enforces this: references that cross a package boundary must resolve to public entities, or it is a link error.

This gives you:

- **Dependency hiding by default.** `package A` uses `package B` internally; `package C` depending on `A` cannot see `B` at all unless `A` re-exports it.
- **Version isolation where you want it.** `A` and `C` may depend on different `B` versions; neither sees the other's `B`.
- **Deduplication where you want it.** If `A` and `C` depend on the same `B` version, the linker shares one `B`.

The frontend can still inline aggressively _within_ a package. Cross-package inlining is a linker/backend decision, because that is where package identity and visibility are enforced.

## What to add to the CIR now

Two small things, both optional, both forward-compatible:

```ts
export type ClawrModule = {
  $schema: '...'
  source?: string // single-file case
  sources?: string[] // bundled case; if present, Span.file indexes it
  package?: {
    // optional; absent = anonymous module
    name: string
    version: string // e.g. "1.2.3"
  }
  startBlock?: Statement[]
  declarations?: Declaration[]
}

export type Span = {
  file?: number // index into sources; absent = 0
  from: [line: number, col: number]
  to: [line: number, col: number]
}

export type RCTypeLattice = {
  type: 'rc-type'
  package?: { name: string; version: string } // absent = current module's package
  namespace?: string
  name: string
}

export type InterfaceLattice = {
  type: 'interface'
  package?: { name: string; version: string }
  namespace?: string
  name: string
}
```

And a matching rule in the schema doc:

> Entity identity is `(package, namespace, name)`. Two entities with the same `namespace` and `name` but different `package` are **different entities**, even if their structure is identical.

That one sentence is the whole decision. Everything else — deduplication, version resolution, hiding, the linker — is an implementation of it.

## What to defer

You can defer almost all of the machinery:

- The package manifest format.
- The linker / resolver.
- Version resolution rules (semver vs exact).
- Whether packages are directories, archives, or single files.
- Whether the stdlib is one package or many.

You cannot defer:

- Putting `package` on `RCTypeLattice` and `InterfaceLattice`.
- Putting `sources?` on `ClawrModule` and `file?` on `Span`.
- Writing the identity rule down.

Those three are cheap to add now and expensive to add later. The rest is a project, and you can start it when the stdlib forces your hand — which, based on your own reasoning, is soon.
