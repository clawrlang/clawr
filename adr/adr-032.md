# ADR-032: `subset` and `type`

> Status: ✍🏼 Draft

## Context

The `integer` and `real` universes support subsets based on ranges. Such a range might be useful to declare officially. The `truthvalue` universe has only three values/states and supports enumerated subsets selecting any one, two or all of said states.

A `real` also needs a representation (its precision). That is a separate property from its range (see [ADR-025](./adr-025.md)), so it is not part of a `subset`. A range alone is a `subset`. A range together with a representation is a `type`. This ADR covers named ranges, and the named bundles that standard numeric formats need.

**Terminology.** A `universe` is a top set (`integer`, `real`, `truthvalue`, `rc-type`). A `subset` is a universe plus a range. A `type` is a subset plus, for `real`, a representation.

![taxonomy](./images/type-taxonomy.svg)

**Precision base and storage base.** In `sig n base`, `base` defines the precision and representation requirements. For `bin` and `ter`, the storage base is flexible as long as precision holds above $x_{\text{guarantee}}$ (see [ADR-025](./adr-025.md)). For `dec`, the type strictly mandates a base-10 decimal representation. This ensures that `dec` behaves predictably according to decimal arithmetic expectations (e.g. `0.1 + 0.2 == 0.3`), while binary/ternary types focus on conceptual precision across architectures.

## Decision

The `subset` keyword defines a named subset of the `truthvalue`, `integer` or `real` universes.

- `subset boolean = truthvalue(false|true)`
- `subset natural = integer(1...)`

Subset and type declarations do not propagate to the CIR. They are only aliases used by the frontend. The range and representation they stand for are carried by the variable's type.

### Binary integer widths

Integers have no precision axis: the range alone determines the representation, so a `subset` suffices.

- `subset int32 = integer(-2^31..<2^31)`
- `subset uint32 = integer(0..<2^32)`
- `subset int64 = integer(-2^63..<2^63)`
- `subset uint64 = integer(0..<2^64)`
- `subset int128 = integer(-2^127..<2^127)`
- `subset uint128 = integer(0..<2^128)`

### Balanced ternary integers

A balanced ternary range is symmetric and includes both ends, so it uses `...` rather than `..<`:

- `subset btint27 = integer(-(3^27-1)/2...(3^27-1)/2)`
- `subset btint54 = integer(-(3^54-1)/2...(3^54-1)/2)`
- `subset btint81 = integer(-(3^81-1)/2...(3^81-1)/2)`
- ...

### IEEE-shaped binary types

A named bounded real type is a range plus a precision, so it is a `type`, not a `subset`:

```clawr
type float64 = real(-(2^53-1)*2^971...(2^53-1)*2^971) sig 53 bin
```

The range explicitly caps the magnitude. For `float64`, `sig 53 bin` requires 53 significant binary digits at and above $x_{\text{guarantee}}$; below it, reduced precision is allowed. The boundary is approximately binary64's smallest normal value, so its subnormal range is permitted by the type's precision contract. This is intentional: a binary backend with IEEE binary64 support can use that format to lower `float64` with confidence.

| Type       | `sig` (bits) | $x_{\text{guarantee}}$ | Largest magnitude                  |
| ---------- | ------------ | ---------------------- | ---------------------------------- |
| `float16`  | 11           | $≈ 2^{-14}$            | $(2^{11}−1) \cdot 2^5 $            |
| `float32`  | 24           | $≈ 2^{-126}$           | $(2^{24}−1) \cdot 2^{104 }$        |
| `float64`  | 53           | $≈ 2^{-1{,}022}$       | $(2^{53}−1)·2^{971}$               |
| `float128` | 113          | $≈ 2^{-16{,}382}$      | $(2^{113}−1)·2^{16{,}271 }$        |
| `float256` | 237          | $≈ 2^{-262{,}142}$     | $(2^{237}−1) \cdot 2^{261{,}907 }$ |

The $x_{\text{guarantee}}$ column follows the formula in [ADR-025](./adr-025.md). These types specify a range and precision; they do not mandate IEEE bit layout. Their ranges and precision guarantees are intentionally aligned with the corresponding IEEE binary formats where such formats exist. Arithmetic rounds after each operation as specified by [ADR-027](./adr-027.md).

- **IEEE lowering is the intended binary-backend path.** A corresponding IEEE format has the stated maximum magnitude and full precision at and above the guarantee boundary; its subnormal range is allowed below that boundary. The representation can therefore be used directly where the backend supports it.
- **Results may differ across platforms.** Storage grids and operation precision derivation can affect results; `(a * b) + c` must preserve the rounding after each operation and is not promised to match across platforms.
- **Clawr's value semantics still apply.** NaN and ±∞ are not reals, and ±0 collapse to one real value. The backend must preserve Clawr's specified error behavior at range boundaries even when using IEEE storage. Interop with C `double` bit patterns is an explicit conversion at the boundary (for example from a `bitfield`).

> [!tip]
>
> The backend does not have to use the “intended” IEEE format for `float64` or other types; it only needs to meet the precision and range guarantees specified by the type. Using `double` for all `real` values that fit within its precision and range is acceptable and can dramatically reduce [the combinatorial explosion](./adr-024.md) of storage formats and conversions.

### Balanced ternary types

The base word `ter` is reserved. No ternary hardware exists yet, and the only layout reference is an independent draft (Ternary27: 27 trits made of a 2-trit type code, a sign trit, a 5-trit exponent and a 19-trit significand). It is not known whether that draft has been submitted to a standards body.

Values derived from the draft, to be verified before this is adopted:

```clawr
type btfloat27 = real(-(3^20-1)/2*3^102...(3^20-1)/2*3^102) sig 20 ter
```

- `sig 20` counts the sign trit, which is the leading digit of normal numbers in the referenced format. A finite-exponent ternary layout can serve bounded types when its precision meets the guarantee above $x_{\text{guarantee}}$; reduced precision is allowed below.
- Speculative: larger ternary representation might be formed as 1, 2, 3: `2*27 = 54` and `3*27 = 81`. The complete series would be: $3^k, 2 \cdot 3^k, k \in \mathbb{N}$
- In balanced ternary, round-to-nearest is truncation, so there are no ties.
- The ideal precision grids for `bin`, `ter`, and `dec` never nest as exact value sets: 1/3 is exact in `ter`, 1/2 is not; 1/2 is exact in `bin`, 1/3 is not; 1/10 is exact in `dec`, neither 1/3 nor 1/2 is. So there is no implicit conversion between precision bases, only an explicit `round`.
- The `bt` prefix (balanced) is meaningful: positive and balanced ternary give different value sets at the same digit count. Avoid `ternary27`, because `ternary` already names the truth value.
- Rounding-direction type codes, NaNs and infinities belong to a boundary type, as for the IEEE-shaped types.

## Rationale

- Easy reuse for type declarations.
- Seems like an obvious feature as subsets already play an important role.
- A named type that bundles range and precision cannot be written inconsistently. A prose convention ("use `sig 53` with this range") cannot be checked, and the pairing is what the name means.
- Standard types describe range and precision rather than prescribing bit layout. Their IEEE-shaped bounds let a backend use a corresponding IEEE representation directly when available, while keeping the type contract meaningful on other hardware.

## Open Questions

1. **Where do the standard types live?** In the standard library as ordinary declarations, or as built-in names?
2. **Sizes without a standard.** `btfloat54` and up, and any ternary decimal-like formats, wait for hardware and standards. Speculation: larger sizes might follow the series $3^k$ and $2 \cdot 3^k$ (27, 54, 81, 162, 243, ...), since $2 \cdot 27 = 54$ and $3 \cdot 27 = 81$.
