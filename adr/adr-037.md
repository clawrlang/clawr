# ADR-037: Hashing and `HashEquatable`

> Status: ✍🏼 Draft

## Context

The standard-library sketch proposes `HashEquatable`, a backend-defined
`HashCode` and a `HashBuilder`. Hash-based sets and dictionaries will need
compatible equality and hashing, but Clawr does not yet have collections.
The [standard-library proposal](https://clawrlang.github.io/clawr-doc/std-lib/)
also leaves the hash representation and algorithm to the backend.

An application should be able to describe which parts of a value determine
its equality without selecting a machine word size or implementing its own
hash mixing. In particular, the frontend should not need to know the range
or representation of a backend's hash codes.

## Proposed direction

`HashEquatable` requires `Equatable`. Its hashing requirement contributes a
value's equality-relevant components to a runtime-provided builder. The
collection or runtime creates and finalizes the builder; the conforming
value does not choose the algorithm or return a hash code.

Equal values are assumed to produce the same hash when contributed to a
builder using the same hashing context. Since the implementation is provided
by the programmer, there is no guarantee that it is true. Both frontend and
backend MAY assume that the programmer upholds this contract.

The following is an API sketch, not currently implemented syntax:

```clawr
trait HashEquatable: Equatable {
    func hash(into builder: HashBuilder)
}

// Backend-provided service that mixes multiple `HashEquatable` values into a single hash code
trait HashBuilder {
  func add(value: HashEquatable)
  func mixedValue() -> HashCode
}

// Future companion object for HashBuilder
companion HashBuilder {
  extern func new() -> HashBuilder
}

// Initial implementation as a free function(should be removed once companion object is supported)
extern func newHashBuilder() -> HashBuilder
```

The companion object feels like a natural place to provide a constructor for `HashBuilder`, but it may be complex to implement and integrate with the backend and runtime. The free `extern` function `newHashBuilder()` provides a simpler initial approach.

For example, if equality of a `Money` value depends only on `cents`, its
`hash(into:)` implementation contributes `cents` to the supplied builder.
The spelling and signatures of builder operations are still open: generics,
overloads or distinct operations for each supported primitive are possible.
They must support composition of user-defined values, not just individual
primitives.

`newHashBuilder()` is a free `extern` function rather than a companion
method. It would be available to ordinary programs initially; hiding it is
deferred until visibility is designed. The declaration and the builder's
ownership, mutation, and runtime ABI remain to be specified. This draft
does not assume that `extern` currently supports types or methods.

### Equality and hash contract

- For values of the same type, if `a.equals(b)` is `true`, hashing each
  into a **fresh builder using the same hashing context** must produce the
  same final hash. The same context means the same algorithm, seed and
  relevant parameters.
- Unequal values may have equal hashes. A collection must use equality to
  distinguish keys after a hash match.
- Implementations must contribute values consistently with their equality
  definition, including nested values. Framing component contributions
  must not depend accidentally on how a value was split into calls.
- A key's equality- and hash-relevant state must remain stable while it is
  stored in a collection. How collections enforce or guarantee this is
  deferred.

The consistency requirement applies to implementations of `HashEquatable`;
the type checker cannot generally prove it. Hash quality also depends on the
conformance: a user implementation that contributes nothing can produce
many collisions even with a good runtime algorithm.

### Backend-owned hashing

The backend and runtime choose the internal hash representation, algorithm
and seed. A backend may use a bounded integer, but no particular range,
width or storage base is part of the frontend contract. Hash results are not
portable or stable across processes, backends or runtime versions, and must
not be used as persistent identifiers.

The runtime must make compatible contexts available to every hash operation
within a collection, including insertion, lookup, removal and resizing.
Independently seeded builders for the same collection would break lookup.
One possible initial design uses a securely generated process-wide key,
with each `newHashBuilder()` starting fresh state under that key; a later
collection-specific context is possible, but its API is not yet specified.

For hash tables exposed to adversarial keys, the backend should use a
well-established keyed hash with a secret generated by an appropriate
secure random source. Randomizing a multiplier alone is not a sufficient
design. The choice of algorithm, entropy failure behavior, and whether
the public builder can expose a finalized result require further design.

### `HashCode`

Initially the finalized hash is an internal runtime detail, not a public
Clawr type. This avoids pretending that the frontend knows the bounds of
a backend-specific integer subset. If programs later need a hash value,
an opaque type or a mechanism for backend-provided type declarations can
be designed then. Existing `subset` and `type` aliases in
[ADR-032](./adr-032.md) are frontend-resolved, not backend-selected.

## Implementation considerations

1. Define trait inheritance and `HashEquatable`'s conformance rules:
   today the interface parser does not accept a supertrait list. Decide
   how inherited requirements and witness dispatch are represented.
2. Define the builder's Clawr-facing interface, ownership and mutation
   semantics, its creation and finalization lifecycle, and how nested
   conformances contribute values. Decide which builder operations can be
   declared and called without generics or overloading.
3. Add a backend/runtime builder with a compatible hashing context and
   canonical component encodings. Specify equality-consistent behavior
   for each primitive before claiming its conformance, especially where
   different representations denote equal values.
4. Prove the path end-to-end with a user-defined value containing an
   integer field. Test equal values, unequal values, deliberate collisions,
   component order and framing, nested contributions, and repeated fresh
   builders in the same context. Test backend-specific seed behavior without
   relying on hashes differing by chance.
5. Defer collections, collection key ownership, source-level visibility,
   a public `HashCode`, and companion constructors. Test the runtime
   contract directly until collections exist.

## Alternatives considered

- **Return `HashCode` from each value.** This exposes a backend-dependent
  result to the frontend and makes combining components and managing seeds
  harder to centralize.
- **Fix an integer range and hash algorithm in Clawr.** This simplifies the
  interface but unnecessarily restricts backends and invites reliance on
  a stable result.
- **Use the documented `hashCode(using:) -> HashCode` sketch.** It passes a
  builder but still makes each value return a finalized code; contributing
  into a shared builder makes nested composition more direct.

## Consequences

- User code describes equality-relevant components; the runtime controls
  representation, seeding and mixing.
- The frontend can reason about conformance and method signatures without
  knowing the set of possible hash codes.
- The initial free factory is visible until visibility support exists.
- This is a draft: none of the sketched hashing API, trait inheritance or
  collection behavior should be treated as implemented or adopted.
