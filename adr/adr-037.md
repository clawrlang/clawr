# ADR-037: Hashing and `HashEquatable`

> Status: 📝 Proposed

## Context

Most object-oriented languages define a `hashCode` or equivalent method on objects, which returns an integer that is presumed equal for equal objects. This hash is used in hash-based collections like sets and dictionaries to locate objects in constant time.

The agnostic approach of Clawr means that the frontend `MUST NOT` assume any particular hash representation or numeric base. Hence, it also cannot implement its own hash mixing or rely on specific hash code properties. Instead, it needs to rely on the backend to provide a suitable hashing mechanism, allowing for flexibility and optimization at the runtime level.

An application should be able to describe which parts of a value determine its equality without selecting a machine word size, a numeric base, or a specific hash representation.

## Decision

### First-stage implementation

The contribution API is implemented. Its portable contract is defined in the [standard library](../spec/stdlib/README.md#hashequatable); runtime-specific hashing and finalization are described in the [example backend guide](../guides/implementation/backend/hashing.md). Interface inheritance rules are defined in [Traits and Roles](../spec/language/user-types/trait-role.md#interface-inheritance).

Collections, Clawr `HashCode`, `mixedValue()`, `bucketIndex`, optional primitive
methods, initializer/companion construction and layer-2 visibility are
deferred. The broader APIs below are design sketches, not implemented syntax.

### Deferred Hashing Design

For later bucket indexing, `CollectionIndex` is a candidate backend-owned
name with frontend semantics `integer(0...)`. An ordinary subset loses its
name before CIR, so backend-specific fixed-width lowering needs preserved
identity and explicit conversion/representability rules. It must not narrow
all nonnegative integers. A capacity must also be positive.

There are three layers of hashing in Clawr:

1. **User-facing.** `HashEquatable.hash(into:)`. The only hashing signature ordinary programs see or implement.
2. **Library-facing.** `HashBuilder`, `HashCode`, `bucketIndex`, and the builder factory. Named by collection implementations (when collections exist) and by the standard library. Not intended for ordinary programs.
3. **Backend/runtime.** The opaque representations, mixing algorithm, seeding, and canonical encodings behind layer 2.

The `HashCode` type represents an opaque hash value. It is created and manipulated through the `HashBuilder` and related library-facing APIs, but its internal representation is hidden from ordinary programs. It functions like a `trait`, but without the ability for programs to conform to it themselves.

The `HashBuilder` is an opaque `service` type (much like a `role`, but one that cannot be embodied by other types). It is used to incrementally construct a `HashCode` by feeding it the components of a value that contribute to its hash. It provides a controlled interface for combining hashable elements without exposing the underlying representation or mixing algorithm.

The mechanisms for layer 2 are not yet designed. Until they are, these declarations `MAY` be visible to all programs; that is a temporary concession to allow progress, not a design goal.

### `HashEquatable`

`HashEquatable` requires/inherits `Equatable`. Equal values MUST produce equal hashes in the same hashing context. Matching hashes do not imply equality: collisions are valid and collections must check equality. Equality- and hash-relevant state must remain stable while a key is stored.

The method `hash(into:)` is responsible for feeding the relevant components of the value into the provided `HashBuilder`. It must do so in a stable order to ensure consistent hashing across equal values. It does not return a hash code, because the frontend does not have access to the underlying hash representation. Instead, it feeds components of the value into the builder, which the runtime then uses (internally) to compute the final hash code.

```clawr
trait HashEquatable: Equatable {
    func hash(into builder: HashBuilder)
}
```

### `HashBuilder`

The `HashBuilder` is an opaque `service` type (like a `role` that cannot be embodied by ordinary programs). It is instantiated once per hashing operation and is used to incrementally build a `HashCode` from the components of a value.

```clawr
service HashBuilder {

    /*
        This method is responsible for detecting boxed primitive values and directly converting them into a `HashCode` using backend-defined mechanisms. That value should be mixed into the aggregate hash state maintained by the builder.
        If `value` is not a boxed primitive, it should delegate to `value.hash(into: self)` and not attempt any further processing itself.
    */
    extern func add(_ value: HashEquatable)

    // Optionally, the backend may provide additional `add(<primitive>:)` methods that do not require boxing for primitive types.
    extern func add(integer value: integer)
    extern func add(real value: real)
    extern func add(truthvalue value: truthvalue)
    extern func add(string value: string)

    // Not visible to user code; used by the standard library to obtain the mixed hash value.
    extern func mixedValue() -> HashCode

init:
    // Invoked by the `{HashBuilder.new()}` data literal
    extern func new()
}
```

The `add(<primitive>:)` methods are leaf methods that must be implemented by the backend to calculate a hash contribution for the given primitive value. They could be made public and called directly by the programmer, or they could be the equivalent of `helper` methods only used internally. They should be called by the generic `add(_:)` method if the input is a primitive value.

The program never needs to call the leaf `add(<primitive>:)` methods directly; they exist for convenience and a small performance gain. It might just call `add(_:)` instead (which would require boxing them). The frontend could automatically convert `add(_:)` calls into the appropriate leaf calls as a future optimization.

The future `mixedValue()` method must not consume the builder. Repeated snapshots of unchanged state produce the same result; adding further contributions remains valid. The runtime already tests this behavior with its keyed algorithm.

Adding the same values in a different order is expected to produce a different `HashCode`. The hash function is not required to be commutative. Maybe it _should not_ be commutative in fact; it only needs to consistently produce the same hash every time, given **the same sequence** of input values.

### `HashCode`

A `HashCode` is used to index into collections and to compare hashed values for equivalence within a hashing context.

The `HashCode` type represents an opaque hash value produced by a `HashBuilder`. The exact representation is determined by the backend and is not exposed to user code. Clawr code cannot construct, manipulate, or interpret `HashCode` values directly.

```clawr
// Opaque “primitive” value type. Not constructible, manipulable, or interpretable by user code.
opaque type HashCode
```

The backend chooses the representation: probably a single register's worth of bits that it treats as an integer value (with modulus), but the backend is free to implement it in other ways, as long as it is able to mix multiple values consistently and can check for equality, and as long as it is able to use the hash to find bucket indices correctly. The backend `MAY` choose to use a pointer — with additional information — to implement the type, but in that case, the frontend will not be able to dereference it; the pointer address would _be_ the `HashCode`.

Whatever the bits (or trits) represent to the backend, the frontend only sees them as opaque `HashCode` values. It is considered a primitive value type in the frontend, so it is atomic, immutable, and can be only copied by value (`isolated` bindings).

### `bucketIndex`

```clawr
// Result `MUST` satisfy 0 <= result < max.
extern func bucketIndex(hash: HashCode, max: integer (0..<2^32)) -> integer (0..<2^32)
```

Alternative syntax:

```clawr
trait HashCode {
    func bucketIndex(max: integer (0..<2^32)) -> integer (0..<2^32)
}
```

A problem with the `trait` syntax is that it suggests that the user can define their own implementation of `HashCode` and its `bucketIndex` method, which is not intended. The `HashCode` type and its associated method are backend-owned and should not be implemented by user code.

To avoid the `trait` problem, the `bucketIndex` function can be provided as an extension on the `HashCode` type. This allows the backend to implement it once, and the collection algorithm can still call it as a method. (Requires implementation of the [Extensions](./drafts/extensions.md) idea.)

```clawr
extension HashCode {
    extern func bucketIndex(max: integer) -> integer
}
```

> [!question] What is the correct type for `bucketIndex` and `max`?
>
> The `integer` type is arbitrary-precision. An unqualified `integer` would not generally fit the processor's register width.
> But, the frontend `MUST` be agnostic to the actual representation chosen by the backend, so even adding bounds to the type is
> not sufficient. Unless the backend can somehow communicate the actual representation to the frontend (maybe through an opaque-ish subset?).
>
> For now, lets assume that the max value for `bucketIndex` is always valid. The implementor is not the programmer, so the frontend does not need to check it.
> It is implemented by the collection library, not by the frontend code. Maybe that means that collections cannot be created outside the standard library?

The backend implements this function. The frontend cannot perform modular reduction on an opaque `HashCode`; only the backend can map one to a frontend `integer` suitable for indexing collection storage. The postcondition is trusted because the backend implements the operation; implementations may debug-assert it.

If a collection context object is introduced later, `bucketIndex` becomes a method on it; a free function is sufficient for now.

### Backend-owned hashing

The backend and runtime choose the internal hash representation, the mixing algorithm and a random seed. A backend may use a bounded integer or a field; no particular range, width, base or storage form is part of the frontend contract. Hash results are not portable or stable across processes, backends or runtime versions, and must not be used as persistent identifiers.

The seed should be securely generated at each process start (and kept secret) to prevent adversarial manipulation of hash values.

## Implementation considerations

1. Trait inheritance and implied supertrait conformances are implemented; traits and roles cannot inherit from each other.
2. The initial opaque shared builder and free factory are implemented with ARC lifetime management.
3. Defer actual collections, collection key ownership, source-level visibility of layer 2, a public `HashCode`, and companion constructors. Test the runtime contract directly until collections exist.
4. General opaque primitive types and backend-owned index representations remain to be designed.

## Alternatives Considered

- **Return `HashCode` from each value.** Exposes a backend-dependent result to the frontend and makes combining components and managing seeds harder to centralize.
- **Fix an integer range and hash algorithm in Clawr.** Simplifies the interface but unnecessarily restricts backends and invites reliance on a stable result.
- **`HashCode` and `HashBuilder` as standard `trait` and `role`.** Invites user conformances that could bypass the runtime's canonical framing and context handling.
  - They `MAY` _appear_ as ordinary abstract types in APIs, but they `MUST NOT` be directly instantiated or conformed to by user code.
- **`bucketIndex<Max: integer>` with a dependent return type.** Requires value-indexed types and cannot express a runtime table capacity.
- **`bucketIndex` returning `HashCode`.** The frontend cannot index storage with an opaque token; the conversion to a frontend `integer` belongs in the backend.

## Consequences

- User code describes equality-relevant components; the runtime controls representation, seeding and mixing.
- The frontend reasons about conformance and method signatures without knowing the set of possible hash codes, their width, or their base.
- The runtime can change the underlying hash representation without affecting frontend code.
- May be hard (even impossible) to define new collections that integrate with the hashing runtime.
